# Decisions log

Append-only. Every entry has a date, the decision, the reason and the alternatives rejected. Never edit or reopen a locked entry; if one looks wrong, write `docs/proposals/NNN-title.md` and notify the owner.

Id scheme:
- **D-Lnn**: locked by owner (brief §2). Reason: the owner's brief, cited per entry. Alternatives: not recorded, because the owner chose.
- **D-Onn**: decided by orchestrator for owner (`docs/agent/PREDECISIONS.md`, 2026-10-11). Ranks just below D-L.
- **D-nnn**: decided by an agent session, applying the brief's §3 tie-breakers where the spec is silent.

## Locked by owner (brief §2)

### D-L01 · Syntax and files (locked by owner)
- **Date:** 2026-10-11
- **Decision:** The syntax is TypeScript plus one contextual keyword, `parallel`, which is a keyword only in `parallel <expression>` (expression position) and `parallel for (...)` (statement position). Existing code that uses `parallel` as an identifier keeps working. The brief names the extension `.pts`; the owner later overrode it to `.ps` (see D-O01).
- **Reason:** Brief §2.1.

### D-L02 · The compatibility principle (locked by owner)
- **Date:** 2026-10-11
- **Decision:** A source program that uses only plain TypeScript features (no `parallel`, no integer types, no `pts:` imports) prints exactly what Node prints when run as TypeScript, except where the spec documents a difference.
- **Reason:** Brief §2.1.

### D-L03 · Front end is a fork of TypeScript 7 (locked by owner)
- **Date:** 2026-10-11
- **Decision:** Fork typescript-go pinned to the latest 7.x release tag (`typescript/v7.0.2`). The compiler `pts` is written in Go inside the fork's module (it needs `internal/`). Upstream modifications are minimal, marked `// PTS:` and listed in `docs/FORK.md`; new code goes in new directories (`pts/`, `cmd/pts/`). Upstream parser and checker suites stay green for the areas touched. `LICENSE` and `NOTICE` stay intact; ParallelScript's own code may use Apache-2.0. Prelude types and `pts:` modules are declared in ParallelScript's own lib declaration files.
- **Reason:** Brief §2.2.

### D-L04 · Compilation pipeline and IR (locked by owner)
- **Date:** 2026-10-11
- **Decision:** TS AST plus checker → PTS semantic checks → lowering to a typed ParallelScript IR → IR passes → C11 → clang -O2, linked with the runtime into one native binary. The IR is structured (SSA not required) and fully typed, with explicit boxing, closure environments, monomorphized generics and async/generator state machines. C is never emitted directly from the AST. Generated C is readable and carries `#line` directives pointing at the source.
- **Reason:** Brief §2.3.

### D-L05 · Runtime and CLI (locked by owner)
- **Date:** 2026-10-11
- **Decision:** The runtime is C in `pts/runtime/`, statically linked. bdwgc and libuv are vendored as pinned submodules and built from source; `pts build` output depends only on libc. The CLI is `pts build file -o out`, `pts run`, `pts emit-c`, `pts test` (later) and `pts lsp` (M7). `--cc zig` cross-compiling is a stretch goal.
- **Reason:** Brief §2.3.

### D-L06 · Fixed variable types and `number` (locked by owner)
- **Date:** 2026-10-11
- **Decision:** Variables have fixed types. `number` keeps exact JS semantics (IEEE-754 f64, `NaN`, `Infinity`, `-0`). Number-to-string conversion matches JS exactly via shortest round-trip formatting.
- **Reason:** Brief §2.4.

### D-L07 · Integer types and numeric rules (locked by owner)
- **Date:** 2026-10-11
- **Decision:** `int` (i64) and `i8 i16 i32 i64 u8 u16 u32 u64 f32 f64` are declared in a global prelude, starting as aliases of `number`; the PTS semantic pass enforces the rules (and later the language server shows them). Literals take their type from context. Implicit conversions are lossless only (integer → `number`; smaller → larger integer of compatible sign); anything lossy needs `as`. `int` mixed with `number` yields `number`. Numeric `as` converts with Rust rules (truncate toward zero, saturate, `NaN` → 0). Integer overflow wraps; integer `/` truncates; integer division or modulo by zero throws `RangeError`. `typeof` of any numeric type is `"number"`.
- **Reason:** Brief §2.4.

### D-L08 · Strings (locked by owner)
- **Date:** 2026-10-11
- **Decision:** Strings are immutable UTF-8 with a pure-ASCII flag. `.length`, `s[i]`, `charCodeAt` and `slice` count UTF-16 code units; ASCII strings take an O(1) fast path and non-ASCII strings may build an index lazily.
- **Reason:** Brief §2.4.

### D-L09 · `any`, `unknown` and casts (locked by owner)
- **Date:** 2026-10-11
- **Decision:** `any` is a checked dynamic value: operations follow JS semantics at runtime via type descriptors, and assigning an `any` to a typed location checks the value and throws `TypeError` on mismatch. Every runtime type carries a descriptor (name, fields → offsets, methods), reused by `console.log` and JSON. `unknown` is as in TS. Non-numeric `as`: upcasts free; downcasts and unrelated casts checked at runtime (`TypeError`); `x!` checked; `as unknown as T` cannot lie.
- **Reason:** Brief §2.4.

### D-L10 · Objects, classes and interfaces (locked by owner)
- **Date:** 2026-10-11
- **Decision:** Classes have fixed layouts and vtables, with single inheritance, fields, methods, accessors, statics, `private`/`#private`, abstract classes and `instanceof`. Interfaces stay structural; runtime dispatch goes through per-(concrete type, interface) tables built at compile time where possible and cached at runtime otherwise. Object literals are anonymous struct types; optional properties are stored as `T | undefined`. Properties cannot be added or deleted after construction; `delete` works only on index-signature types; `Record<string, T>` and index signatures are hash maps. `null` and `undefined` are distinct; `?.` and `??` are supported.
- **Reason:** Brief §2.4.

### D-L11 · Unions, generics and equality (locked by owner)
- **Date:** 2026-10-11
- **Decision:** Unions are tagged values; narrowing works for `typeof`, `instanceof`, `in`, discriminants, equality and user-defined type guards (the checker reasons, the backend emits tag tests). Generics are monomorphized. `===` compares objects by identity and strings and numbers by value with JS `NaN` rules; `==` has its JS meaning.
- **Reason:** Brief §2.4.

### D-L12 · Exceptions and unsupported features (locked by owner)
- **Date:** 2026-10-11
- **Decision:** `throw`/`try`/`catch`/`finally` have JS semantics and any value can be thrown. `Error` and subclasses have `message`, `name`, `cause` and `stack` (with source lines, possibly later). Compile errors with clear explanations for: `eval`, `new Function`, `with`, `var` (suggest `let`), `arguments`, prototype manipulation (`__proto__`, `Object.setPrototypeOf`, assigning `.prototype`), `Proxy`, `Reflect`, declaration merging and namespaces. Decorators, `Symbol` beyond `iterator`/`asyncIterator`, and `WeakRef` can come later.
- **Reason:** Brief §2.4.

### D-L13 · Memory and the race-safety invariant (locked by owner)
- **Date:** 2026-10-11
- **Decision:** GC with bdwgc in thread-aware mode with thread-local allocation; pointer-free data uses the atomic allocator; a precise/generational GC is later. **Non-negotiable:** racy programs may see stale values but never crash, corrupt the heap or access out of bounds. No torn multi-word values in shared slots; growable arrays keep capacity inside the buffer and bounds-check against the buffer actually accessed; strings are immutable.
- **Reason:** Brief §2.5.

### D-L14 · Event loops and `await` (locked by owner)
- **Date:** 2026-10-11
- **Decision:** One libuv event loop per core (configurable, e.g. `PTS_THREADS`), each on its own OS thread over one shared heap; `uv_async_send` wakes a loop. Plain `await` keeps exact JS semantics: a task belongs to one loop for life and a loop runs one task at a time; single-loop ordering of microtasks, timers and I/O matches Node. Async functions and generators are state machines with GC-managed heap frames, no per-task native stacks.
- **Reason:** Brief §2.6.

### D-L15 · `parallel <expr>` (locked by owner)
- **Date:** 2026-10-11
- **Decision:** `parallel e` runs `e` as a new task on another loop and immediately returns a promise (flattened if `e` is a promise), typed `Promise<Awaited<T>>`. Captures are shared by reference. The target loop is chosen by load (least-loaded, or round-robin with stealing of unstarted tasks); tasks never migrate. Promises can be awaited from any loop and settling wakes the awaiting loop.
- **Reason:** Brief §2.6 and §6 (M5).

### D-L16 · Data parallelism, `.par`, helpers and `parallel for` (locked by owner)
- **Date:** 2026-10-11
- **Decision:** A Chase–Lev work-stealing fork-join pool, one deque per worker, separate from loop threads; a thread that starts a parallel operation helps until it finishes; Rayon's design is copied. `.par` on arrays, typed arrays and ranges offers `map` (order-preserving), `filter`, `forEach`, `reduce(fn, initial)` (associative), `flatMap`, `some`, `every`, `find` (any match), `count`, `sum`, `min`, `max`, `sort`/`sortBy` (parallel merge sort) and `toArray`, all synchronous. `range(start, end)` and `join(a, b)` come from `pts:parallel` or the prelude. `parallel for (const x of it)` is sugar for a parallel `forEach`: `continue` allowed; `break`, `return`, `yield`, `await` and labelled jumps out are compile errors; the first thrown error cancels the rest and is rethrown after joining.
- **Reason:** Brief §2.6.

### D-L17 · The single guardrail (locked by owner)
- **Date:** 2026-10-11
- **Decision:** Inside a parallel body (the operand of `parallel`, a `parallel for` body, or a function passed to a `.par` method or `join`), assigning to a captured outer `let` is a compile error suggesting `.par.reduce`, `.par.sum` or an `Atomic`. Parallel-callback parameters are marked with a branded function type in the stdlib declarations. Mutating object fields is allowed. **No other parallelism checks without asking the owner.**
- **Reason:** Brief §2.6.

### D-L18 · `pts:sync` (locked by owner)
- **Date:** 2026-10-11
- **Decision:** `Mutex<T>` (blocking `withLock(fn)`, async `lock()`), `AtomicInt`/`Atomic<int>` (`load`, `store`, `add`, `compareExchange`), `Channel<T>` (bounded or unbounded, async `send`/`recv`, `close`, `for await`) and `Once`. A concurrent map only if benchmarks or examples want it.
- **Reason:** Brief §2.6.

### D-L19 · Modules and standard library (locked by owner)
- **Date:** 2026-10-11
- **Decision:** ES modules with relative imports; stdlib modules use the `pts:` prefix (`pts:fs`, `pts:path`, `pts:process`, `pts:http`, `pts:sync`, `pts:parallel`); no npm or `node_modules` in v1. Globals: `console` (matching `util.inspect`), `Math`, `JSON`, `Promise` (with `all`, `allSettled`, `race`, `any`, `withResolvers`), timers, `queueMicrotask`, `performance.now()`, `fetch`. Built-ins: the common parts of `String`, `Array`, `Map`, `Set`, `Number`; `Object.keys`/`values`/`entries`; basic `Date`; `RegExp` (PCRE2 or a port, may come later).
- **Reason:** Brief §2.7.

### D-L20 · Tie-breakers when the spec is silent (locked by owner)
- **Date:** 2026-10-11
- **Decision:** In order: (1) memory safety under races is never traded away; (2) for plain TS code, do what Node does; (3) don't add strictness the owner didn't ask for, preferring a runtime check that throws over a compile error that blocks a reasonable program; (4) for parallel semantics, do what Rayon does for data parallelism and what Go does for tasks and channels; (5) simple and working beats clever and half-done. Every such call is logged here.
- **Reason:** Brief §3.

### D-O04 · Differential-test contract (decided by orchestrator for owner)

### D-O05 · Disambiguating `parallel` (decided by orchestrator for owner)
- **Date:** 2026-10-11
- **Decision:** The parser treats `parallel` as the operator only when the next token is on the same line and starts an expression other than `(`, `[`, `.`, `?.`, a template, `=`, an operator, `,`, `;`, `)` or `}`. `parallel for (` is the loop statement. `parallel(expr)` parses as a normal call, which the checker reinterprets as the operator only if no binding named `parallel` is in scope and it has exactly one argument.
- **Reason:** Keeps existing code that uses `parallel` as an identifier working while `await parallel(f(x))` still reads naturally.
- **Alternatives rejected:** A reserved keyword; always treating `parallel(` as the operator.

### D-O06 · `PTS_THREADS=1` (decided by orchestrator for owner)
- **Date:** 2026-10-11
- **Decision:** `parallel e` still creates a new task, on the same loop; `.par` runs sequentially on the caller.
- **Reason:** Programs stay correct with one thread.
- **Alternatives rejected:** Running `parallel e` inline (would change ordering).

### D-O07 · Uncaught errors and rejections (decided by orchestrator for owner)

## Decided by agent sessions

### D-001 · How `.ps` plugs into the front end
- **Date:** 2026-10-11
- **Decision:** `.ps` is a TypeScript implementation extension (`ScriptKindTS`; declarations emit as `.d.ts`; implied module format as for `.ts`). In the grouped extension lists used by tsconfig `include`, `.ps` is its own priority group, appended last, so `a.ps` and `a.ts` side by side are both included and upstream's ordering is unchanged. Module resolution: an extensionless import (`./x`) tries `x.ps` first, then upstream's order (D-O01); an explicit `./x.ps` resolves to that file (like `./x.ts`, it needs `allowImportingTsExtensions`, which `pts` sets). `./x.js` does not map to `x.ps`. A missed `.ps` probe is not written to the resolution trace.
- **Reason:** Smallest upstream diff that meets D-O01. Untraced misses keep every upstream `traceResolution` baseline byte-identical, so upstream tests stay green without baseline churn; appending `.ps` last keeps upstream's extension priorities and messages stable apart from the extra entry.
- **Alternatives rejected:** Putting `.ps` in the `.ts` group (would make `a.ps` shadow or be shadowed by `a.ts` in `include`). Tracing `.ps` misses (changes upstream trace baselines). Trying `.ps` only from `.ps` importers (a `.ts` file in a PTS program couldn't import a `.ps` module). Mapping `./x.js` to `x.ps` (no PTS code writes `.js` specifiers; can be added later).

### D-002 · Dynamic values are one word, encoded as in JavaScriptCore
- **Date:** 2026-10-11
- **Decision:** `pts_value`, the runtime's dynamic value (used for `console.log` arguments now, and later for unions and `any` where a static C type isn't enough), is a `uint64_t`. Heap objects are stored as raw pointers (top 16 bits zero, at least `0x10000`). Doubles are stored as their bits plus 2^49, with `NaN` canonicalised. `undefined`, `null`, `false` and `true` are small constants (`0x0a`, `0x02`, `0x06`, `0x07`). Every heap object starts with a pointer to its `pts_type` descriptor. 64-bit integers that need to live in a `pts_value` will be boxed.
- **Reason:** One word means a racing reader can never see a torn value (D-L13, tie-breaker 1). Keeping pointers raw means bdwgc's conservative scan still sees them; classic NaN-boxing puts tag bits in the pointer's top bits, which hides the reference from the GC.
- **Alternatives rejected:** A two-word `{tag, payload}` struct (can tear under races). NaN-boxing with tagged pointers (invisible to bdwgc). Boxing every number (an allocation per dynamic number).

### D-003 · The toolchain builds the C libraries itself, without CMake
- **Date:** 2026-10-11
- **Decision:** `pts/toolchain` (Go) compiles bdwgc (as the single translation unit `extra/gc.c`, with the defines its CMake build uses for threads, parallel mark and thread-local allocation), libuv (its Linux source list and defines, copied from its `CMakeLists.txt`) and the runtime (`pts/runtime/src/*.c`) with clang, archives them with `ar`, and caches each archive in `~/.cache/pts/<name>-<key>/` (`$PTS_CACHE_DIR` overrides). The key hashes the compiler version, flags, source list and the library's version header (vendored) or all its sources (runtime). Builds take a file lock and publish with an atomic rename, so parallel tests and processes build each archive once. Vendored libraries are always `-O2`; the runtime also has a `Sanitize` profile (ASan + UBSan) for its unit tests.
- **Reason:** One implementation serves the CLI and the tests. Users need only clang, not cmake or make. The cache keys keep rebuilds of user programs from rebuilding vendored libraries (D-O11). MASTER_PLAN M0.4 says "CMake (or Make)"; this meets its intent (a cached build of the vendored libraries) with fewer moving parts.
- **Alternatives rejected:** Driving the libraries' own CMake builds (needs cmake and ninja on users' machines, and slower). A Makefile (a second build implementation next to the Go one).

### D-004 · Source extension reverts to `.pts` (owner instruction; supersedes the extension in D-O01 and D-001)
- **Date:** 2026-10-11
- **Decision:** ParallelScript source files use **`.pts`**, the brief's original extension. Everything D-O01 and D-001 say about `.ps` now applies to `.pts`: `ExtensionPts` in `tspath`, its own group in the grouped extension lists, extensionless imports try `.pts` first (untraced), and `.gitattributes` maps `*.pts` to TypeScript. The `.ps` extension is no longer recognised.
- **Reason:** Owner instruction after M0.4, before any `.ps` programs existed outside the front-end tests.
- **Alternatives rejected:** Accepting both `.ps` and `.pts` (two extensions for one language, with `.ps` clashing with PostScript).

### D-005 · Fixed front-end options and an embedded prelude
- **Date:** 2026-10-11
- **Decision:** `pts` type-checks every program with fixed options: `strict`, target and module `ESNext`, `moduleResolution: bundler`, `allowImportingTsExtensions`, `moduleDetection: force` (every file is a module, so top-level names never clash with globals), `lib: ["esnext"]` (no DOM) and `types: []` (no `@types` from a `node_modules` nearby). A `tsconfig.json` is not read. ParallelScript's own declarations (`pts/lib/*.d.ts`, the prelude now) are embedded in the binary and served by a wrapping file system at `ptslib:///…`; the prelude is a root file of every program. The prelude declares only what the compiler can lower, starting with `console.log`.
- **Reason:** The language has one dialect, so its options aren't user settings (tie-breaker 5). Without the DOM lib, `document` and friends are type errors instead of link errors. Embedding keeps the declarations in step with the compiler that implements them, and a URL root can't clash with real paths. Upstream's lib loading needs no edit.
- **Alternatives rejected:** Reading `tsconfig.json` (options would change semantics; can come later for `include` lists). Registering the prelude in upstream's `LibMap` and generated lib tables (upstream edits plus regeneration). Reading the declarations from `PTS_HOME` on disk (a second thing to keep in sync).

### D-006 · One diagnostic format, PTS codes and CLI exit codes
- **Date:** 2026-10-11
- **Decision:** tsc's errors and ParallelScript's own are printed alike, one per line: `file:line:col - error CODE: message`, with the file relative to the working directory when below it. tsc errors keep `TSnnnn`. ParallelScript's codes: `PTS1001` "… is not supported yet" (valid TypeScript the compiler can't lower yet; any construct the lowering doesn't handle gets it automatically) and `PTS1002` for features left out by design (D-L12, e.g. `var`). Semantic errors are only reported when there are no syntax errors, as in tsc. `pts` exits 0 on success, 1 on compile or toolchain errors, 2 on a malformed command line; `pts run` exits with the program's own code, or 128 + the signal number if it was killed.
- **Reason:** Error tests (M0.6) match message substrings, so one stable plain-text format is enough; a code-frame "pretty" mode can come with M7.3. A blanket `PTS1001` makes the supported subset explicit and fail-safe.
- **Alternatives rejected:** Upstream's pretty formatter (hard-codes the `TS` prefix). Numeric codes in tsc's range (would read as tsc errors).

### D-007 · Names and `#line` in generated C
- **Date:** 2026-10-11
- **Decision:** IR functions become `static` C functions named `pts_fn_<name>`; top-level code is `pts_fn_main`, called from a generated `main` between `pts_runtime_init` and `pts_runtime_exit`. Locals keep their source name unless it is a C keyword, a lowercase macro the headers may define (`errno`, `stdin`, …), all-caps (likely a macro), starts with `_`, `pts_`, `PTS_` or `GC_`, or has characters C doesn't allow (`$` → `_S`, others `_uXXXX`); such names get a trailing `_`. Names are made unique per function with `_2`, `_3`, …. `#line N "<absolute .pts path>"` precedes each function and each statement whose line differs from the line the C compiler already presumes, so there are no redundant directives. String literals are `PTS_STATIC_STRING` constants `pts_str_N`, one per distinct value, written as readable UTF-8 with octal escapes for anything unprintable and `\?` against trigraphs.
- **Reason:** Readable C (brief §2.3) and exact source mapping: gdb stops at `hello.pts:1` and shows the `.pts` line. Absolute paths make the mapping independent of where clang ran.

### D-009 · Test corpus format and how Node runs differential tests
- **Date:** 2026-10-11

### D-011 · Number semantics in C: Ryu, `fmod`, `pow` and no FP contraction
- **Date:** 2026-10-11
- **Decision:** Number::toString takes its shortest round-trip digits from Ryu (`d2s_buffered_n`), vendored as the submodule `pts/third_party/ryu` pinned at tag `v2.0` (Apache-2.0) and built by the toolchain as `libryu.a`; the runtime keeps ECMAScript's notation rules. `+ - * /` and comparisons are C operators on `double`; `%` is `fmod` (`pts_number_rem`); `**` is `pow` except that `x ** NaN` and `(±1) ** ±Infinity` are NaN (`pts_number_pow`). These helpers use clang builtins, so `pts.h` doesn't pull `<math.h>` macros into generated C. The runtime and programs compile with `-ffp-contract=off`. `==`/`!=` lower to `===`/`!==` because the lowering only accepts operands of one primitive type. `NaN` and `Infinity` lower to constants when they resolve to the ES library's globals.
- **Reason:** Ryu is proven, small and fast, and it implements exactly ECMAScript's choice (shortest digits, closest value, ties to even); the existing 25,000-value differential test against `jsnum` passes unchanged. `fmod` is exactly JS's `%`. glibc's `pow` matched Node's `**` bit for bit on 200,000 random inputs, so only the spec's NaN cases need code. Without `-ffp-contract=off`, clang may fuse `a*b+c` into an FMA on targets that have one (e.g. `-march=native`), which rounds once instead of twice and breaks JS semantics.
- **Alternatives rejected:** Writing a Ryu-style algorithm by hand (more code to trust, same result). Porting V8's fdlibm `pow` (no observed difference). Including `<math.h>` in `pts.h` (its `isnan`/`signbit`/… macros would collide with user names).

### D-012 · How the integer types work
- **Date:** 2026-10-11
- **Decision:** The prelude declares `int i8 i16 i32 i64 u8 u16 u32 u64 f32 f64` as aliases of `number`. A new semantic pass, `pts/check`, recovers numeric types from annotations (prelude aliases, and user type aliases of them) and records them for the lowering; an unannotated variable takes its initializer's numeric type, and a bare literal is a `number`. Literals are untyped constants, as in Go: they take the type their context expects (a declaration's annotation, or the other operand of a binary operator), integer literals are range-checked exactly from their source text (so 64-bit values keep every digit), and a non-integer constant next to an integer operand stays a `number`. Operands of a binary operator convert to their common type: the wider of two compatible types, or `number` when an integer meets a float. Unsigned to a strictly wider signed type counts as lossless; `int → f32` is not implicit (the spec lists only integer → `number`). Mixing two integer types with no lossless common type (e.g. `i64` and `u64`) is a compile error. Arithmetic wraps (computed in `uint64_t`), `MIN / -1` wraps to `MIN` and `MIN % -1` is 0, `/` and `%` by zero throw `RangeError: Division by zero`, an integer `**` with a negative exponent throws `RangeError: Exponent must be non-negative` (BigInt's message), and unary minus on an unsigned value wraps. `f32` arithmetic is C `float`; its `%` and `**` go through `double`. In a dynamic value a 64-bit integer is a number while `|v| ≤ 2^53` and a boxed integer beyond, so `console.log` prints every digit. Error codes: `PTS2001` (lossy implicit conversion), `PTS2002` (literal doesn't fit or isn't an integer), `PTS2003` (no common type).
- **Reason:** tsc erases the aliases to `number`, so only a pass of our own can see them; annotations are where the brief says the types come from. Go's untyped constants give the brief's "literals take their type from context" a precise meaning. A compile error for `i64 + u64` follows "anything lossy needs `as`" rather than silently switching to floating point. Wrapping through `uint64_t` avoids C's undefined signed overflow (UBSan runs on the runtime tests).
- **Alternatives rejected:** Branded types in the prelude (tsc would reject `const x: int = 5`). Doing the numeric typing inside the lowering (the language server needs the diagnostics without lowering, M7.1). Converting mixed integer types to `number` (surprising loss of integer semantics). Compile-time evaluation of constant expressions (`const b: u8 = 200 + 56` wraps at run time to 0 instead of failing; can come later).

### D-014 · Strings hold lone surrogates as WTF-8
- **Date:** 2026-10-11
- **Decision:** A string's bytes are UTF-8, except that a lone surrogate (which JS strings may contain) is its 3-byte generalised encoding, as the TS scanner already produces for literals. Concatenation joins a trailing lone high surrogate and a leading lone low one into the 4-byte encoding of their code point, so `"\uD83D" + "\uDE00" === "😀"` and the representation stays canonical (byte equality is string equality). Output (`console.log`) writes a lone surrogate as U+FFFD, as Node does. `<`/`>` compare by UTF-16 code units, decoding non-ASCII strings on the fly (`pts_string_compare`). Members of the ES library that the runtime implements are listed with the prelude's in `lower.builtins`, keyed `"Interface.member"` (first `String.length`).
- **Reason:** D-L08 requires UTF-8 with UTF-16 semantics, and JS programs can build lone surrogates; WTF-8 is the standard way to keep them losslessly in UTF-8. Joining on concatenation keeps one representation per string value.
- **Alternatives rejected:** Replacing lone surrogates with U+FFFD on creation (changes `.length` and equality). UTF-16 storage (contradicts D-L08).

### D-015 · `s[i]` out of range: JS's undefined where it fits, RangeError where a string is required
- **Date:** 2026-10-11
- **Decision:** tsc types `s[i]` as `string` (D-005 doesn't enable `noUncheckedIndexedAccess`), but in JS an index out of range (negative, past the end, or not an integer) gives `undefined`, which a `string` can't hold (D-L06). The lowering keeps JS's result wherever the context can take it: as a `console.log` argument or other place that takes any value (`String.element` → `pts_value`), as an operand of string concatenation or a template literal (ToString gives `"undefined"`), and compared with a string by `===`, `!==`, `==` or `!=` (`String.elementEquals`: false, or true for `!==`). Everywhere else (a `const`, a method receiver, a relational operator, the other operand of `s[i] === t[j]`) the read is checked and an index out of range throws `RangeError: String index 5 is out of range (length 3)`. `charCodeAt` is exact JS (`NaN` out of range). Arrays (M2.4) should follow the same rule.
- **Reason:** Tie-breaker 2 (do what Node does) covers the common idioms exactly: printing, building strings, and the peek-ahead test `s[i + 1] === "="` at the end of the input. Where the value would flow into a typed `string`, a runtime check that throws (tie-breaker 3) beats a compile error, and is the same boundary check D-L09 makes for `any`. RangeError names the actual cause.
- **Alternatives rejected:** Always throwing (breaks `console.log(s[9])` and peek-ahead comparisons, which are common in plain TypeScript). Turning on `noUncheckedIndexedAccess` (rejects ordinary TypeScript and makes every array read `T | undefined`). An empty string (silently wrong). A TypeError (the cause is an index, and the message says so).

### D-016 · How the String methods are implemented
- **Date:** 2026-10-11
- **Decision:** The methods of M1.3b (`charCodeAt`, `slice`, `substring`, `indexOf`, `includes`, `startsWith`, `endsWith`, `toUpperCase`, `toLowerCase`, `trim`, `trimStart`, `trimEnd` and the aliases `trimLeft`/`trimRight`, `padStart`, `padEnd`, `repeat`) are runtime functions taking doubles for indices and applying ToIntegerOrInfinity, so a left-out (or `undefined`) index argument is passed as `NaN` where the spec turns undefined into 0 and `Infinity` where it means the length; `padStart`/`padEnd` get `" "`. Integer-typed arguments convert to `number`. Index work on an ASCII string is O(1); a non-ASCII string is scanned from the start (no lazy index yet). Searches use `memmem` on the bytes, except for a search string that starts with a lone low surrogate or ends with a lone high one, which can match half of a pair and is compared unit by unit. Results that cut a surrogate pair hold lone surrogates; padding and repeating join halves at the seams, as concatenation does. Case mapping uses Unicode's full mappings (`ß` → `SS`) plus Final_Sigma, from tables generated out of Node's ICU (`pts/runtime/gen/case_tables.mjs` → `pts/runtime/src/case_tables.h`, Unicode 17.0); `TestGeneratedStringCorpusMatchesNode` compares every code point in planes 0 and 1 with Node. Errors match V8's messages: `RangeError: Invalid count value: -1`, `RangeError: Invalid string length`.
- **Reason:** One runtime function per method keeps the generated C readable and the semantics in one place, tested under the sanitizers. Taking the tables from Node makes Node the oracle (D-L02); Go's `unicode` package is Unicode 15 and has no full (SpecialCasing) mappings. A lazy UTF-16 index needs a traced field in `pts_string`, which is allocated pointer-free today; it can come with the object model (M2.1) or performance work (M8).
- **Alternatives rejected:** Generating the tables from Go's `unicode` package (older Unicode, simple mappings only). Decoding strings to UTF-16 for every operation (an allocation per call). A lazy index now (needs a GC-traced field).

### D-018 · Bitwise operators and shifts on the integer types
- **Date:** 2026-10-11
- **Decision:** On `number`, the bitwise operators have JS's int32 semantics exactly (ToInt32 of both operands, ToUint32 for `>>>`, the shift count modulo 32). On an integer type they work on the type's own bits: `&`, `|`, `^` and `~` as in C; `<<` wraps; `>>` is arithmetic for signed types and logical for unsigned ones; `>>>` shifts the bits as unsigned and keeps the type (`-16 as i32 >>> 0` is still -16). The shift count is taken modulo the type's width, as in Java. The operands convert to their common type first, as for arithmetic (D-012), so `u8 << int` is an `int`, and an integer meeting a `number` is the int32 operation on numbers.
- **Reason:** Plain TypeScript must match Node (D-L02), which fixes the `number` case. The integer types are ParallelScript's own; Java's rules are the closest familiar ones for fixed-width types with `>>>`, never undefined behaviour in C, and agree with JS for `i32`'s `<<`, `>>`, `&`, `|`, `^` and `~`. Applying D-012's common-type rule keeps one rule for every binary operator.
- **Alternatives rejected:** Rust's rules (overshifting panics in debug builds; no `>>>`). Making `>>>` on `i32` return a `u32` like JS's uint32 (the result type would depend on the operator, unlike every other operator). Typing the shift count separately from the value (a second rule for one operator family).

### D-019 · How statements and evaluation order compile to C
- **Date:** 2026-10-11
- **Decision:** C leaves the evaluation order of operands and function arguments unspecified (and `x + (x = 5)` undefined), so `cgen` keeps JS's left-to-right order: when an operand writes (an assignment, output) next to another non-constant operand, or two operands may throw, the operands are evaluated into temporaries `pts_tmpN` inside a GNU statement expression `({ … })`, which clang accepts under `-std=c11`. Otherwise the C stays a plain expression. `x++` whose value is used, and `&&`/`||` on non-booleans, also use a statement expression. A JS `switch` (any type, cases tried in order, fallthrough, `default` anywhere) becomes an if-chain of `goto`s to case labels; its value is stored once in a local `tag`. Loops are C loops; `break`/`continue` to the innermost C loop stay C's, others are `goto <label>_break`/`<label>_continue`, and labels are written only where a `goto` jumps. `let x: T;` starts at T's zero value (tsc ensures it is assigned before use). `&&`, `||` and `?:` need operands of one type until unions arrive (M3.1), and `??` waits for M3.1.
- **Reason:** Exact JS semantics (tie-breaker 2) with readable C: the temporaries appear only in the rare expressions that need them. Statement expressions keep each expression's temporaries local without a pass that hoists them into statements. C's `switch` only takes integer constants and has no ordered, lazily evaluated cases.
- **Alternatives rejected:** Always evaluating into temporaries (unreadable C). An IR pass that splits expressions into statements (much more machinery for the same result now; may come with the async state machines in M4). C `switch` for integer cases (an optimisation for later).

### D-020 · Functions in the IR and C; the features left out by design are semantic-pass errors
- **Date:** 2026-10-11
- **Decision:** Every function declaration becomes an IR function before any body is lowered (so calls may precede declarations and recurse), with typed parameters (`ir.Func.Params`) and a result type: the numeric type the semantic pass gives it, `void`, or tsc's type. The semantic pass types parameters from their annotations, return values against an annotated result type, and arguments against parameter types; an unannotated function that returns a number takes the common type of what it returns (untyped constants follow the others, as for operands), so `function half(n: int) { return n / 2; }` returns an `int`. In C, functions are `pts_fn_<name>` (a nested one `pts_fn_<outer>_<inner>`) and the top-level code moves from `pts_fn_main` (D-007) to `pts_main`, so a user function named `main` keeps its name. Calls count as writing and throwing for the evaluation order (D-019). A non-void function whose last statement isn't a `return` ends with `pts_unreachable()`. Not yet: using variables from outside the function (top-level ones with M1.4b, closures with M2.5), function values, optional, default and rest parameters, generics, generators and async functions (PTS1001). The features left out by design (SPEC §3.10) are reported by `pts/check` (so the language server will show them) as PTS1002 with the reason: `var`, `arguments`, `eval`, `Function`, `Proxy`, `Reflect`, `__proto__`, `Object.setPrototypeOf`, assignments to `.prototype`, namespaces, BigInt, `Symbol` other than `Symbol.iterator`/`Symbol.asyncIterator`, and declaration merging; a regex literal is PTS1001 "RegExp arrives in M6". `with` needs nothing of ours: every file is a strict-mode module, so tsc rejects it. Declaration merging excludes function overloads and interfaces that merge only with interfaces.
- **Reason:** Hoisting and recursion need every signature first. Inferring an unannotated result from its returns matches how unannotated variables take their initializer's type (D-012). `pts_main` can't clash with a user name, which matters because `function main()` is common. The design exclusions are language rules, which belong with the other rules in the semantic pass (D-012). Merged interfaces and overloads change nothing at run time, so rejecting them would add strictness the owner didn't ask for (tie-breaker 3).
- **Alternatives rejected:** A `number` result for every unannotated function (a needless conversion and a surprise for `int` code). Keeping `pts_fn_main` and renaming a user `main` (confusing in a debugger). Reporting the exclusions in the lowering (the editor wouldn't see them). Rejecting interface merging (no runtime reason).

### D-021 · M1.4b split; module-scope bindings that functions use are C globals with a ready flag
- **Date:** 2026-10-11
- **Decision:** M1.4b becomes M1.4b1 (module-scope bindings in functions) and M1.4b2 (imports and exports between modules); no scope is dropped. A `let`/`const` declared directly at module scope that some function uses becomes a C global `pts_global_<name>` (the IR marks the `Local` as `Global`), with a flag `pts_global_<name>_ready` set when its declaration runs. A function's read or write checks the flag first (`pts_check_ready`) and throws `ReferenceError: Cannot access 'x' before initialization` before then, as JS's temporal dead zone does; the top-level code needs no check, because tsc rejects its uses before the declaration. Bindings no function uses stay C locals of `pts_main`. Function bodies are lowered after the top-level code, when every module-scope binding is known (function declarations are hoisted). Variables of an enclosing function or block are still not usable in a function (closures, M2.5).
- **Reason:** The session protocol's split rule. Globals keep C readable and let clang keep the other locals in registers; the flag gives JS's behaviour for the one case tsc can't see (a call before the declaration) at the cost of a well-predicted branch.
- **Alternatives rejected:** Making every module-scope binding a global (slower top-level loops, noisier C). No TDZ check (a function would read a zero value where Node throws).

### D-022 · How modules compile: evaluation order, bindings shared across modules, C names
- **Date:** 2026-10-11
- **Decision:** Every source file reachable from the entry by imports is a module of the program (declaration files have no code and aren't). `frontend.Load` lists them in ES module evaluation order (`Program.Modules`): depth first from the entry, a module after the modules it requests, in source order, each once; a module already being evaluated (an import cycle) is skipped, so it runs after the module that imported it. Every `import` and `export … from` requests its module, also one that names only types (Node, like `verbatimModuleSyntax`, keeps those imports), except `import type` and `export type … from`, which Node erases. Each module's top-level code is its own IR function, and C `main` calls them in that order (the entry's is still `pts_main`, others `pts_module_<module>`). Imports produce no code: the lowering follows an imported name through imports and re-exports (`GetImmediateAliasedSymbol`) to the exporting module's own binding, so imports are live bindings, as in JS, and a namespace import's `m.x` is the same binding. Module-scope bindings that another function or module uses are globals (D-021), and all of them, with every function, are declared before any code is lowered. `export default <expression>` is a binding of its own (`default`), set when the statement runs, as JS requires (a later assignment to the exported variable doesn't change it); when the expression names a function (which can't be reassigned) or only a type, importing the default names that directly. The ready check (D-021) is left out where the declaration has surely run: in its own module's top-level code and in the top-level code of modules that run later; functions, and modules that run earlier in a cycle, check. C names outside the entry module carry the module's file name: `pts_fn_<module>_<name>`, `pts_global_<module>_<name>`; clashes (two `util.pts` in different directories) get `_2`, `_3`, …. Names after a `pts_` prefix no longer get the C-keyword underscore (`pts_fn_main`, as D-020 intended). Not yet (PTS1001): a namespace object as a value (`console.log(m)`), dynamic `import()`, `import defer`. The semantic pass checks every module and types a module-scope binding on first use if it hasn't reached its declaration yet (a function above a typed binding it uses, or an import cycle), which also fixes a wrong PTS2001 for a function declared above an integer-typed binding it uses.
- **Reason:** Static imports fix the evaluation order at compile time, so calling each module's code from `main` in a fixed order is exactly Node's behaviour, cycles included, with no runtime module records. Resolving imports to the exporting binding gives live bindings for free and keeps generated C as plain global accesses. A snapshot binding for `export default <expression>` is what the ES spec does; skipping it for functions keeps the common `export default function` and `export default f` as direct calls. Leaving out ready checks that can never fail keeps importer code readable and fast.
- **Alternatives rejected:** One combined top-level function for all modules (loses the per-module order in cycles and the TDZ boundary). Runtime module objects with export tables (needless indirection; namespace objects can come with objects in M2). Eliding imports that name only types, as tsc does without `verbatimModuleSyntax` (Node, the oracle, doesn't). Treating `export default x` as an alias of `x` (differs from JS when `x` is reassigned later). Ready checks on every cross-module use (noise in the common acyclic case).

### D-023 · Benchmark layout; nbody moves to M2.7
- **Date:** 2026-10-11
- **Decision:** A benchmark is a directory `pts/bench/<name>/` holding `main.pts` and its Go twin `main.go` (a `main` package of the repo's Go module). Node and Bun run `main.ts` if the directory has one, otherwise `main.pts` itself (copied to a `.mts` file) when it is plain TypeScript, so the JS runtimes run exactly the program ParallelScript compiles; a `main.pts` that uses the integer types and has no `main.ts` runs under ParallelScript and Go only (`fib_int`). `pts/bench/run.sh` (`make bench`) builds everything, checks that every implementation prints the same output, runs hyperfine (`--shell=none`, 2 warm-ups, 10 runs) and prints the `docs/BENCHMARKS.md` table, where "PTS vs X" is X's mean time divided by ParallelScript's (above 1 means ParallelScript is faster). nbody moves from M1.5 to M2.7: its standard form keeps the bodies in an array of objects and needs `Math.sqrt`, none of which exists before M2.
- **Reason:** Sharing the source keeps the comparison honest (D-O15) and avoids twins drifting apart; the `.ts` escape hatch remains for programs that need ParallelScript-only features. A scalar nbody (35 module-scope variables and hand-unrolled pairs) would be throwaway code measuring something other than the usual benchmark (tie-breaker 5; the same reasoning as D-013 for `split`).
- **Alternatives rejected:** A hand-written `.ts` twin for every benchmark (drifts from the `.pts`). A scalar nbody in M1 (throwaway, unrepresentative). Pulling arrays and objects into M1 (out of order, large).

### D-024 · The object model: descriptors that are also GC layouts
- **Date:** 2026-10-11
- **Decision:** `pts_type`, the descriptor every heap object points to from its first word, holds the kind, a bdwgc mark descriptor (`gc_descr`, the descriptor's second word), the name, the superclass (`parent`), the instance size, the fields (name, byte offset, `pts_field_kind`: number, boolean, string, dynamic value, object, each integer type, f32; inherited fields first) and the methods (name, function pointer). `pts_object_new(type)` allocates a zeroed instance: with bdwgc's gcj-style allocator (`GC_gcj_malloc`, which stores the type pointer and scans only the words `gc_descr` names) when it holds pointers, and with the atomic allocator, never scanned, when it doesn't. `gc_descr` is a bitmap descriptor (`PTS_GC_POINTER_WORDS`, bit i for word i) for instances of up to 62 words and `PTS_GC_ALL_WORDS(size)` (scan every word) beyond; string, object and dynamic-value fields count as pointers. Both allocators use thread-local free lists. bdwgc is now built with `GC_GCJ_SUPPORT` and `GC_ENABLE_SUSPEND_THREAD`, as its CMake defaults have it, and `pts_runtime_init` calls `GC_init_gcj_malloc`. Descriptors are static constant data; the compiler will compute `gc_descr` from the layout when it emits a class (M2.2). The runtime's C tests run under ASan with `detect_stack_use_after_return=0`, because bdwgc can't see the fake stack frames that option puts locals in.
- **Reason:** The descriptor every object already carries becomes its precise layout at no cost per object, so number fields (doubles, and the encoded doubles of D-002) are never taken for pointers and never keep garbage alive, while allocation keeps the thread-local fast path that parallel code needs (D-L13). One descriptor serves the collector, `console.log` and JSON (D-L09).
- **Alternatives rejected:** Conservative `GC_MALLOC` for every object (number fields pin garbage, and every word is scanned). `GC_malloc_explicitly_typed` (an extra descriptor word per object and no thread-local free lists). A custom mark procedure per type (more code and slower than bdwgc's descriptor interpreter).

### D-025 · M2.2 split into M2.2a–M2.2d
- **Date:** 2026-10-11

### D-026 · How classes compile (M2.2a)
- **Date:** 2026-10-11
- **Decision:** A class declared at a module's top level is an `ir.Class`, and the static type of a reference to an instance. In C it is a struct `pts_class_<Name>` (the `pts_header` type pointer, then the fields in declaration order with their static C types; instances are pointers to it) and a `static const pts_type pts_type_<Name>` with the field and method tables and a GC layout the C compiler computes with `offsetof` (`PTS_GC_WORD`, D-024); outside the entry module the names carry the module's, as functions' do. The constructor and methods are C functions `pts_fn_<Class>_<name>` taking `this` first. `new C(args)` evaluates the arguments, allocates a zeroed instance (`pts_object_new`) and calls the constructor, which runs the field initialisers in declaration order, then its body; a field without an initialiser starts at its type's zero value (`""`, 0, `false`, `undefined` for a dynamic value), as `let x: T;` does (D-019). Method calls are direct calls. Fields and methods are found by their declarations, because the checker gives an instance's members symbols of their own. A compound assignment or `++` on a field of an instance computed by an expression with effects evaluates that expression once (`ir.Bind`). References to instances are never null until unions arrive (M3.1). The semantic pass applies the numeric rules to fields (initialisers, reads, assignments), method parameters and results, and constructor arguments. Inheritance, accessors, statics, `#private`, parameter properties, optional fields, generic and abstract classes, classes in functions, and methods as values are PTS1001 until their tasks (M2.2c, M2.2d, M2.6, M3.1, M2.5).
- **Reason:** Fixed layouts (D-L10) make a field access one load and keep the C readable, and one descriptor serves the collector, `console.log` and JSON. Declaration order is JS's property order for classes compiled with `useDefineForClassFields` (the ESNext default), so `console.log` (M2.2b) can list fields as Node does. Keeping allocation out of the constructor leaves room for `super(...)` (M2.2c), where a base constructor initialises an instance the derived `new` allocated.
- **Alternatives rejected:** Hash-map objects (slow, and against D-L10). Constructors that allocate and return the instance (no way to run a base constructor on a derived instance). Keying members by symbol (misses the checker's instantiated member symbols). Evaluating the instance twice in `o().x += 1` (wrong when `o()` has effects).

### D-027 · `console.log` of instances is a runtime port of `util.inspect`, driven by descriptors
- **Date:** 2026-10-11
- **Decision:** The runtime (`pts/runtime/src/inspect.c`) formats a class instance from its `pts_type`: the class name, then each field in descriptor order as `key: value`, following Node's `formatValue`, `formatRaw`, `reduceToSingleString` and `isBelowBreakLength` with the default options (depth 2, `breakLength` 80, `compact` 3), `strEscape` for strings (quote choice, escapes, lone surrogates as `\uXXXX`), Node's `keyStrRegExp` for bare keys, `[Name]` beyond depth 2 (but `Name {}` for an instance without fields at any depth), and `<ref *n>`/`[Circular *n]` for cycles. Line lengths count UTF-16 units, as Node's `.length` does. 64-bit integer fields print every digit. An object field still NULL (read before the constructor assigned it) prints `undefined`. The output is built in C heap buffers, never the GC heap.
- **Reason:** One generic formatter over descriptors serves every class without generated code per class (D-L09), and porting Node's functions line for line makes the output match byte for byte (D-O16); it grows into the full port in M3.6 (arrays, `Map`, `Set`, format strings).
- **Alternatives rejected:** Generating a print function per class in C (code bloat; the inspect rules would be spread over generated code). Formatting in the compiler (instances only exist at run time).

### D-028 · How inheritance compiles (M2.2c)
- **Date:** 2026-10-11
- **Decision:** A subclass's C struct starts with its parent's struct as the member `pts_base`, so an inherited field is `o->pts_base.f` and an instance converts to an ancestor with a cast (`ir.ClassCast`), which C allows because a struct pointer converts to a pointer to its first member. `ir.Class` gains `Parent` and `Abstract`; `Fields` are the class's own, and the descriptor lists `AllFields` (inherited first) with `offsetof` paths. A method is an `ir.Method`; it is *virtual* when it is abstract, overridden or an override, and every chain of overrides has one *slot*, its topmost method. A class whose hierarchy has slots gets a generated method-table struct `pts_vtable_<C>` that starts with the parent's (`pts_base`) or with the `pts_type` itself (`pts_descriptor`), followed by a typed function pointer per slot the class introduces; its descriptor `pts_type_<C>` is that struct, so the instance header points at the `pts_type` inside it, and a virtual call is `((const pts_vtable_<Slot> *)o->pts_header)->m(o, …)`: two loads, as in C++. Every implementation of a slot takes `this` as the slot's class and casts it on entry (`pts_this`), so the table holds the functions without casts and every call is through the function's own type. A call is virtual only when a subclass of the receiver's static class overrides the method (or it is abstract); otherwise it is a direct call, which C can inline (class hierarchy analysis over the whole program). `super.m()` is a direct call; `super(args)` calls the parent constructor on `this`, and the subclass's field initialisers run right after it returns, as in JS; a subclass without a constructor passes its arguments on. A field redeclared with the same type is the inherited field with a new initialiser. `instanceof` is `pts_instance_of`, a walk up the `parent` chain. Narrowing is trusted: an instance converts to a subclass only where the checker narrowed it to that subclass. The semantic pass gives an override without a result annotation the overridden method's numeric result type, a redeclared field without an annotation the inherited field's, and `new` and `super(...)` arguments the nearest declared constructor's parameter types. PTS1001 for now: overrides with other parameter or result types (covariant results, fewer parameters), abstract fields, extending anything but a class of the program (`Error` arrives in M3.2), using an instance where a structurally equal but unrelated class is expected, `super(...)` inside a larger expression in a class with fields, and `instanceof` with anything but a class of the program on the right.
- **Reason:** Embedding keeps the layout prefix-compatible in standard C, so clang's type-based alias analysis stays correct (a flattened copy of the parent's fields would be a different struct type, which struct-path TBAA may assume doesn't alias). Typed method tables keep calls readable and free of function-pointer casts while costing what C++ vtables cost, and only hierarchies that override anything pay for them. Devirtualising by the whole-program class hierarchy makes the common case (no override below the static type) a direct, inlinable call. Running initialisers after `super()` returns and dispatching virtually from constructors match JS's order of effects.
- **Alternatives rejected:** Flattened subclass structs (alias-analysis hazards). An untyped `void (**)(void)` table in `pts_type` (casts at every call, and calls through mismatched function types unless the thunks are generated). A third load through a `vtable` pointer in `pts_type`. Dispatch by comparing type pointers (cost grows with the number of subclasses). Thunks per override to adapt `this` (an extra jump and more generated code). Making every method virtual (no inlining).

### D-030 · How accessors, abstract fields and parameter properties compile (M2.2d1)
- **Date:** 2026-10-11
- **Decision:** A getter or setter is an `ir.Method` of kind `Getter` or `Setter` (`ir.MethodKind`), with a function named `<Class>.get_<name>` / `<Class>.set_<name>`; overriding, slots and devirtualisation work as for methods (D-028), keyed by name and kind, and a slot's member in the method table is `pts_get_<name>` / `pts_set_<name>`, which can't collide with a method's. Reading an accessor property calls its getter; assigning calls its setter and has the stored value as its value (`o.p = v` evaluates `o`, then `v`, then calls the setter); a compound assignment or `++` calls the getter once, then the setter, with the instance evaluated once (`place` gains accessor properties: `current` and `stored` temporaries). `super.p` calls the parent's getter directly. An abstract field (`abstract name: T`) is an abstract getter and, unless `readonly`, an abstract setter; a subclass that declares the field implements them with generated accessors over its field (`implementAbstractAccessors`), or declares accessors itself; reads through a reference of the subclass's static type stay plain field reads. A parameter property is a field declared before the class's other fields, stored at the start of the constructor (in a subclass, right after `super(...)`, before the field initialisers), which is the property order Node shows. `private`, `protected` and `readonly` change nothing at run time: tsc enforces them, and `console.log` shows such fields, as Node does. The semantic pass types accessors like functions, gives an accessor property its getter's numeric type (or its setter's parameter type), and gives a parameter property its parameter's. `ir.Method.Abstract` replaces testing for a missing body, since bodies are lowered after calls may be. PTS1001: a getter and setter of different types or classes, reading a property that has only a setter, assigning through `super.p`, and auto-accessors (`accessor x`). A subclass that overrides only the getter of a get/set pair keeps the parent's setter, where JS would leave the property without one (and throw TypeError on assignment); tsc rejects that assignment through the subclass's own type.
- **Reason:** Accessors are methods with a calling convention, so reusing methods (and their tables) gives overriding and devirtualisation for free and keeps the C a plain call. An abstract field has no storage of its own (each subclass decides), so reading it through the base is necessarily a dispatch, which accessors already are. Storing parameter properties first matches Node's printed property order (it runs TypeScript through swc, which assigns them before the field initialisers).
- **Alternatives rejected:** Accessor properties as a separate IR concept with their own tables (duplicated dispatch logic). Storing abstract fields at a fixed offset in the base (subclasses may implement them with accessors, and their own fields come after the base's). Parameter properties stored where tsc's emit puts them (after the field initialisers), which Node doesn't do.

### D-031 · How statics and `#private` members compile (M2.2d2)
- **Date:** 2026-10-11
- **Decision:** A static field is a module-scope binding of its class's module (an `ir.Local` named `<Class>.<field>`, always `Global`, so a C global `pts_global_<Class>_<field>` with a ready flag), declared by a `LocalDecl` at the class declaration's place in the module's top-level code; static fields' initialisers and static blocks run there in declaration order. Reading one before the class declaration has run throws ReferenceError naming the class, as JS does for the class binding. A static method is a plain function `<Class>.<method>` without `this`. `C.f`, `m.C.f` and, in static code, `this.f` and `this.m()` name the declaring class's members statically; reads may go through a subclass (`Derived.count` reads `Base.count`). Two cases where JS would differ are PTS1001: assigning to an inherited static field through a subclass (JS gives the subclass a field of its own) and calling, through a subclass, a static method that uses `this` (JS's `this` would be the subclass). `this` as a value in static code is PTS1001 (classes as values come later). A `#private` member is a member whose name keeps its `#`: it never overrides or redeclares an inherited member (a subclass's `#x` is a field of its own, in its own part of the struct), its C names are `pts_private_<x>` for a field and `private_<x>` inside function and global names, and it is left out of the descriptor's field table, so `console.log` (and later JSON) don't show it, as in Node, while the GC layout still covers it. `#x in o` is `pts_instance_of(o, C)` for the class C that declares `#x`, since only instances of C and its subclasses have it. Static getters and setters are PTS1001.
- **Reason:** Reusing module-scope bindings gives statics their storage, their initialisation order and their TDZ check with no new machinery, and keeps every access a plain global load. Resolving static members statically is what makes them free; the two subclass cases are the only ones where the static answer and JS's dynamic one can differ, so they are errors rather than silent divergences. Keeping `#` in the name makes private members distinct from public ones of the same name and from a subclass's private ones without a separate namespace.
- **Alternatives rejected:** A per-class statics struct (one more indirection, and a second kind of global). Copying statics into subclasses (wrong after an assignment to the base). Dispatching static calls on a hidden class argument (cost on every static call for a rare pattern). Name-mangling `#x` to `x_` (collides with a public `x_`).

### D-033 · How object literals and exact object types compile (M2.3a)
- **Date:** 2026-10-11
- **Decision:** An object type of the program (an interface, type literal, alias of one, or an object literal's type; not a class, a function type, a type with index signatures or a type of the ES library) maps to a *shape*: an `ir.Class` with `Shape` set, one field per property in name order, and nothing else. Object types with the same properties of the same IR types share a shape (`shapeKey`), so `interface Point`, `{ x: number; y: number }` and the type of `{ y: 1, x: 2 }` are one C struct `pts_class_object<n>`; a recursive object type gets a shape of its own. Until M2.3b, a value of an object type is always an object of exactly its shape: a class instance or an object of another shape where one is expected is PTS1001. An object literal (`ir.NewObject`) allocates an object of its type's shape and stores each property's value in the literal's order. Because JS lists an object's properties in the order they were created, every distinct property order of a shape gets its own descriptor (`pts_type_object<n>`, `pts_type_object<n>_2`, …), sharing the struct and GC layout; descriptors of shapes are named "Object", which `inspect.c` prints as Node prints plain objects (`{ x: 1 }`, `{}`, `[Object]` beyond depth 2), as Node does for any constructor named Object. A property access whose member is declared in an object type of the program reads or writes the shape's field. The semantic pass types an interface or type literal property like a field, and a literal's number-typed property by the property of the literal's contextual type (`GetContextualType`), so `const p: Pixel = { r: 250 }` checks 250 against `u8`; without a context a property takes its value's type. PTS1001: optional properties (M3.1, D-032), methods and accessors in object types and literals (function values arrive in M2.5), spread (M2.6), computed property names, and property names that are array indices (JS orders those first).
- **Reason:** Shapes are D-L10's anonymous struct types, with the same fixed layouts, descriptors and printing as classes, so every property access is one load and no new runtime machinery is needed. Interning by structure is what makes structurally identical types interchangeable without conversions, which is how TypeScript treats them. Per-order descriptors keep Node's property order without giving up a canonical layout; the descriptor pointer every object already has costs nothing extra.
- **Alternatives rejected:** One shape per TypeScript type (identical types written twice wouldn't convert). Layout in each literal's order (two literals of one type would have different layouts). Hash-map objects (against D-L10). A flag in `pts_type` for plain objects (the name "Object" is exactly Node's own rule).

### D-035 · How interfaces over fields compile (M2.3b1)
- **Date:** 2026-10-11
- **Decision:** Every object type of the program (D-033's) is now an `ir.Interface` as the type of a binding, field, parameter or result: structural, interned by its properties' names and IR types, a one-word `pts_object *` in C. Shapes stay the concrete classes of object literals; a literal written where an object type with the same properties is expected takes that type's shape (`literalType`), so its values convert to the context's property types. A reference to an object of a class, a shape or another interface converts to an interface (`ir.ClassCast`, a pointer cast) when, for every property of the interface, the object has a field of the same name and the same IR type: then every access through the interface finds a field it can use as it is, and an assignment through it can't break what the object's own type promises. An interface value converts to a class where the checker narrowed it (`instanceof`). A property read or write through an interface finds the field's address with `pts_field_address(object, &site, "name")`, where `site` is a `static pts_site` at that place in the C: a one-word cache of the last descriptor met there and the field's offset in it (descriptor | offset << 48, read and written with relaxed atomics, so racing threads never see half an update); on a miss the runtime finds the field by name in the descriptor's field table. `===`, `?:`, `&&` and `||` meet a class and an interface it provides in the interface. PTS1001 until M2.3b2: a property that a class provides with a getter, interfaces with methods; and always for now, property types that differ in IR type (an `int` field where an interface says `number`).
- **Reason:** D-L10 asks for dispatch per (concrete type, interface) pair, built at compile time where possible and cached at run time otherwise. With one-word values (D-002) the table has to be found from the object at the place of use, and a per-site cache keyed by the descriptor is the fastest way to find it: one load and one compare on a hit, the same as an inline cache in a JS engine. Fields need no table beyond the descriptor's field list, which already exists; methods and accessors (M2.3b2) will add per-pair tables of functions. Requiring identical property types keeps every object's fixed layout honest under writes through any interface.
- **Alternatives rejected:** Fat pointers carrying a table (two words, against D-002, and lost on boxing). Exact shapes for annotated object types (a class instance could never be passed where the object type is expected). A global (descriptor, interface) hash table looked up on every access (slower than a per-site cache, and still a lookup on every call). Converting representations (an `int` field read as a `number`) at run time (every access would need the field's kind).

### D-036 · How methods and accessors through interfaces compile (M2.3b2)
- **Date:** 2026-10-11
- **Decision:** An `ir.Interface` now also has `Methods` (`ir.InterfaceMethod`: name, parameter and result IR types), from the method signatures of interfaces and type literals; accessor signatures (`get x(): T`, with or without `set`) declare properties like `x: T`. A class provides an interface's property with a field of the same IR type, or with a getter returning that type (and a setter taking it, if it has one); it provides a method with a method of the same name, parameter types and result type. `o.m(args)` on an interface value is `ir.InterfaceCall`. Each class's descriptor carries, in its `methods` table, the methods, getters and setters that interfaces may call (named like a method of some interface, or like an accessor-provided property of one), inherited ones included with the implementation the class has, each through an *entry point* `pts_entry_<function>` that takes `this` as `pts_object *` and calls the method with it as its class (so every call is through the function's own type). A call site through an interface is `((R (*)(pts_object *, P…))pts_method_find(o, &site, "m", PTS_METHOD))(o, args)`, where the site's one-word cache (D-035's `pts_site`) holds the last descriptor met there and the method's index in its table. A property of an interface that some class of the program provides with an accessor (`ir.Field.Accessor`, set by a whole-program pass over the classes' getters and setters) is read and written with `PTS_GET`/`PTS_SET`, whose site caches either the field's offset or, flagged, the accessor's index; every other interface property keeps D-035's field-only site. Reading such a property in a compound assignment or `++` reads it once (`current`), as JS does. Writing, through an interface, a property whose class has only a getter throws `TypeError: Cannot set property x of #<C> which has only a getter`, as in JS. Branches of `?:`, `&&` and `||` of unrelated classes convert to their contextual interface when both provide it. PTS1001: object literals with methods or accessors (function values arrive in M2.5), methods as values, setter-only properties in object types, overloaded and generic methods in object types, and members whose IR types differ from the interface's (as in D-035).
- **Reason:** D-L10 asks for per-(concrete type, interface) tables built at compile time and cached at run time. With one-word values (D-002) the table must be found from the object where it is used, so the compile-time part is each descriptor's member table (fixed per class, inherited members resolved), and the run-time part is the per-site cache: one load and one compare on a hit, then one indexed load, like an inline cache. Entry points keep calls type-correct in C without a function-pointer cast at every call, and clang turns them into a jump. Choosing the accessor-capable path only for property names some class has accessors for keeps plain field access through interfaces exactly as fast as in M2.3b1.
- **Alternatives rejected:** Tables per (class, interface) pair computed as a whole-program closure of conversions (fragile through interface-to-interface conversions and subclasses, and the site still has to find the pair's table from the object). Fat pointers (two words, against D-002). Calling methods through `pts_object *` without entry points (calls through mismatched function types). Making every interface property access a call (slower for the common field case). A branch on field-or-accessor at every interface property site (needless where no class has an accessor of that name).

### D-038 · How arrays compile (M2.4a)
- **Date:** 2026-10-11
- **Decision:** `T[]`, `Array<T>` and `readonly T[]` are `ir.Array{Elem}`, one per element IR type, a `pts_array *` in C: a header, a buffer pointer and a length. The buffer holds its capacity and the elements, each stored in its element type's C representation (doubles, `bool`, pointers, `pts_value`s), so numeric arrays are unboxed and their buffers are allocated atomic (never scanned); pointer buffers are scanned. Each element kind has one static descriptor in the runtime (`PTS_KIND_ARRAY`, its `element` field naming the kind), which `console.log` reads. Race safety (D-L13, brief §2.5): growing allocates a bigger buffer and publishes it (release) before the length that needs it; every access loads the length, then the buffer (acquire), and checks the index against both the length and that buffer's capacity; elements are copied with one store or load each. Racing pushes may lose elements, and may leave a slot below the length that no push wrote in the current buffer; buffers start zeroed, and a zero pointer or dynamic value there is a hole that reads as out of range (`PTS_ARRAY_GET_WORD`), so no NULL reaches typed code. `pop` and `shift` leave the old slot's value in place. Semantics: arrays have no holes. `a[i]` follows D-015: `ArrayElement` (a dynamic value, `undefined` out of range) where any value can go, `ArrayElementChecked` (`RangeError`) elsewhere; `a[i] = v` stores in range or appends at the length, and throws `RangeError` beyond; `a.length = n` may only shrink. `a.pop()` and `a.shift()` are dynamic values (`T | undefined`); under `!` they return the element and throw `RangeError` on an empty array. `for (const x of a)` is a loop over indices that reads the length before each iteration, as JS's array iterator does. `Array.isArray(x)` is decided by `x`'s static type. An array literal takes its contextual array type, so its elements convert to the context's element type; `never[]` (an empty literal without context) has dynamic-value elements. PTS1001: converting between array types of different element types (TypeScript's covariant arrays would let a write through `Point[]` put a non-`Pixel` into a `Pixel[]`), spread and holes in literals, tuples, the methods of M2.4b and M2.4c, `for...of` over anything but arrays, and arrays of the integer types and f32: the checker sees `u8[]` as `number[]`, so their element types need the semantic pass to track type nodes, which generics (M2.6) need too; M2.6 takes them on.
- **Reason:** Static element types (D-L06) make unboxed, typed storage the natural representation: no boxing per element, atomic buffers for numbers (brief §4), and one load per read. Keeping the capacity in the buffer, publishing buffers before lengths and bounds-checking against the buffer read is exactly brief §2.5's rule, and treating unwritten pointer slots as holes extends it to the slots a lost push leaves. JS's sparse arrays have no representation in fixed-type buffers, so creating holes is a runtime error rather than a silent zero.
- **Alternatives rejected:** Arrays of boxed `pts_value`s (an allocation per number, and every read a type test). A lock per array for pushes (correct, but a lock on the most common operation; the brief allows lost pushes). Capacity in the array header (a racing reader could pair a new capacity with an old buffer). Zero values for holes (silently wrong). Copying on conversion between element types (hidden O(n) work at assignments).

### D-039 · How the array methods without callbacks compile (M2.4b)
- **Date:** 2026-10-11
- **Decision:** Each method is an `ir.ArrayOp` (`slice`, `splice`, `concat`, `indexOf`, `lastIndexOf`, `includes`, `join`, `reverse`, `sort`, `flat`, `fill`) implemented once per element kind in `array.c`, with values of the element type passed by address (a C compound literal) and JS's index rules (negative from the end, ToIntegerOrInfinity; a left-out start is 0 and a left-out end Infinity, as for the String methods). `slice`, `splice`, `concat` and `flat` make new arrays; `splice` fills a new buffer before publishing it (as `unshift` does, D-038); `concat` copies the receiver and appends each argument: an array of the receiver's type spreads, anything else is one element. `indexOf`/`lastIndexOf` compare with `===` and `includes` with SameValueZero, per element kind (strings by content, objects by reference). An element's string (for `join`, `sort` and ToString of an array, which is `join(",")`) is its JS ToString: numbers by Number::toString, holes `""`, nested arrays joined, a class instance by its class's `toString()` if it has one taking nothing and returning a string (descriptors list it in their method table for this), other objects `"[object Object]"`; joining an array that is already being joined on the thread gives `""`, as in V8. `join` concatenates halves recursively, so copying is O(n log n) and `pts_string_concat` stays the one place that joins surrogate halves. `sort()` sorts stably by those strings in UTF-16 order (a merge sort over (key, element) pairs in scanned memory). `flat(depth)` needs a constant depth, which gives its result type; holes are skipped. `Array.from` takes an array (a copy) or a string (its code points). `split` takes a string separator (`""` splits into UTF-16 code units) and a limit (ToUint32). An empty literal `[]` converts to any array type, since tsc types a nested one `never[]`. PTS1001: `sort` with a comparator and `Array.from` with a mapper (M2.4c), a non-constant `flat` depth, and recursive array types (`type Nested = Nested[]`).
- **Reason:** One runtime implementation per operation, driven by the element kind in the descriptor, keeps the generated C to one call per method and puts JS's index and equality rules in one place. Tie-breaker 2: `toString()` on classes and the cycle rule are what Node prints.
- **Alternatives rejected:** Generating each method per element type in C (code bloat for every array type used). Joining by repeated concatenation (quadratic). Sorting numbers numerically (not what JS's default sort does). Computing `flat`'s result type at run time (the IR needs it statically).

### D-041 · How closures and function values compile (M2.5a)
- **Date:** 2026-10-11
- **Decision:** A checker type with exactly one call signature and nothing else is an `ir.FuncType` (parameters, result; one per signature), a `pts_closure *` in C: a heap object whose first word is its descriptor (`PTS_KIND_FUNCTION`, named with the function's JS `name`) and second the code pointer, followed by the captured values. Arrow functions, function expressions, function declarations inside functions or blocks, and adapters are *closure functions*: their C code takes the closure first (`pts_closure *pts_env`) and starts by copying the captures into C locals. A closure function records in `Captures` the locals of enclosing functions that it, or a closure it makes, uses (module-scope bindings stay globals and are never captured), and `Outer`, the function that makes it. A captured local is copied by value into each closure unless it may change after a closure captured it: if it is assigned after its declaration anywhere, or a closure may be made before its declaration has run (a hoisted function declaration, or a closure in its own initialiser), it is a `Cell`, a `T *` to a GC cell that the block declaring it allocates on entry, which closures hold instead. A for loop's `let` variables that are cells are copied into fresh cells before each update (`Loop.Bindings`), so each iteration has its own as in JS. Nested function declarations get their closure in a local at the start of their block (JS's hoisting), are called directly with it (`ir.Call.Closure`), and in their own body use `pts_env` for their name (`Self`). A function declared at a module's top level stays a plain C function; used as a value, it is one static closure whose code is a wrapper. An arrow or function expression that captures nothing is one static closure too. Calls of function values cast the code to the exact function type (`(R (*)(pts_closure *, P…))f->code`). An arrow function or function expression is lowered at its contextual function type's shape when that takes more parameters or returns nothing (extra unused parameters, results discarded); any other value of a function type converts to another by an *adapter*, a closure that captures it and converts arguments and result (parameter types by the usual conversions, more parameters, a discarded result); adapters print as the function they wrap. An arrow's `this` is its method's or constructor's `this`, captured like a variable; `super.m()` works in arrows. A variable a closure uses above its declaration gets its local early (`declareAhead`). `console.log` prints `[Function: name]` or `[Function (anonymous)]`, `typeof` is "function", `===` compares identity. PTS1001: function values whose signature has integer types or f32, and function types written with them (reported by the semantic pass, as arrays of them are, D-038): the checker sees them as `number`, so the semantic pass couldn't check calls through such values (M2.6); generic, async and generator functions, `this` parameters, overloaded, recursive, optional- and rest-parameter function types, converting functions to strings, `super(...)` in arrows, and methods as values (M2.5b).
- **Reason:** One word per function value (D-002) means a pointer to a closure, and a descriptor first lets `console.log`, `typeof` and the collector treat it like any object; the code pointer in the closure makes a call two loads and an indirect call. Copying immutable captures (the common case: parameters and `const`s) needs no allocation and keeps reads to one load; cells give exactly JS's sharing for the rest, including per-iteration `let` bindings, and allocating them on block entry makes hoisted functions work. Closure functions taking the closure as their first parameter keep every call type-correct in C, without casts to mismatched function types, which is why top-level functions get wrappers rather than a second calling convention. Shaping arrow literals to their context avoids an adapter on the most common path (callbacks with fewer parameters, such as `forEach(x => …)`). Tie-breaker 2 (behave like JS) decides NamedEvaluation names, hoisting and per-iteration bindings; static closures for capture-free functions trade JS's per-evaluation identity, which programs rarely compare, for no allocation (tie-breaker 3, performance, recorded in SPEC §8).
- **Alternatives rejected:** One environment object per scope shared by all its closures (V8's contexts; fewer allocations with many shared variables, but every captured read becomes an indirection, and per-iteration copies copy whole scopes). Fat function values (code pointer plus environment: two words, against D-002). Boxing every captured variable (an allocation per captured parameter). A uniform calling convention with an unused closure parameter for every function (changes every direct call). Adapters for arrow literals too (an allocation and an extra call per callback). Allowing integer types in function signatures now (calls through values would escape the semantic pass's conversion rules).

### D-042 · How the array methods with callbacks compile (M2.4c)
- **Date:** 2026-10-11
- **Decision:** `forEach`, `map`, `filter`, `flatMap`, `some`, `every`, `find`, `findIndex`, `findLast`, `findLastIndex`, `reduce` and `reduceRight` (with and without an initial value), and `Array.from(source, mapper)` (as `map` over the array, or over the string's code points) call a helper function the lowering generates once per method variant, array type and callback type: an IR loop that reads the length once, visits each index the array still has (from the end for the `Last` methods and `reduceRight`), and calls the callback, a function value, with as many of (element, index, array) as it takes, each converted to its parameter type; so a callback with fewer parameters, or with a supertype parameter, needs no adapter. A callback's result is tested with JS's ToBoolean where the method tests it. `map` returns an array of the callback's result type; `flatMap` appends the elements of a result that is an array, or the result itself; `find`/`findLast` return a dynamic value (the element or `undefined`), and under `!` the element, throwing `RangeError: find() found no element` if none matches; `reduce` without an initial value throws `TypeError: Reduce of empty array with no initial value` on an empty array (through `pts_throw_error`, an uncaught error until M3.2). `sort(compare)` converts the comparator to `(T, T) => number` (adapting it if needed) and sorts in the runtime with a stable merge sort, calling it through a generated function per element type that loads the elements as their C type; NaN counts as 0; holes left by racing pushes go last, as JS sorts `undefined`. A union of number literals (`-1 | 0 | 1`, which comparators often return) is `number`, and of string literals `string`. PTS1001: `thisArg` arguments, `map`, `flatMap` and `reduce` with a callback that returns nothing, and callbacks that take more parameters than the method passes.
- **Reason:** A helper per (method, types) keeps every call type-correct in C (one runtime implementation would have to call callbacks of every element and result type through one signature), shows the loop in readable C, and lets clang inline the helper and the callback where it can; generating it in IR reuses conversions, boxing and the evaluation-order handling. Calling the callback with only the parameters it takes is what JS does for callers that ignore extra arguments, without adapters. Sorting in the runtime reuses the stable merge sort of D-039; a generated loader per element type is the one type-specific part. Tie-breaker 2: reading the length once, skipping vanished indices, the error messages and stability are Node's; the `!` behaviour follows `pop()!` (D-038).
- **Alternatives rejected:** Runtime implementations per element kind with callbacks called through a generic signature (mismatched function types in C). Inlining each method's loop at its call site (code bloat for every call). An adapter to the full (element, index, array) signature for every callback (an allocation and an extra call per call site). Mapping `find` to the element type without `!` (it can be undefined; unions arrive in M3.1).

### D-044 · How methods in object literals, methods as values, `bind` and `call` compile (M2.5b1)
- **Date:** 2026-10-11
- **Decision:** A method of an object type gives the type's shape a field of its name (in name order, like properties) that holds the method's closure; its type is a function type whose first parameter is the shape (`this`), then the method's. A method in an object literal is a closure function (it may capture variables, like an arrow) whose first parameter is `this`, typed as the shape, so `this.x` is a direct field access; arrows in it capture that `this` (D-041). Shapes are interned by their properties and methods, as interfaces are (D-035). `o.m(…)` on a shape calls the closure in o's field with o; through an interface it goes through the descriptor's method table (D-036), whose entries for a shape's methods (`pts_entry_<shape>_<m>`, one per shape, shared by its per-order descriptors) load the closure from the object and call it with the object. `console.log` shows methods as `m: [Function: m]`, as Node does. A method used as a value (`o.m` not called) is a closure bound to `o`, which calls `o.m` with its arguments (virtual and interface dispatch included), named like the method; a static method used as a value is the plain function. `o.m.bind(x, a…)` makes such a closure bound to `x` with leading arguments fixed, named "bound m"; `o.m.call(x, a…)` calls the method on `x`. For a class's method `x` converts to `o`'s class and the method of `x`'s class runs; for a method of an object type `x` must be `o` itself, written the same way (`g.m.bind(g)`, `this.m.call(this)`), since JS runs `o`'s own closure, which may hold `o`'s captured state. On a function value, `f.call(x, a…)` evaluates `x` and calls `f(a…)`, and `f.bind(x, a…)` makes a closure (marked `Binds`) that captures `f` and the bound arguments and prints as "bound " and `f`'s name. A function type whose rest parameter is a tuple (what `bind` leaves) has the tuple's elements as parameters. PTS1001: accessors in object literals and `apply` (M2.5b2), generic, async and generator methods in literals, methods whose parameter types differ from their object type's, and `call`/`bind` on an object type's method with another object as `this`.
- **Reason:** Closures in fields are the only way a literal's methods can capture variables per object while objects of one shape share a layout and descriptors; typing `this` as the shape keeps field access in methods as fast as in classes, and the method-table entries make literals and classes interchangeable behind interfaces (D-036). Binding `o.m` to `o` is what makes every program that works in JS work the same here (a method that doesn't use `this` behaves identically bound or not), while JS's unbound semantics would need `this` to be undefined, which typed `this` can't be; tie-breakers 3 and 5. Restricting `call`/`bind` on an object type's method to its own object keeps the semantics exact without a way to call one object's closure on another.
- **Alternatives rejected:** Literal methods as methods of a class per literal (no captured variables). `this` typed as the interface (every field access in a method through a site cache). Rejecting methods as values (blocks callbacks like `arr.map(Maths.cube)` and `arr.forEach(obj.handle)` that work in JS). Unbound method values that throw when called (a compile-time `this` analysis or a runtime check for a case JS programs avoid). Dispatching `o.m.call(x)` on `x` for object types (wrong when `o` and `x` hold different closures).

### D-045 · How accessors in object literals and `apply` compile (M2.5b2)
- **Date:** 2026-10-11
- **Decision:** A getter or setter in an object literal is a closure (like a literal's method, D-044) that takes the object first; the literal's shape holds it in a field named `get p` or `set p` (C members `pts_get_p`, `pts_set_p`), and the accessor property p has no value field. A literal with accessors always has a shape of its own type (not its contextual type's), and shapes with accessors are interned apart from shapes that hold the same properties as values. The shape's descriptors list p once in their field table, where its getter or setter first appears in the literal, with a kind (`PTS_FIELD_GETTER`, `PTS_FIELD_SETTER`, `PTS_FIELD_GETTER_SETTER`) that `console.log` prints as Node does (`[Getter]`, `[Setter]`, `[Getter/Setter]`) and that field lookups skip; their method tables have `PTS_GETTER`/`PTS_SETTER` entries named p that call the closures. Interface properties named like a shape's accessor property are accessor-capable (D-036's `PTS_GET`/`PTS_SET`), so reads and writes through interfaces find the getter or setter; writing a getter-only property throws TypeError as for classes. Inside the literal's own methods, `this.p` for an accessor property goes through the interface of the literal's type. A shape provides an interface's property with its getter (and setter, if any), or a setter-only property with its setter. `f.apply(thisArg, [a, b])` is `f.call(thisArg, a, b)`. PTS1001: `apply` with arguments that aren't an array literal (other arrays need tuple types, M2.6).
- **Reason:** Per-object closures keep accessors able to capture variables, as methods do (D-044), and the method-table entries make a literal's accessor and a class's interchangeable behind interfaces (D-036) with no new access path. Listing accessor properties in the field table, under a kind lookups skip, gives Node's printing without a second table. Routing `this.p` through the interface reuses the accessor-capable sites, for a case rare enough not to need a faster path. With strictBindCallApply, `apply`'s arguments must be a tuple; an array literal is the only tuple-typed expression ParallelScript has before tuples.
- **Alternatives rejected:** Accessors as methods of a per-literal class (no captured variables). Calling getters when printing (Node doesn't). A separate table of accessor properties in `pts_type` for printing (one more field for every descriptor). Reading a setter-only property as `undefined` (it has no value representation in a typed field; reading one throws instead).

### D-046 · How Map and Set compile (M2.5c)
- **Date:** 2026-10-11
- **Decision:** The ES library's `Map<K, V>`, `Set<T>`, `ReadonlyMap` and `ReadonlySet` are `ir.MapType`s (one per key and value type), a `pts_map *` in C: an ordered hash table in the runtime (`map.c`), generic over key and value kinds like arrays (D-038), whose descriptors the generated C writes per type (`pts_type.key` is new, `element` holds the value kind). A table holds its entries in insertion order (key, value and hash, one word each), with deleted entries marked in place, and an open-addressing index twice the entries' capacity. Keys compare with SameValueZero: numbers by value with `NaN` equal to `NaN` and `-0` to `0`, strings by content, booleans and integers by value, objects, arrays and functions by identity, dynamic values by those rules. Growing (when the entries are full), compacting (when three quarters are deleted) and clearing publish a new table; the old one links to it, and an iteration follows the links, keeping its place by counting the live entries before it, so iteration is JS's: it sees entries added during it and skips entries deleted before it reaches them. Race safety (D-L13): tables are never resized in place, every read is bounded by the table it loaded and its published count, and each word is written with one store, so racing threads may lose updates but never read out of bounds. Operations: `new Map()`, `new Set()`, copies (`new Map(map)`, `new Set(set)`), `new Set(array)`; `get` (a dynamic value, `undefined` if absent; under `!` the value, throwing `RangeError: Map has no entry for the key` if absent, as `find(…)!` does, D-042), `set` and `add` (returning the map), `has`, `delete`, `clear`, `size`; `forEach` and `Array.from` (of a set, `keys()` or `values()`, with or without a mapper) through generated helpers like D-042's; `for…of` over a set, `keys()` and `values()` as a loop over a runtime iteration in a local. `console.log` prints `Map(2) { 'a' => 1 }`, `Set(1) { 1 }`, `[Map]` beyond depth 2 and `... n more items` past 100, as Node does. PTS1001 until M2.6 (tuples and destructuring): `entries()`, iterating a Map directly (its `[key, value]` pairs), `new Map(entries)` (except an empty literal), and iterators as values; and maps and sets of the integer types and f32, which the semantic pass reports as it does arrays of them (D-038).
- **Reason:** Insertion order is part of JS's semantics for both iteration and printing, and an entries array with an index (as V8's OrderedHashTable and CPython's dict) gives it with one allocation per table and cache-friendly iteration. Replacing tables rather than resizing them is the same rule that makes arrays race-safe (brief §2.5), and the link from old to new tables is what JS's live iteration needs anyway. Generating descriptors per map type, like classes', avoids a static table of every key and value kind pair. Reusing D-042's helper generation keeps callbacks type-correct in C.
- **Alternatives rejected:** A hash table without order plus a linked list of entries (two allocations per entry, pointer-chasing iteration). Resizing in place under a lock (a lock on every operation; brief §2.5 allows lost updates instead). Snapshotting a map for each iteration (not JS's semantics, and O(n) per loop). Boxing keys and values as dynamic values (an allocation per number, as D-038 rejected for arrays).

### D-048 · The integer types and f32 are number types of their own to the checker (M2.6a)
- **Date:** 2026-10-11
- **Decision:** The prelude still declares `int`, `i8 … u64` and `f32` as aliases of `number` (`i64` as an alias of `int`, `f64` of `number`), but the forked checker resolves each of those aliases to an intrinsic number type of its own, named as the alias (`internal/checker/pts.go`, `ptsNumericAliasType`). The types carry `number`'s flags, so tsc relates them to `number` and to each other exactly as it relates `number` to itself (every numeric type is assignable to every other, and identical under tsc's identity relation); the PTS semantic pass keeps enforcing the conversion rules. Because they are types, they survive in every type tsc builds: `u8[]`, `Map<string, int>`, `(n: int) => int`, inferred type arguments (`ints.map(…)`). tsc also types arithmetic by ParallelScript's rules (`ptsArithmeticType`, `ptsUnaryType`): `a * 2` with `a: u8` is a `u8`, `a + n` with `n: int` an `int`, `a * 1.5` a `number`, through `numeric.Operation`, the rule the semantic pass uses too (moved to the leaf package `pts/numeric` so that the checker can import it). The type printer writes them by name. The semantic pass reads numeric types from checker types (`check.NumericOf`; a union of numbers is their common type) instead of following annotations, gives a number-typed expression its contextual type's numeric type (array literal elements, arguments of built-in methods, element assignments) and checks the conversion, and reports a function value used where a function type passes it arguments its parameters can't take without loss, or expects a result its own doesn't convert to without loss (PTS2001), since the adapter the lowering makes (D-041) would convert them silently. The lowering maps the types to IR numeric types in `irType`, so arrays, maps, sets and function types of them need nothing else; `new Map()` (a `Map<any, any>` to tsc) takes its contextual Map type. A literal without a context is still a `number`, so `[byte, 1]` is a `number[]`.
- **Reason:** D-038 and D-046 deferred these types because the checker saw them as `number`; following type nodes in the semantic pass would have meant re-implementing tsc's inference for every generic signature in the ES library (`map`'s `U`, `reduce`'s `T`, `Map`'s `K` and `V`) and, for M2.6b, for users' generics too. With distinct types, tsc's own inference carries them, and monomorphization can key instantiations on checker types. Typing arithmetic in the checker keeps tsc's types and the semantic pass's in agreement, so that what an editor shows is what the program computes (`ints.map(x => x * 2)` is an `int[]`, as `const y = x * 2` is an `int`). The fork edits are small: one new file and four one-line calls in the checker, one in the type printer, all marked `// PTS:`, and none active unless ParallelScript's prelude is loaded.
- **Alternatives rejected:** Following type nodes in the semantic pass (the plan's sketch in D-038; it can't see through inference). Branded types such as `number & { __u8: never }` (tsc rejects `const x: u8 = 5`, D-012). Distinct types that tsc doesn't relate to `number` (every `Math` call and array index would need `as`). Leaving arithmetic `number` to tsc (the semantic pass would compute `u8` while tsc's inferred `map` results said `number[]`).

### D-049 · How generic functions and generic object types compile (M2.6b1); M2.6b split
- **Date:** 2026-10-11
- **Decision:** M2.6b becomes M2.6b1 (generic functions declared at module scope, generic interfaces and type aliases) and M2.6b2 (generic classes, generic methods, nested generic functions); no scope is dropped. Generic functions are monomorphized at the IR level: a generic function declaration has one instance per distinct list of IR types its calls pass as type arguments (tsc's inferred or written type arguments, taken from the resolved signature's mapper through a small export in `internal/checker/pts.go`). Each instance is an ordinary `ir.Func` named `<name>_<types>`, declared when a call first needs it and lowered after the other bodies; while an instance is declared or lowered, every checker type the lowering asks about is instantiated with the instance's type arguments (`PtsInstantiateType`), so the lowering's type-directed choices (arrays, maps, strings, classes, numeric types) see the concrete types, and a member access through a constraint (`x.name` with `T extends Named`) resolves against the instantiated type. Type arguments that lower to the same IR types share an instance. Generic interfaces and type aliases need no instances: tsc instantiates them, and the lowering maps the instantiated types like any other (a reference to a generic interface is an object type; its members are read from the instantiated type). The semantic pass stays generic-agnostic: a value of a type parameter is not a number to it, so arithmetic on such values is done in `number` (as tsc types it) and converted at the boundaries, and `x as T` converts by the numeric rules in an instance whose `T` is numeric. An instance's body is lowered once per instance, so diagnostics are deduplicated. More than 64 instances of one function (polymorphic recursion such as `f<T>` calling `f<T[]>`) is PTS1001; so are generic functions as values and generic functions nested in functions or blocks (M2.6b2).
- **Reason:** The brief locks monomorphization (D-L11). Keying instances on IR types rather than checker types gives each runtime representation exactly one copy of the code. Instantiating checker types, rather than substituting only in `irType`, keeps every existing type-directed decision of the lowering correct inside instances without touching each one. Deferring instance bodies to the end mirrors how function bodies already wait for every declaration (D-021), and lowering one instance at a time keeps the per-symbol maps (locals, nested functions) consistent. Doing arithmetic on type-parameter values in `number` needs no per-instance semantic pass and matches what tsc says the expressions are.
- **Alternatives rejected:** Boxing type-parameter values as dynamic values (one generic copy; slower, and contrary to D-L11). Keying instances on checker types (duplicate code for type arguments that lower alike). Re-running the semantic pass per instance (only arithmetic on unconstrained numeric type parameters would gain). Generic function values via dictionary passing (no monomorphization; can come later if programs need them).

### D-050 · How generic classes compile (M2.6b2); M2.6b2 split
- **Date:** 2026-10-11
- **Decision:** M2.6b2 becomes M2.6b2 (generic classes) and M2.6b3 (generic methods and nested generic functions); no scope is dropped. A generic class is monomorphized like a generic function (D-049): each distinct list of IR types it is instantiated with (from a type reference such as `Box<int>`, a `new` expression's type or a base type) makes an `ir.Class` of its own, named as the generic class so that `console.log` prints `Box { value: 1 }` for every instance (C names are made unique as before). Its superclass is the declaration's base type instantiated, so instances extend classes and generic classes (`class Labeled<T> extends Box<T>`), and non-generic classes extend instances (`class IntBox extends Box<int>`). Because the lowering keyed every class member by its declaration, each instance has its own member tables (`classMembers`), and a member lookup finds the right instance from the receiver's class (or, for `this`, the constraint of its type), walking up the superclasses; the other classes keep sharing one table set. Members are declared superclass first (`ensureMembers`), whenever the instance is made: with the other classes if before, at once if after. Constructors and methods are lowered per instance, with the class's type parameters substituted in every checker type. Static members of generic classes (shared by every instance in JS) and `instanceof` of a generic class (which would have to test every instance's class) are PTS1001 for now. Since instances are made while code is lowered, a call of a method that a generic class extending the receiver's class redeclares goes through the method table, as if an instance overriding it already existed.
- **Reason:** D-L11 locks monomorphization, and one class per instance gives unboxed fields of each instance's types, as D-038 does for arrays. Naming instances as the class matches what Node prints. Per-instance member tables keep the existing class lowering unchanged for every non-generic class while letting each instance's fields and methods differ in type.
- **Alternatives rejected:** One class with dynamic-value fields for every instance (boxing; not monomorphization). Keying member tables by (declaration, instance) everywhere (every lookup would need the instance, even for non-generic classes). Cloning the class's syntax per instance (the checker wouldn't know the clones).

### D-051 · Generic methods and nested generic functions (M2.6b3); generic function values move to M3.3
- **Date:** 2026-10-11
- **Decision:** A generic method of a class (an instance method, of a generic class's instance too, or a static method) is monomorphized like a generic function (D-049): its instances are keyed on the IR types of the call's type arguments, take the class instance's substitution plus the method's own, take `this` (instance methods), and are called directly, never through the method table; overriding with a generic method, or overriding a generic method, is PTS1001, as is a generic method used as a value. A generic function nested in a function or method (outside generic code) is monomorphized the same way; its instances are plain functions, so one that uses a variable of an enclosing function is PTS1001 (`using x from outside the function`). Generic functions nested in generic functions or in generic classes' methods, which would need two substitutions at once for their declarations, are PTS1001. Nested non-generic functions of a generic class's methods are declared again in each instance. Generic function *values* (a generic arrow function or function declaration used as a value) and generic methods of object literals and interfaces (which are values in shape fields and method tables) can't be monomorphized, since one value must serve every type argument; they move to M3.3, where dynamic values let one boxed copy serve every type argument.
- **Reason:** Methods are functions with a receiver, so D-049's machinery carries over with the receiver's class and substitution. Direct calls keep generic methods out of method tables, which need one entry per name. Moving generic function values to `any`'s task rather than dropping them keeps the scope while putting them where their representation exists.
- **Alternatives rejected:** Dictionary passing for generic values now (needs the dynamic value machinery of M3.3). Closures for nested generic instances that capture variables (an instance's closure would have to be made where its declaration's block is entered, before the calls that need it are known; rare enough to report).

### D-052 · How enums compile (M2.6c)
- **Date:** 2026-10-11
- **Decision:** Enums compile away. A member access (`E.m`, `E["m"]`, also through an import or a namespace import, for regular and `const` enums alike) is the constant tsc computes for the member; an enum type is the number or string type of its members (a numeric member is a `number`, so it converts to an integer type only with `as`, like any number); an enum declaration emits nothing. The one use of a regular numeric enum's object is the reverse mapping `E[n]`: it compares `n` with each numeric member's value, the last member first, so that the last member with the value wins as JS's assignments make it; where any value can go (D-015's contexts), a value no member has gives `undefined`, and where a `string` is required it throws `RangeError: <n> is not a value of the enum <E>`. PTS1001: members whose values tsc can't compute (`A = s.length`), and the enum object as a value (`console.log(E)`, `Object.keys(E)`), which waits for objects with numeric keys.
- **Reason:** tsc already computes every constant member's value (`GetConstantValue`), so no enum object is needed for member accesses, and constants keep `switch` and comparisons cheap. Following D-015 for the reverse mapping keeps one rule for reads that JS answers with `undefined`. Treating members as `number` rather than as untyped constants keeps tsc's types and the semantic pass in agreement (D-048).
- **Alternatives rejected:** Building the enum object at run time as a hash map (only printing and `Object.keys` would use it; can come with M3.5). Members as untyped constants that take an integer type from context (tsc types them as enum literals of `number`, so its arithmetic types would disagree with the pass).

### D-053 · How tuples compile (M2.6d1); M2.6d split
- **Date:** 2026-10-11
- **Decision:** M2.6d becomes M2.6d1 (tuples), M2.6d2 (destructuring and default parameter values) and M2.6d3 (Map entries as pairs, and `apply` with tuples); no scope is dropped. A tuple type of fixed length is a shape whose fields, named `0`, `1`, …, hold its elements unboxed, one shape per list of element IR types; its descriptor has the new kind `PTS_KIND_TUPLE`, which `console.log` prints as an array (`[ 'a', 1 ]`, grouped past six elements as Node groups arrays). An array literal makes a tuple where its own or its contextual type is a tuple, including `as const` and `as [T, U]`; `t[i]` needs a constant index, and reads or writes the element's field; `length` is a constant. Tuples are mutable objects compared by identity, as JS arrays are. PTS1001: optional and rest elements, a non-constant index, converting a tuple to an array type, array methods and `for…of` on tuples.
- **Reason:** A tuple's length and element types are fixed, so a struct with typed fields stores it unboxed with one load per element, unlike an array of dynamic values; reusing shapes reuses their layout, allocation and field access. Printing as an array is what Node does, since tuples are arrays at run time.
- **Alternatives rejected:** Tuples as arrays of dynamic values (boxing every number, and a type test on every read). A tuple type in the IR of its own (would duplicate the shapes' layout and allocation code).

### D-054 · How destructuring compiles (M2.6d2a); M2.6d2 split
- **Date:** 2026-10-11
- **Decision:** M2.6d2 becomes M2.6d2a (destructuring) and M2.6d2b (default parameter values, which need left-out arguments passed somehow); no scope is dropped. A pattern holds its value in a local and binds each name to a part of it, in order: an object pattern reads properties (a field of a class or shape, a class's getter, a field through an interface); an array pattern reads a tuple's fields or an array's elements, an array element through D-015's checked read (`RangeError` past the end, where JS gives `undefined`) unless the element has a default, which then applies when the array is too short; a default past a tuple's end always applies; a rest element is the array's `slice` from its index, or for a tuple a new array (or tuple) of the remaining elements. Defaults on object properties and on tuple elements never apply, since those parts can't be `undefined` until unions arrive (M3.1), so they are not lowered (tsc still checks them). The same parts serve declarations (module-scope names are declared ahead like other bindings), parameters (the argument arrives in a local the body starts by destructuring), `for…of` over arrays, and destructuring assignments (whose value is their right side). The value a pattern destructures is lowered with its own type, not the one tsc derives from the pattern (`{ x: any }`). PTS1001: rest properties in object patterns (M2.6e), computed property names, and destructuring a Map's or Set's items (M2.6d3).
- **Reason:** Binding each name from a local evaluates the value once and the parts in order, as JS does. Reading array elements with the checked read keeps D-015's rule for a typed name that JS would leave `undefined`; a default is exactly the case where JS's `undefined` is handled, so it replaces the check.
- **Alternatives rejected:** Copying the whole value per name (evaluates it more than once). Giving names `undefined` when an array is short (they are typed; D-015).

### D-055 · How default parameter values compile (M2.6d2b)
- **Date:** 2026-10-11
- **Decision:** A parameter with a default takes two parameters in the IR and in C: the argument (`x_arg`) and a flag of the new IR type `given` (a C `bool`, `x_given`) that says whether the call passed the argument, that is, neither left it out nor passed `undefined`. The function's body starts by declaring the parameter's local as `x_given ? x_arg : <default>`, in parameter order and before a pattern parameter is destructured, so a default runs in the function's scope, sees the parameters before it (and `this`, and the variables around the function, its module's private ones included) and runs only when needed, as in JS. A call passes `true` after each argument it gives such a parameter, and for an argument it leaves out, or an `undefined` (still evaluated), the type's zero value (`ir.LeftOut`) and `false`; so every caller fills in the flags: direct calls, `new`, `super(...)`, implicit constructors (which forward every parameter), virtual and interface calls, calls of function values, `call`, `bind` and `apply`, and builtins that call callbacks (a callback parameter with a default past the arguments the builtin passes is left out). Function types carry the flags too: each optional parameter of a signature (`x?: T`, a default, or past the minimum argument count) is its type without `undefined` followed by `given`, so `(x: number, y?: number) => number` is `(number, number, given) => number`, distinct from `(number, number, boolean) => number`; interface methods and overrides compare such lists as before. An arrow function shaped by a contextual function type that always passes an argument (`xs.map((x, i = 0) => …)`) drops that parameter's flag, since its default can't apply; otherwise a function value converts between function types through an adapter that passes `false` for parameters the other type doesn't pass and `true` for ones it always passes. A parameter with a default and no type annotation has the type tsc gives it in the body, without the `undefined` of an optional contextual parameter. The semantic pass checks a default against its parameter's numeric type (`function f(x: u8 = 300)` is PTS2002) and doesn't check an `undefined` argument. PTS1001 until unions (M3.1): an optional parameter without a default in a function with a body, and a default for a parameter whose type includes `undefined`; a function whose parameter is required where a type it converts to may leave the argument out (a method without a default providing an interface method's optional parameter, or overriding a method with a default).
- **Reason:** Functions take fixed parameter lists in C (D-020), so leaving an argument out has to be said explicitly. One flag per defaulted parameter keeps the C readable (`pts_fn_greet(name, greeting_arg, greeting_given)`), costs one register per such parameter, and needs no limit on the number of parameters; unlike a count of the arguments passed it also says when an argument in the middle is `undefined` (`f(undefined, 2)`), and with unions (M3.1) a caller computes it from a value that may be undefined. Evaluating defaults in the callee is the only way they see the callee's scope (earlier parameters, `this`, a module's private bindings) and run only when needed. Typing the flag as `given` rather than `boolean` keeps a function type with an optional parameter from being confused with one that takes a boolean. Binding the parameter's local in the prologue (rather than assigning the parameter) means a captured parameter that the body doesn't assign is still copied into closures rather than put in a cell (D-041).
- **Alternatives rejected:** The caller evaluating the default (wrong scope, and it can't for function values). A hidden count of the arguments passed (can't express `undefined` in the middle). A bitmask of passed parameters (less readable, limited to 64 parameters). A sentinel value in the argument (no spare value for integers and booleans). Assigning the default to the parameter itself (makes captured parameters cells).

### D-056 · Map and Set entries as pairs (M2.6d3); iterators as values move to M4.1
- **Date:** 2026-10-11
- **Decision:** A map's entries are tuples `[K, V]` (D-053's shapes, one per pair of IR types; a set's entries are `[T, T]`): iterating a map directly or its `entries()` yields a new pair per entry, in `for…of` (with a name or any pattern), `Array.from` (with or without a mapper) and `new Map(...)`. A pattern of one name per element over a pair made in place (`for (const [k, v] of map)`, and likewise `const [a, b] = [x, y]`) binds each name to the element's value without making the pair. `new Map(entries)` of an array of pairs sets each in order through a helper generated per map type (`Map.of`); an array literal argument is lowered as an array of the map's pairs (tsc types `[["a", true]]` by its elements, as a union of literal tuples). `new Map(m)` and `new Map(m.entries())` of a map of the same type copy it, as `new Set(set)` does. `f.apply(thisArg, t)` with a tuple `t` passes its elements, evaluated after `f` and `thisArg` as in JS. Iterators as values (`const it = m.keys()`, `it.next()`) move to M4.1: `next()` returns an `IteratorResult` union (M3.1), and M4.1 brings the iterator representation that generators share, so a map-only one now would be redone. Still PTS1001: a map or set of another collection's keys or values (`new Set(m.keys())`).
- **Reason:** Tuples are fixed layouts of unboxed elements, so a pair costs one small allocation where JS allocates an array per entry too, and the common destructuring loop costs none. Generating `new Map(entries)` in IR keeps the runtime free of tuple layouts, as D-046's helpers do. Tie-breaker 5 for the iterators: simple and working now, one design later.
- **Alternatives rejected:** A runtime entry iterator returning boxed pairs (dynamic values and an allocation per element read). Escape analysis to remove pair allocations generally (the in-place pattern case covers the common loop). Map iterators as heap objects now (a second iterator design before M4.1's).

### D-057 · Rest parameters and spread arguments (M2.6e1); M2.6e split
- **Date:** 2026-10-11
- **Decision:** M2.6e becomes M2.6e1 (rest parameters and spread arguments), M2.6e2 (spread in array and object literals, rest properties in object patterns) and M2.6e3 (`Record<string, T>` and index signatures as hash maps, with `delete`); no scope is dropped. A rest parameter `...xs: T[]` is one parameter of the new IR type `Rest` (`...T[]`, a `pts_array *` in C) holding the array of the arguments from its position on, which the caller makes; the function's body starts by binding `xs` to it (`RestArgs`). Function types and interface methods carry `Rest` in their parameter lists, so `(...xs: number[]) => number` differs from `(xs: number[]) => number`. A call packs the arguments for the rest parameter into a new array; a spread argument `...a` of an array passes its elements there (the array is built with `concat`), and a spread of a tuple (a literal, or a variable read once per element) passes its elements to any parameters; `console.log(...a)` prints an array's elements as arguments (`pts_console_log_spread`). Adapters pack fixed parameters into a rest array, or take a fixed parameter from a rest array with D-015's checked read (`RangeError` where JS gives `undefined` for a missing argument); builtins calling a callback with a rest parameter pass it the arguments left. The semantic pass already types rest arguments by their contextual element type, so `total(300)` with `...xs: u8[]` is PTS2002. PTS1001: rest parameters of tuple types, spreading a tuple that isn't a literal or a variable, spreading sets and strings into arguments, spreads in `call`, `apply` and `bind` and in other builtins' arguments, `bind` arguments that reach a rest parameter, and adapting a rest parameter list to optional parameters.
- **Reason:** One array argument keeps calls fixed-arity in C (D-020) and is what JS's rest parameter is anyway; the caller knows the argument count, so it builds the array with one allocation. A type of its own for the rest parameter follows D-055's `given`: whatever compares parameter lists (overrides, interfaces, adapters, function types) tells `...T[]` from `T[]` without extra bookkeeping.
- **Alternatives rejected:** C varargs (no type safety and no GC precision). A count and a pointer into the caller's stack (the callee may keep the array). Marking rest-ness on the function or local instead of in the type (every comparison of parameter lists would need to consult it).

### D-058 · Spread in literals and rest properties (M2.6e2)
- **Date:** 2026-10-11
- **Decision:** An array literal with spreads is a new array built with `concat` of its elements and, in place of each spread, an array of the literal's type, a tuple's elements (a literal's, or a variable's), a string's code points (`Array.from`) or a map's or set's items (D-056's helpers); spreading an array of another element type is PTS1001. A tuple literal takes a spread tuple's elements. `a.push(...xs)` and `a.unshift(...xs)` build such an array of the values and add its elements at once (`pts_array_push_all`, `pts_array_unshift_all`), so the values are evaluated before any is added, as in JS. An object literal with spreads makes an object of its type's shape whose properties come in JS's order: each spread copies, at its place, a class instance's fields in the order its constructors make them (not its getters or methods, as JS copies own properties only), or an object type's properties in the order its type lists them; a property written later replaces an earlier value in its place. Values are evaluated in the literal's order: impure values and spread objects go into locals first, and a spread's property reads do too when something impure follows them. A rest element of an object pattern (`const { a, ...others } = o`) is a new object of its type's shape with o's other properties, in the order tsc keeps from o's type. `f.call(thisArg, ...xs)` spreads as other calls do. PTS1001: methods and accessors beside a spread in an object literal, rest properties holding methods, spreading tuples and other non-objects into objects, and spreads in `apply`, `bind` and other builtins' arguments.
- **Reason:** Building one array with `concat` evaluates the spreads in order with one allocation per array; a shape for the result follows D-033, since tsc gives the literal a fixed type. Copying a class instance's fields in layout order is exactly JS's own-property order; for objects of an object type the static order is the best one known at compile time (documented in SPEC §8).
- **Alternatives rejected:** Copying properties in the order of the source object's runtime descriptor (needs a result descriptor per source order, chosen at run time). Evaluating every value into a local (correct but clutters the C for the common `{ ...o, x: 1 }`).

### D-059 · How hash-map objects compile (M2.6e3)
- **Date:** 2026-10-11
- **Decision:** An object type with string or number index signatures (`Record<string, T>`, `Record<number, T>`, `{ [key: string]: T }`, `Readonly<…>` of them, the type tsc gives `{ [k]: v }`) whose properties, if any, are required properties of the index signatures' value type is a *hash-map object*: `ir.MapType` with `Record` set, keys `string` and values of one IR type, a `pts_map *` in C over D-046's ordered hash table, with a descriptor of the new kind `PTS_KIND_RECORD` named "Object". Number keys are converted to strings with JS's ToString where they are used (`o[1]` is `o["1"]`). `o[k]` and `o.k` read an entry: where any value can go (printing, concatenation, template literals, conditions, `typeof`) a missing key gives undefined (`MapGet`), elsewhere it throws `RangeError: Object has no property 'k'` (`PTS_RECORD_GET`), as D-015 does for strings. The idioms that test for a missing key keep JS's meaning exactly: `o[k] ?? d` and `o[k] || d` (with the new `MapGetInto`, the fallback evaluated only when needed), `o[k] ??= v` and `o[k] ||= v`, `o[k] === undefined` (and `!==`, `==`, `!=`), `k in o`, `o.hasOwnProperty(k)`, `Object.hasOwn(o, k)`. Writes and compound assignments set entries (`MapPut`, whose value is the value written); `delete o[k]` deletes one and is true. Object literals whose contextual or own type is a hash-map object build one entry by entry in the literal's order (computed and numeric keys, shorthands, spreads of hash-map objects of the same type with the new `MapAssign`, and spreads of objects through D-058's property order). JS lists an object's keys with array indices first, in numeric order, then in insertion order: `pts_record_iterate` iterates in insertion order when there are no array-index keys and otherwise over a sorted snapshot, and `console.log`, `Object.keys`/`values`/`entries` (helpers like D-056's) and `for…in` all use it; `for (const k in o)` loops over the keys o has when it starts, skipping the ones deleted meanwhile, as V8 does. `console.log` prints them as Node prints plain objects (keys quoted unless identifiers, all entries). The semantic pass types a literal's values by the index signature's value type, so `{ a: 300 }` for `Record<string, u8>` is PTS2002. Function values in literals take constant computed and numeric keys as their names. `delete` of anything else is PTS1002 (D-L10: fixed layouts; arrays have no holes). PTS1001: index signatures with other key types (template literal patterns, symbols), types mixing an index signature with methods, optional properties or properties of other types, recursive hash-map object types, methods and accessors in their literals, using an object of another type as a hash-map object (tsc's implicit index signatures; the message suggests `{ ...o }`), `for…in` over other objects or without a declaration, `Object.keys`/`values`/`entries` of other objects (M3.5), and the other methods of `Object.prototype`.
- **Reason:** D-L10 locks index-signature types as hash maps. D-046's table already keeps insertion order, compares strings by value and is race-safe, so one representation serves both; a kind of its own tells `console.log` and the key-order rule apart. Sorting only when array-index keys are present keeps the common case (word counts, caches) as fast as a Map, and snapshotting is what `Object.keys` and printing need anyway. The missing-key idioms are rewritten into lookups that know whether the key was there, so the commonest TypeScript patterns (`counts[w] = (counts[w] || 0) + 1`, `(groups[k] ??= []).push(x)`) run as in Node instead of throwing; elsewhere a missing key has no value of the entry's type, and a RangeError (as for strings, arrays and `Map.get(k)!`) beats silently inventing one (§3 tie-breaker 3).
- **Alternatives rejected:** Boxing values as dynamic values (an allocation per number and a type test per read, as D-038 rejected for arrays). Keeping keys in JS order on insertion (an O(n) insert for every array-index key). A zero value for a missing key (silently wrong). Copying objects into hash-map objects on conversion (would break aliasing: writes through one wouldn't show through the other). Naming functions from computed keys at run time (closures' names are static, D-041; documented in SPEC §8).

### D-060 · M2.7 split; binary-trees and nbody as written; Math basics; the collector's heap growth (M2.7a)
- **Date:** 2026-10-11
- **Decision:** M2.7 becomes M2.7a (binary-trees and nbody, with the Math basics nbody needs) and M2.7b (the string-building benchmark, with whatever makes `s += x` in a loop run in linear time: today each concatenation copies both strings, so building a string piece by piece is quadratic); no scope is dropped. binary-trees (depth 18) is the Benchmarks Game's algorithm, except that a leaf's children are the leaf itself where the usual version has null, since null arrives with unions (M3.1); the Go twin does the same. nbody (5,000,000 steps) prints its energies unrounded (`toFixed` is M3.5), and its `Body` fields start at 0, since `x: number;` without an initializer makes V8 box every number stored in the field (6× slower in Node); the Go twin computes its constants at run time, since Go folds constant expressions exactly where JS rounds each step. Math's `sqrt`, `abs`, `floor`, `ceil`, `round`, `trunc`, `sign`, `max` and `min` (any number of arguments) and its eight constants move forward from M3.5, with JS's semantics (Math.round rounds halves up and keeps -0; max and min propagate NaN and order -0 below +0). The collector runs once the program has allocated as much as the heap holds (bdwgc's free-space divisor 1, overridable with `GC_FREE_SPACE_DIVISOR`), as Go's default GOGC=100 does, instead of bdwgc's default of three times as often. Programs and the runtime compile with `-fno-math-errno`.
- **Reason:** The session protocol's rule for tasks too big for one session; making string building linear is runtime work of its own. Benchmarks must run the same source in every language (D-023) without tripping a known pathology of one of them, or the numbers say nothing (D-O15). The divisor halved binary-trees' time (2.9 s → 2.1 s at depth 18) for 127 MB instead of 85 MB of memory, still half of Node's 264 MB; Go's default makes the same trade. Nothing reads errno, so letting clang inline the math builtins costs nothing.
- **Alternatives rejected:** binary-trees with two classes (Leaf and Node; Go's empty leaves would allocate nothing, which isn't the same work). Waiting for M3.1 to add binary-trees (the milestone wants its GC numbers). bdwgc's defaults (three times the collections for a third less memory). Fewer marker threads (the gain was within the noise of this shared machine).

### D-061 · Strings point at their bytes; concatenation appends in place when it can (M2.7b)
- **Date:** 2026-10-11
- **Decision:** `pts_string` holds a `char *bytes` instead of inline bytes. A string made by `pts_string_alloc` keeps its bytes right after its header (pointer-free, allocated atomic, NUL-terminated); a literal's point at static storage. A concatenation of at least 64 bytes goes to an *append buffer* (`pts_string_buffer`: capacity, claimed length `used`, data) with room for as much again, and its header (allocated scanned, since `bytes` keeps the buffer alive through an interior pointer) is flagged `PTS_STRING_BUFFERED`. Concatenating onto a buffered string whose length equals the buffer's `used` claims the next bytes with a compare-and-swap of `used` and copies only the right side; every other case (the string doesn't end the buffer, the buffer is full, surrogate halves join) copies into a new string or buffer as before. All strings of a buffer are prefixes of its claimed bytes, which never change, so strings stay immutable and racing threads can only lose the race and copy (D-L13). Nothing may rely on a string's bytes being NUL-terminated (`pts_throw_error` and `inspect.c`'s quote choice no longer do). The string-building benchmark (`pts/bench/string_building`) appends a million pieces with `+=`, template literals and `join`; its Go twin uses a `strings.Builder`, Go's way to build a string (Go's `+=` copies).
- **Reason:** Building a string piece by piece is one of the commonest things programs do, and copying both sides every time made it quadratic: 50,000 appends took 3.3 s against Node's 0.1 s; now 0.014 s. A pointer to the bytes lets several strings share one buffer without changing any code that reads `->bytes`, and the claim-by-CAS rule is the one Go's `append` applies to slices, made safe for sharing by only ever extending.
- **Alternatives rejected:** Ropes flattened on first read (every reader of `->bytes` would need a flattening call, and flattening in place under races needs its own protocol). A compiler rewrite of `s += x` in loops into a builder (only catches the loops it can see, and aliasing makes it subtle). Over-allocating inline bytes (the new string needs a header of its own, so inline bytes can't be shared).

### D-062 · M3.1 split; how union values compile (M3.1a)
- **Date:** 2026-10-11
- **Decision:** M3.1 becomes M3.1a (union values: their representation, null and undefined, narrowing by the checker, equality, `typeof`, truthiness, `??`, `||`/`&&`, `!`, `instanceof`), M3.1b (optional properties and parameters, optional chaining `?.`, defaults of parameters whose type includes undefined) and M3.1c (unions of object types: reading properties and calling methods their members share, discriminants, `in`, and `==` with JS's conversions); no scope is dropped. A union of checker types whose members map to more than one IR type is `ir.Union` (its member IR types, interned as a set), a `pts_value` in C (D-002): numbers, f32 and the integer types up to 32 bits as numbers, i64 and u64 as numbers while a double holds them exactly and boxed beyond, booleans, null and undefined as constants, and every reference as its pointer; unions of literals of one type (`"a" | "b"`, `1 | 2`, `boolean`) stay that type, and a union of two numeric types is PTS1001. `ToUnion` converts a member (or a smaller union) to a union, a C no-op for references and constants and a box for numbers; `FromUnion` converts a union to the type the checker narrowed it to, a C no-op for unions and a cast or unbox for members. Narrowing is tsc's: wherever a variable, property or element of a union type is read (`expression` for identifiers, property and element accesses; `x += 1` and `x++` too), the lowering compares tsc's type at that place with the union and converts to it if it is narrower, so `if (x !== null) x + 1` adds numbers. `x === null`/`undefined` and `!==` compare words; `==`/`!=` against null or undefined test both; `===` between unions (or a union and a member) is `pts_value_strict_equals` with JS's rules for numbers and strings; comparisons with null of a value tsc narrowed to a non-nullable type are constants. `typeof` and truthiness use the dynamic value's tag. `x ?? y` and `x || y`, `x && y` keep x in a temporary, test it, and convert the branch taken to the type tsc gives the expression (`name || "anonymous"` is a string). `x!` on a union throws `TypeError: Non-null assertion on null` (or undefined), as SPEC §3.5 asks. `instanceof` on a union tests that it is an object first. `x as U` to a wider union is a free upcast. A class field of a union type declared without a value starts undefined, as in JS. The semantic pass types a number in a union context by the union's numeric type (`NumericContext`): `let b: u8 | null = 300` is PTS2002, and so are such arguments, assignments, returns and literal properties; a union variable narrowed to its numeric member has that type. Hash-map objects whose values may be null or undefined compare `o[k] === undefined` and apply `??` by value, not just by key. PTS1001 until M3.1b/c: reading properties of a union (`s.kind`, `either.length`), `==` between a union and anything but null or undefined, and the M3.1b features.
- **Reason:** One-word dynamic values were chosen (D-002) so that unions and `any` could share them; a pointer stays a pointer in them, so unions of references cost nothing to make or narrow, and numbers need no allocation. Relying on tsc's flow analysis for narrowing ("the checker reasons, the backend emits tag tests", D-L11) means every narrowing form tsc knows (typeof, equality, truthiness, instanceof, type guards, assignments) works without the lowering re-implementing any of them; the backend only converts where tsc's type at a reference is narrower than the variable's. A checked `!` is the spec's.
- **Alternatives rejected:** Tagged two-word unions (`{tag, payload}`; torn under races, against D-L13). Mapping every union to `ir.Value` (the lowering would lose which members a value can hold, which conversions and the equality fast paths need). Re-deriving narrowing in the lowering (would have to follow tsc's flow analysis exactly). Boxing small integers (an allocation per `u8 | null` value).

### D-063 · M3.1b split; optional parameters and `??=` (M3.1b1)
- **Date:** 2026-10-11
- **Decision:** M3.1b becomes M3.1b1 (optional parameters without a default, defaults of parameters whose type includes undefined, `??=`), M3.1b2 (optional chaining `?.` on properties, calls and elements) and M3.1b3 (optional properties); no scope is dropped. An optional parameter `x?: T` of a function with a body keeps D-055's calling convention, the value as a `T` and a `given` flag, so function types, interfaces and adapters see no difference; its local is `T | undefined`, bound at the start of the body to `given ? x_arg : undefined`. A parameter with a default whose type includes undefined takes `T | undefined` and its flag, and its local is `T`: `x = given && x_arg !== undefined ? x_arg : default`, since JS applies a default for an undefined argument. A caller passing a value of `T | undefined` to an optional parameter of type `T` passes `undefined` as left out: the flag is `x !== undefined` and the value its `T` (the value must be a variable or constant, read twice; a computed one is PTS1001). An adapter from a function whose parameter is `T | undefined` to a function type whose parameter is optional passes `given ? arg : undefined` (`(a, b) => …` written for `(a: number, b?: string) => …`). `x ??= v` on a union place is `x == null ? (x = v) : x`, reading x once; on a place that is never null or undefined it is x, and v isn't evaluated.
- **Reason:** The session protocol's rule for tasks too big for one session. Keeping D-055's convention means no call site, function type or interface changes: only the callee's prologue knows the parameter is optional, as D-055 intended for when unions arrived.
- **Alternatives rejected:** Passing `T | undefined` as one dynamic value for optional parameters (every function type with optional parameters would change representation, and numbers would be boxed at every call). Evaluating a computed argument into a temporary hoisted before the call (changes evaluation order relative to earlier arguments).

### D-064 · How optional chaining compiles (M3.1b2)
- **Date:** 2026-10-11
- **Decision:** An optional chain is lowered from its outermost node (tsc's `IsOutermostOptionalChain`, so `a?.b.c?.d` is two chains, the inner one the outer one's object): the object of the chain's outermost `?.` link is evaluated once into a temporary; if it is null or undefined (`IsNullish`) the chain is undefined and nothing after the `?.` runs; otherwise the rest of the chain is lowered with that object node standing for the temporary as its non-nullable type (`chainObjects`, which `expression` and `typeAt` consult), so every property, method, call and element form lowers as without `?.`. The result is converted to tsc's type for the chain (`T | undefined`); a call of a method that returns nothing makes the chain undefined either way. The rest is lowered where any value can go, so `a?.[9]` out of range is undefined. An object that is never null or undefined makes `?.` a `.`. Dynamic values (`a.find(…)`'s) can be chain objects and convert to unions as they are. `x!` drops null and undefined from tsc's type, which inside a chain still carries the chain's undefined. Object literals take their contextual type without null and undefined (`{ … }` written for `Point | null` makes a Point).
- **Reason:** Short-circuiting the whole rest of the chain is JS's semantics, and substituting the tested object lets every existing lowering of property accesses, calls and element accesses serve chains unchanged, rather than a parallel implementation per form.
- **Alternatives rejected:** Lowering each `?.` link separately with a test per link (wrong: `a?.b.c` must not read `.c` of undefined when a is null, and would test again at each link). Rewriting the AST (the checker's types belong to the original nodes).

### D-065 · M3.1b3 split; how optional properties compile (M3.1b3a)
- **Date:** 2026-10-11
- **Decision:** M3.1b3 becomes M3.1b3a (optional properties of object types and classes, literals that leave them out, reads, writes, `in`, destructuring defaults, spreads, mapped types) and M3.1b3b (objects that lack an optional property of the object type they convert to, or hold it as `T` instead of `T | undefined`); no scope is dropped. An optional property `p?: T` of an interface, type literal or mapped type (`Partial<T>`, `Pick`, `Omit`, `Readonly`, `Record<"a" | "b", T>`, which now count as object types) is a field of type `T | undefined` marked `Optional`, so a shape for `{ p?: T }` differs from one for `{ p: T | undefined }`. An object that leaves the property out holds the absent value in it, `PTS_VALUE_ABSENT` (zero, which no other `pts_value` is, and which a new object's fields already hold): every read of an optional field (`FieldRef`) turns it into undefined (`pts_value_present`), `console.log` skips the field, and `"p" in o` (`HasField`) tests for it. A literal written for an object type takes that type's shape when it gives every required property and only properties the type declares; the optional properties it leaves out come after its own in the shape's order, in the order the type declares them, so a property assigned later prints after the literal's properties in declaration order (JS: in assignment order). A spread copies an optional field as it is (`Raw`) into an optional field of the same type, so the copy leaves out what the object leaves out; spread over an earlier value of the property (`{ ...defaults, ...o }`), an absent property keeps the earlier value, and where the result's field can't hold undefined (tsc types `{ a: 1, ...o }`'s a as a number), an undefined one does too. Rest properties copy as spreads do. A default in an object pattern (declarations, parameters, assignments) applies when the property is undefined or absent. Only an optional property provides an optional property of an interface (tsc allows nothing else). Class fields declared `x?: T` (and optional parameter properties) are `T | undefined` fields that JS defines as undefined, so they are never absent and print `x: undefined`. `"p" in o` with a constant key of a property o's static type declares is true unless the property is optional; other keys wait for M3.1c. `delete o.p` stays PTS1002 (D-L10). The semantic pass types a read of a property of a union type by the union's numeric member, as it does for variables.
- **Reason:** A sentinel in the field keeps the layout fixed (D-L10) and the value one word (D-L13), costs one compare per read of an optional field and nothing elsewhere, and needs no runtime support beyond printing; zero makes left-out properties free in fresh objects and matches the arrays' holes. Treating mapped types as object types is what makes `Partial<T>`, the commonest source of optional properties, work.
- **Alternatives rejected:** Storing undefined (prints `p: undefined` and makes `in` true, where Node prints nothing and says false). A bit set per object of the properties present (another word per object, and racing writers could tear it from the values). Making absent a distinct value that every union operation understands (every comparison, `typeof`, truthiness and conversion would need a case).

### D-066 · Objects without an optional property (M3.1b3b)
- **Date:** 2026-10-11
- **Decision:** A value converts to an object type with an optional property `p?: T` (property type U = T | undefined) when its objects provide p as U (D-065), lack any member named p, or hold p in a field of type T, where T is U's one member besides undefined and isn't a union; every other member must be provided as before. Such a relaxed conversion (`objectCast`, the conversion of assignments, arguments and returns; `?:` meets stay exact) is recorded, and once the program is lowered `checkRelaxedCasts` checks every class and shape whose objects the converted values may refer to (the class and its subclasses, a shape, or for an interface, recursively, the types of every value the program converts to it, found by walking the IR's casts): each must provide or hold every property of the target that way, or the conversion is PTS1001. So at run time an object reached through the interface holds p as U, as T, behind a getter and setter of type U, or not at all. Reads, writes and `in` of an optional property through an interface go through `pts_optional_get`, `pts_optional_set` and `pts_optional_has`: a site caches a U field's offset or an accessor's index as property sites do; the slow path converts a T field by its descriptor kind (`pts_value_of_slot`, `pts_store_value_in_slot`) and reads a missing property as absent. Writing undefined to a T field throws `TypeError: Cannot set property p of C to undefined: the object's type doesn't allow it`, and writing a missing property throws `TypeError: Cannot add property p, object is not extensible`, since objects have fixed layouts (D-L10).
- **Reason:** Passing `{ name }` where `{ name: string; verbose?: boolean }` is expected, or a class that lacks an optional property, is everyday TypeScript, and tie-breaker 3 prefers a runtime check that throws to a compile error. The whole-program check keeps sites from ever reading a field as a type it doesn't hold, which a subclass adding the property with another type (or an object hidden behind a narrower interface) would otherwise allow (tie-breaker 1).
- **Alternatives rejected:** Copying the object into the target's shape at the conversion (breaks identity and shared mutation). Checking each field's type at run time (descriptors don't record a field's static type beyond its kind, and object-typed fields can't be checked structurally). Allowing T to be a union (a `string | null` field and a `string | null | undefined` one are both pts_values, so writes of undefined couldn't be refused).

### D-067 · Unions of objects, `in` and `==` (M3.1c)
- **Date:** 2026-10-11
- **Decision:** A property read of a union of object types (classes, shapes and interfaces; `shape.kind` for `Circle | Square`) goes through an interface made for the access, holding just that property with the type tsc gives it (interned like any interface): the union's value is unboxed to it (`FromUnion`, a pointer cast) and read through an interface site. Each member must provide the property as that type, or hold it in a field whose values are all of that type (then the field is `Mixed`, read by the field's kind through D-066's `pts_optional_get`, and writing it is PTS1001); an optional property may also be missing from a member. A method call (`pet.speak()`) goes through an interface with just that method (`InterfaceCall`); every member must provide it with tsc's one signature. A method of a union used as a value, and a member of a union of objects and other values (`string | string[]`'s `length`), stay PTS1001. Narrowing comes from tsc (discriminants, `in`, type guards); narrowing a union to a class is checked (`pts_value_as_instance`: TypeError if the object isn't an instance), since `in` and type guards can be wrong at run time and a class's fields are read at fixed offsets. A union of objects converts to a class all its members extend, or to an interface they all provide. An object literal written for a union of object types takes the one member it fits (the same property rule as D-065 and tsc's assignability), and a value with several object members to choose from takes the one interface member it provides. `c ? new Dog() : new Bird()` whose context is a union or nothing is the union tsc types it as, not their common class. `"p" in o` for a union, or for an object type that doesn't declare p, is looked up at run time in the object's descriptor (`HasKey`, `pts_object_has`, which D-066's `pts_optional_has` becomes: fields that aren't absent, and methods, getters and setters, which the descriptors' method tables list for the keys `in` tests, `Program.InKeys`; `#private` names never match). `==` and `!=` with a union operand are JS's IsLooselyEqual (`pts_value_loose_equals`): null equals undefined only, booleans compare as numbers, strings convert as `Number(s)` does (`pts_string_to_number`, JS's StringToNumber), and an object compared with a primitive converts to its string (an array's join, its class's `toString()`, else "[object Object]"). An array, string or hash-map element read where the context expects a union with undefined (`return list[i]` for a `T | undefined` result) gives undefined out of range, as where any value can go (D-015).
- **Reason:** An interface per access reuses D-035/D-036's sites and method tables, so a union of any object types costs one site lookup and needs no runtime type switch; building it per property keeps members the program never reads from failing the union. The instance check keeps a wrong narrowing from reading memory that isn't there (tie-breaker 1); it costs one compare when the narrowing is right. `==` follows the ECMAScript algorithm, minus `valueOf`, which ParallelScript's objects don't have.
- **Alternatives rejected:** One interface per union with all its common members (fails on members the program doesn't use, and needs every member representable). A runtime switch on the object's class at each read (code per member, and interfaces have no class to switch on). Leaving narrowing to classes unchecked (a lying type guard or a subclass that adds the tested key would read fields at wrong offsets).

### D-068 · M3.2 split; how exceptions compile (M3.2a)
- **Date:** 2026-10-11
- **Decision:** M3.2 becomes M3.2a (throw, try, catch, finally, Error and its native subclasses with message, name, cause and toString, classes extending them, the runtime's errors as catchable Error objects, the catch binding as `unknown`, uncaught exceptions) and M3.2b (`stack` with `.pts` frames and `console.log` of errors with them, the stack-overflow guard); no scope is dropped. **Mechanism:** each `try` pushes a handler on a thread-local chain (`pts_handlers`): a `pts_handler` holding a `jmp_buf`, in the C frame of the function that runs the try; `pts_throw(value)` pops the innermost handler, stores the exception in it and `_longjmp`s there; with no handler the exception is uncaught: stderr gets `Uncaught ` and the error's stack (its `Name: message` until M3.2b) or, for another value, the value as console.log shows it nested (`Uncaught 'text'`), and the process exits with 1 (D-O07). Calls cost nothing; entering a try costs a `_setjmp`. A break, continue or return that leaves a try block pops its handler (`pts_try_leave`; cgen knows how many tries each label is inside); a return computes its value before popping, so a throw while computing it lands in the try. Locals that a try block assigns and that are declared outside it are `volatile` in C (C11 7.13.2.1); cells and globals are in memory anyway. **IR:** `ir.Try` (Body, Exception, a Value local of its own, and Catch) and `ir.Throw` (a Value). `finally` is lowered, not emitted: the statement keeps a completion local (normal, throw, return, or one code per jump target), the protected code (the try, or the try and catch) runs inside a catch-all `ir.Try` inside a labelled block, and a return or jump that leaves it records itself (and the returned value) and breaks out of the block; after the finally block, a dispatch rethrows, returns or jumps, lowered outside the statement so that it routes through enclosing finally blocks in turn; a finally block that returns, breaks or throws discards what was pending, as in JS. **Errors:** Error, TypeError, RangeError, ReferenceError, SyntaxError, EvalError and URIError are `ir.Class`es marked Builtin, registered under the lib's global symbols, so `new`, `extends`, `instanceof`, `super(...)` and the checker's types of them all reach them as classes; the runtime defines their layout (`pts_error`: name, message, cause, and the stack in a member named as the compiler names a `#stack` field), their descriptors (`pts_type_builtin_<Name>`, kind object, methods `toString` and a `stack` getter and setter), the C types `pts_class_builtin_<Name>` and their constructor (`pts_error_init`, the lib's `(message?, options?)` with Given flags; the cause is looked up in the options object by name, absent if it has none). Their constructor and methods are `ir.Func`s with an `Extern` runtime function and no body; a native subclass is laid out as Error (cgen's paths skip it). `name` is a field set to the nearest native class's name (JS: the prototype's), so `this.name = "X"` and `name = "X"` fields work; `message` is "" when left out; `cause` is an optional field (`"cause" in e`); `stack` is formatted from the name and message when first read, as V8 does; `toString` is Error.prototype.toString. A class derived from Error may declare `toString` (not linked as an override: Error's methods stay non-virtual, and `o.toString()` of an object whose class declares none, `${o}` and `String(o)` convert through the descriptor's toString, else "[object Object]"); overriding the stack is PTS1001. The runtime's TypeError, RangeError and ReferenceError (integer division by zero, D-015's and D-038's checked reads, checked `!` and narrowing, missing map entries, `repeat`, ReferenceError before a binding is ready) are thrown with `pts_throw_new`; running out of memory and internal errors stay fatal (`pts_panic`). console.log of an error ports Node's formatError (the stack, improved with the class's name, in brackets without frames, the derived classes' fields, `name` if the stack doesn't show it, `[cause]`). **unknown:** `unknown` is `ir.Value`; the catch binding is one (`catch (e: any)` and destructuring are PTS1001 until M3.3). Reading a Value where tsc narrowed it to a class, a primitive or a union of them converts with a check (a class as D-067's narrowing, a string, number or boolean with `pts_value_as_string`, `pts_value_to_number_checked`, `pts_value_as_bool`: TypeError if wrong); `x as T` from unknown to such a T is the same checked conversion (to an integer type, a checked number, then `as`'s rules); other narrowings leave the value dynamic. `===`, `==`, `instanceof`, `typeof`, truthiness, templates and `String(x)` work on it. **never:** a function returning never returns nothing (Void); a call of one where a value is needed is the call, then the type's zero value, which never materializes; a never parameter is a Value.
- **Reason:** setjmp/longjmp keeps calls free, which the benchmarks (fib) care about, and it needs nothing from the C compiler that C doesn't define; a handler chain per thread is what a multi-loop runtime (M5) needs. Lowering finally to tries and jumps keeps cgen to one new construct and makes the IR's control flow explicit, and routing the dispatch through the outer context gets nested finally blocks right without special cases. Owning the Error classes in the runtime lets runtime errors be ordinary Error objects that `instanceof RangeError` sees, with one layout for both; making them classes of the program's IR reuses `new`, `extends`, field access and narrowing unchanged. Checking narrowings of an unknown keeps a lying type guard from reading memory as the wrong type (tie-breaker 1).
- **Alternatives rejected:** Checking a pending-exception flag after every call (a cost on every call). C++-style unwinding tables from C (needs `-fexceptions` and personality routines; far more machinery). Emitting finally blocks once per exit in cgen (duplicates code per jump and makes nested finally blocks a special case). Error classes written in a PTS prelude module (the runtime couldn't make its own errors without hooks into generated code). A `name` read from the class (JS lets a program assign it, and both the constructor and field idioms are common).

### D-069 · Stack traces and the stack guard (M3.2b)
- **Date:** 2026-10-11
- **Decision:** **Frames:** an error records where it was made: `pts_error_init` captures up to 24 return addresses with libbacktrace's `backtrace_simple` (libgcc's unwinder) into a pointer-free GC block (`pts_private_frames`, a `#frames` field to the compiler so derived classes lay it out); the first read of `stack` symbolizes them with `backtrace_pcinfo`, which reads the program's own DWARF (programs are already compiled with `-g`, and the generated C's `#line` directives make the line tables point at the `.pts` source), and appends at most 10 frames (V8's `Error.stackTraceLimit`) as `\n    at name (file:line)`, or `\n    at file:line` for top-level code and anonymous functions. Only frames in the program's source count: frames whose file ends in `.c` or `.h` (the runtime, inlined runtime headers, the generated `main`) and frames without line information (libc) are left out, and so are the leading frames of constructors of classes derived from Error, as V8 leaves them out. JS names come from a table the generated C registers at startup (`pts_register_function_names`, sorted C name → JS name): functions by their own names, methods as `Class.method`, constructors as `new Class`, static methods and builtin helpers (`Array.forEach`) by their full names; functions without one are left out of the table. libbacktrace (BSD) is vendored as a submodule pinned to commit 0b9b49c (it has no release tags) and built by the toolchain like the other libraries, with its configure's output for x86-64 Linux checked in as `pts/third_party/libbacktrace-config`; programs link libgcc statically (`-static-libgcc`) so the unwinder adds no `libgcc_s` dependency. **Guard:** each thread has a stack limit (`pts_stack_limit`, thread-local, 256 KB above the bottom of its stack, from `pthread_getattr_np`; 0 means none), and every generated function that may recurse (it calls functions, function values or methods, makes instances, accesses properties through interfaces, or calls the runtime with values whose toString may run) except a module's top-level code starts with `pts_stack_check()`. On x86-64 that is two instructions, `cmp %fs:pts_stack_limit@tpoff, %rsp; jb pts_stack_overflow_stub`, so the function needs no frame for it and a leaf path keeps its shape (fib's base case still returns before its prologue); the stub, a few lines of assembly, aligns the stack and calls `pts_throw_stack_overflow`, which throws `RangeError: Maximum call stack size exceeded`. Elsewhere it compares `__builtin_frame_address(0)`. The stub has no unwind information, so the error made there has no frames.
- **Reason:** Node's errors have stacks and programs print them; the DWARF the compiler already emits holds exactly the mapping to `.pts` lines that the `#line` directives exist for, and libbacktrace reads it without any table of our own. Capturing addresses is cheap (an error-heavy loop runs at Node's speed) and symbolizing only on first read keeps errors used for control flow cheap. A check per call is what V8 and Go do; done as a compare and jump with no call on the function's own path, it costs fib about 5% (205 → 217 ms at best on a noisy machine) where a C-level check with a call in its slow path cost 12–20% by taking away shrink-wrapping.
- **Alternatives rejected:** A shadow stack of positions kept by generated code (a cost on every call and statement). Tables of our own mapping code to source lines (the DWARF line table is that table). glibc's `backtrace()` (loads `libgcc_s` at run time). Frame-pointer walking (needs frame pointers everywhere, a register's cost, and can't cross libc safely). A SIGSEGV handler on an alternate stack (throwing from a signal handler is only safe if the fault was in generated code, and the handler can't allocate the error there). A check at each call site (still forces callee-saved registers; measured 9%).

### D-070 · M3.3 split; how `any` values compile (M3.3a)
- **Date:** 2026-10-11
- **Decision:** M3.3 becomes M3.3a (`any` values: dynamic reads and writes, operators, checked conversions to primitives, integer types, classes and unions of them), M3.3b (runtime descriptors of the program's other types, for checked conversions from `any`/`unknown` to interfaces, arrays, tuples, maps, records and functions, and checked writes of objects through `any`), M3.3c (calls of functions and methods through `any`) and M3.3d (generic function values, moved from M2.6b3); no scope is dropped. **Representation:** `any` is `ir.Value`, as `unknown` is (D-068); a union with an `any` or `unknown` member is a Value. **Reads and writes:** `o.p` and `o[k]` on an any are `DynamicGet(o, key)` (`pts_dynamic_get`): a field by name through the descriptor (an absent optional one reads as undefined), a getter (method-table entries now carry the kind a getter returns or a setter takes, `pts_method.result`, and every class's getters and setters are in its table), an array's or tuple's `length` and elements (numbers and canonical numeric strings index; out of range is undefined), a string's `length` and characters, a hash-map object's entries, a map's or set's `size`; a missing property is undefined; null and undefined throw V8's `TypeError: Cannot read properties of null (reading 'p')`; reading a method as a value is a TypeError until M3.3c. Writes (`DynamicSet`, `pts_dynamic_set`, also compound assignments, `++` and `--` through a dynamic place) check the value against the slot's kind (a number for a number field, an integer it holds exactly for an integer field, a string, a boolean; anything for an `any` field) and throw TypeError otherwise; a property the object lacks throws `Cannot add property p, object is not extensible` (D-L10); writing an object-typed field throws until M3.3b, since a kind doesn't say which objects the field may hold. `"p" in o` on an any is `pts_dynamic_has`. Destructuring an any reads each property dynamically, defaults included. **Operators:** with an `any` operand, `+` is `ValueAdd` (JS's ToPrimitive, then concatenation if either side is a string, else numbers) unless tsc types the result as a string; `- * / % **`, the bitwise and shift operators and unary `- + ~` convert with JS's ToNumber (`pts_value_to_number`) and then compute on numbers; `< <= > >=` follow JS's IsLessThan (`ValueLess`, `ValueLessEqual`; > and >= swap the operands after evaluating them in order); `===`, `==`, `??`, `||`, `&&`, `typeof`, truthiness, templates and `String(x)` work as for unknown. Objects have no valueOf, so ToPrimitive of an object is its string. **Boundaries:** converting a Value to a primitive, an integer type, a class or a union of them is checked wherever it happens (cgen's `fromValue`/`valueTest`; unions with a Value member test each member): TypeError `Expected T, got U`, where U is typeof or the object's class; an integer type takes only an integer it holds exactly (`pts_value_is_integer_of`). Converting an any to any other type is PTS1001 until M3.3b; Values from trusted places (`find`'s results) still convert to unions of other types unchecked. The semantic pass lets an `any` convert to every numeric type. `catch (e: any)`, `x as any`, `x as unknown` work. Calls through any are PTS1001 until M3.3c.
- **Reason:** The session rule for tasks too big for one session; M3.3b needs a runtime description of structural types, a design of its own. Reads, operators and checked boundaries to the types a descriptor or a tag can check are what `catch (e: any)`, loosely typed helpers and parsed data mostly need, and they keep the race-safety and memory-safety invariant: a dynamic value never reaches a typed place it doesn't fit (tie-breaker 1), and writes into typed objects are checked by the slot's kind. Following JS's conversions for operators keeps plain TypeScript printing what Node prints (tie-breaker 2).
- **Alternatives rejected:** Unchecked boundaries (an any holding a string read as a number field would be memory-unsafe). Copying values into typed objects at boundaries (breaks identity). Rejecting operators on any at compile time (tsc allows them, and they are common in loosely typed code).

### D-071 · M3.3b split; converting dynamic values to object types (M3.3b1)
- **Date:** 2026-10-11
- **Decision:** M3.3b becomes M3.3b1 (runtime descriptions of types and checked conversions of `any`/`unknown` to interfaces, shapes, tuples, arrays, hash-map objects, maps and sets, also by `as`) and M3.3b2 (writes of objects through `any`, checked by fields' declared types; interface sites that check kinds); no scope is dropped; function types and object types with methods wait for M3.3c's signatures. **Descriptions:** cgen writes a static `pts_check` (kind, slot kind, name for messages, descriptor, element check, properties as (name, check, optional, offset in the copy), union members) for each type a Value is converted to that cgen's `valueTest` can't test, and for the types inside it; checks may refer to each other (recursive types). **Conversion:** `pts_value_convert(value, check)` returns the value itself if it already is one in the target's representation: an object whose fields hold every property with the kind the target's sites read (an object or dynamic field's current value fitting the property's type, recursively; an optional property may be missing, absent, or held without undefined as D-066 allows; a getter of a primitive kind), an array whose element kind is the element type's and whose elements fit, a hash-map object of the target's descriptor whose values fit, a map or set of the target's descriptor. So a typed object that went through `any` keeps its identity. Otherwise it copies dynamic data into the target's representation, converting each part: an object or hash-map object into a new object of the interface's copy shape (the lowering gives each interface reachable from a conversion the shape of its object type, `Interface.Copy`, with an order in declaration order, so console.log prints copies of data in that order; keys the type doesn't declare are dropped), an array into a new array of the element kind, a hash-map object or an object's fields into a new hash-map object, an array of the right length into a tuple. A missing required property or a part that fits nothing throws `TypeError: Expected T, got U`. A union takes the first member the value fits as it is, else the first it converts to. Meeting an (object, check) pair again during the walk is a cycle: it fits as it is, but a cycle that would have to be copied doesn't (JSON has none).
- **Reason:** An `any[]` holds pts_values where a `number[]` holds doubles (and a `u8[]` bytes), so dynamic data can't be viewed in place as typed data without making every typed array and field access check its representation; converting at the boundary, as Rust's serde or Go's `json.Unmarshal` into structs do, keeps typed code as fast and as safe as before and gives M3.4's `JSON.parse` results their declared types. Keeping typed objects as they are when they fit keeps JS's identity semantics for the common case of typed values passed through `any`.
- **Alternatives rejected:** Viewing dynamic data in place through checked interface sites (arrays still need copies, and every read of such a type would pay for conversions). Copying every value converted from `any` (breaks identity for typed objects). A deep structural comparison of declared types at run time (left for M3.3b2, which needs fields' declared types anyway).

### D-072 · M3.3b2 split; declared types and checked writes through `any` (M3.3b2a)
- **Date:** 2026-10-11
- **Decision:** M3.3b2 becomes M3.3b2a (descriptors carrying declared types, checked writes of objects and unions through `any`, conversions that keep an object only when its declared types make it one of the target) and M3.3b2b (interface sites that guard what conversions accept: checked writes through a view into a narrower field, checked reads of optional properties an object's declared type leaves out); no scope is dropped. **Declared types:** in a program that converts dynamic values to types `valueTest` can't test or writes through `any` (`emitter.declaredTypes`), every field entry of a class's or shape's descriptor (`pts_field.check`), every getter and setter in a method table (`pts_method.check`) and the descriptor of every hash-map object type (`pts_type.check`) carry the `pts_check` of their declared type, and arrays whose element kind doesn't tell their element type (objects and unions, but not `any[]`) get a descriptor of the program's per array type (`pts_type_array_N`, with `.check`), which array literals and `flat` use; slices, splices and copies keep their source's descriptor. Other programs emit what they did before, but every array is made from a descriptor (`pts_array_of(type, …)`; the runtime's are `pts_array_types[kind]`). A NULL check stands for the type its kind holds (`pts_check_declared`: any for a pts_value, an unknown object type for an object). Function types and object types with methods have opaque checks (`PTS_CHECK_OPAQUE`): no dynamic value converts to them until M3.3c, and only a place declared with the same type implies them. **Writes:** `pts_dynamic_set` stores into a field, setter, array element or hash-map value of an object or union kind the value converted to the place's declared type (`storable`, `pts_value_try_convert`): a typed object as it is, dynamic data copied into an object type's copy shape, anything else `TypeError: Cannot set property p of C: expected T, got U` (an object by its class's name, a function as `function`). A union-typed place no longer takes any value (it did since M3.3a, which wasn't memory-safe), and an `any` place still does. In a program that writes through `any`, the lowering gives every interface that a class's or shape's field, an array or a hash-map object of the program is declared with a copy shape where it can (`prepareWrittenTypes`). **Conversions:** an object is one of an object type as it is when the declared types of its descriptor's fields and getters imply the type's properties (`object_fits`, `implies`): a place implies a property when it holds the property's representation (or, for an optional property, a primitive or object field of its type without undefined, D-066) and every value of its declared type is one of the property's type: the same type, any, a union each of whose members is implied, a member of a union, an integer type for number, a subclass for a class, and for an object type, a class or object type whose own properties imply each property, where an optional property the type leaves out is implied (its objects may lack it; M3.3b2b checks it where it is read); recursive types are implied coinductively. Arrays, tuples, maps, sets and hash-map objects are as they are only if their descriptors declare the target's own element types (writes through either type go to the same storage); otherwise they are copied. Values are no longer walked to decide this, and a cycle met while copying fails instead of fitting. So a `child: Animal` field that holds a Dog no longer passes as `{ child: Dog }` (the object is copied), while an object literal of `any` with a nested literal keeps its identity as an interface its declared types imply.
- **Reason:** The session rule for tasks too big for one session. Deciding by declared types rather than current values is what makes a kept object stay valid: its own type can only ever write values of its fields' declared types (tie-breaker 1), and it keeps JS's identity for typed objects that go through `any` wherever the types allow (tie-breaker 2). Describing arrays per type only where the kind doesn't tell the type, and only in programs that need it, keeps every other program's code and data as they were.
- **Alternatives rejected:** Exact type equality for kept objects (a nested literal of `any` would always be copied, unlike Node). Checking the current values (D-071's rule: a later write through the object's own wider type breaks the view). Per-type descriptors for every array (all programs pay for checks they never use). Checking every write through every interface site (a cost on statically safe code; M3.3b2b checks only pairs that conversions made).

### D-073 · Guarded interface sites (M3.3b2b)
- **Date:** 2026-10-11
- **Decision:** In a program whose descriptors carry declared types (D-072), every place that reads or writes a property through an interface passes the `pts_check` of the property's type to the runtime (`pts_field_address`, `PTS_GET`, `PTS_SET`, `pts_optional_get`, `pts_optional_set`, and for writes to plain fields `PTS_FIELD_SET`, which replaces the store through `pts_field_address`); other programs pass NULL and emit the same stores as before. The checks happen only when a site meets a new descriptor (its cache misses), so a hit costs what it did. **Reads** of a field or getter throw TypeError if it holds another kind than the site reads (`Cannot read property p of C as T: it is declared U`), which only a compiler bug could cause; an optional property's read site (and a union member's, D-067) also requires the field's or getter's declared type to imply the property's type (`pts_check_implies`), since an object type that leaves an optional property out implies it (D-072) and an object stored there later may declare it as anything; the pair is cached when it does. **Writes** cache a (descriptor, site) pair only when the field's or setter's declared type is the property's type (`pts_check_same`); otherwise the slow path converts the value to the declared type (`pts_storable`, as writes through `any` do: `Cannot set property p of C: expected T, got U`) and stores it or calls the setter (`pts_call_setter`) itself, uncached, so every write through such a view is checked. A write to a field holding an optional property as T without undefined (D-066) is checked against T the same way. So an object kept through `any` as a view of a wider type (a `Box { item: Dog }` used as `{ item: Animal }`) can't be given a value its own type doesn't allow.
- **Reason:** D-072 keeps typed objects through `any` when their declared types imply the target's, which is right for reading but lets a view write values its object's own type doesn't hold; checking at the site's slow path costs nothing on the paths statically typed code takes (exact pairs are cached as before) and keeps the memory-safety invariant for the pairs conversions make (tie-breaker 1). The kind check on reads makes a broken invariant a TypeError instead of a misread word.
- **Alternatives rejected:** Exact declared types for kept objects (loses identity for nested literals of `any`, D-072). Checking every write through an interface (a cost on statically exact pairs). Marking objects that went through `any` (a header bit per object; a racing write could still go through a cached site).

### D-074 · M3.3c split; how calls through `any` compile (M3.3c1)
- **Date:** 2026-10-11
- **Decision:** M3.3c becomes M3.3c1 (calling function values and the methods of the program's classes and object literals through `any`), M3.3c2 (converting `any` to function types and to object types with methods, methods read through `any` as values, spread arguments) and M3.3c3 (the builtin methods of strings, arrays, maps, sets and numbers called on dynamic values); no scope is dropped. **Lowering:** a call whose callee tsc types as any is `DynamicCall(callee, text, args…)`, and one whose callee is a property or element of a value typed any is `DynamicCallMethod(object, key, text, args…)`; the arguments are boxed, and `text` is the callee's source text, for V8's message `TypeError: text is not a function`. Spread arguments stay PTS1001 (M3.3c2). **Dynamic entries:** in a program that makes such calls (`emitter.dynamicCalls`, which also makes descriptors carry declared types, D-072), every function made a value of has a dynamic entry `pts_dynamic_<f>(pts_closure *self, uint32_t argc, const pts_value *argv)` in its closures' descriptor (`pts_type.call`), and every method in a method table has one (`pts_method.dynamic`): for a class's method it calls the method's entry point, for an object literal's method the closure its field holds, with the object; method tables then list every method of every class but `#private` ones. An entry converts each argument as a conversion from `any` does (`fromValue`: TypeError `Expected T, got U` if it doesn't fit; dynamic data copied into an object type), takes a missing argument as undefined, gives a parameter with a Given flag (D-055: a default or `?`) when its argument is there and isn't undefined, collects the rest into a rest parameter's array, ignores extra arguments, and returns the result boxed (undefined for none). The runtime's Error classes' `toString` has one. `pts_dynamic_call` calls a closure's entry and throws for anything else; `pts_dynamic_call_method` throws V8's `Cannot read properties of null (reading 'm')` for null and undefined, calls the method of an object's descriptor by name, or else calls the function a field or getter of that name holds (without `this`), and throws `TypeError: Calling the method m of a T through \`any\` is not supported yet` for strings, arrays and other builtin objects until M3.3c3. In a program that calls through `any`, the lowering gives every interface among the parameter types of its functions a copy shape (`prepareDynamicTypes`). Function-typed parameters are opaque until M3.3c2, so passing a function to one through `any` throws.
- **Reason:** The session rule for tasks too big for one session. A per-function entry that takes an argument vector is what a call site that knows nothing about its callee needs, and it keeps typed calls exactly as they were: only programs that call through `any` get entries, and typed code never goes through them. Converting at the entry keeps the invariant that a function's parameters hold values of their types (tie-breaker 1), with the same checks as any other boundary from `any`.
- **Alternatives rejected:** libffi-style calls built from a signature at run time (a dependency, and still needs the signature in the descriptor). One entry per function type rather than per function (a function's Given flags and rest parameter aren't in its type, and entries would need the closure's code cast anyway). Passing `this` to functions held in fields (only methods take it in ParallelScript's representation; an arrow ignores it).

### D-075 · Function types and object types with methods from `any` (M3.3c2)
- **Date:** 2026-10-11
- **Decision:** **Signatures:** cgen keeps one function type per list of parameter and result types, by their identities (`canonicalFuncType`; the lowering's function types don't cover methods), and its check (`PTS_CHECK_FUNCTION`) is the signature that closures' descriptors (`pts_type.signature`, the type of their code: their function's parameters, Given flags and rest parameter included, and result) and method table entries (`pts_method.signature`, after `this`) point to. Since signatures, dynamic entries (D-074) and declared types (D-072) serve the same conversions, a program has all three as soon as it converts a dynamic value to a type `valueTest` can't test, or writes or calls through `any` (`emitter.declaredTypes`; D-074's separate flag is gone). **Functions:** converting a dynamic value to a function type keeps a closure whose signature is the type's, and wraps any other closure in an adapter of the type (`pts_adapter`, made by the check's `adapt`; cgen writes the code, descriptor and maker per function type with a check): its code boxes the arguments (one whose Given flag is false as undefined, a rest array's elements spread), calls the wrapped closure through its dynamic entry (`pts_dynamic_call_closure`) and converts the result to the type's with a check; its own dynamic entry forwards (`pts_adapter_call`); console.log shows the wrapped function. Anything but a closure throws `Expected T, got U`. So a callback of another type works as JS would, with its arguments and result checked when it is called, and an adapter isn't `===` to what it wraps. Implication between function types is identity. **Object types with methods:** their checks list their methods with signatures (`pts_check.methods`); an object is one as it is when its method table has each method with the same signature (interfaces call methods through their exact types, D-036) and its declared types imply the properties (D-072), and implication between object types requires the same; such types are never copied into (dynamic data has no methods), so the lowering gives them no copy shape. Function-valued properties don't provide methods, as statically (a known issue). **Methods read through `any`:** a closure bound to the object (as typed code binds methods read as values, D-044), whose descriptor is made per method table entry on first use and kept (named as the method; its dynamic entry calls the method's), with no code and no signature, so typed code gets it only through an adapter; each read makes a new closure (JS: the same function). **Spread arguments** in calls through `any`: `SpreadArg`s whose arrays (or tuples) the runtime spreads into the argument vector (`pts_dynamic_call_spread`, `pts_dynamic_call_method_spread`).
- **Reason:** Callbacks are the commonest function values that pass through `any` (handlers in maps, JSON-driven dispatch), and adapting through the dynamic entry makes any closure usable as any function type with the same checks as every other boundary from `any` (tie-breaker 1), keeping the closure itself where the types already agree (tie-breaker 2). Signatures by identity rather than by name can't confuse two types that print the same.
- **Alternatives rejected:** Comparing signature strings (two classes of the same name in different modules print alike). Rejecting closures of other types (`(x: any) => …` written for an `any` context would never convert to a typed callback). Binding methods lazily to a single cached closure per object (a field per object, or a table keyed by object).

### D-076 · M3.3c3 split; builtin methods through `any` (M3.3c3a)
- **Date:** 2026-10-12
- **Decision:** M3.3c3 becomes M3.3c3a (the builtin methods of strings, numbers, booleans, arrays and functions called on dynamic values, and `Array.isArray` of them) and M3.3c3b (maps' and sets' methods through `any`, which need their keys' declared types in descriptors, and `Object.keys`/`values`/`entries` of dynamic values); no scope is dropped. **Dispatch:** `pts_dynamic_call_method` on a value that isn't an object of the program looks the method up by name in a table for the receiver's kind (`dynamic_methods.c`: strings; numbers, booleans and boxed 64-bit integers; arrays; functions), and failing that, calls the function the property holds (a hash-map object's), so an unknown method is V8's `x.m is not a function`. Each method takes its arguments as dynamic values with JS's conversions: an index or count is ToNumber of its argument, a missing one the default the typed lowering passes (NaN for the start, Infinity for the end, D-015's ToIntegerOrInfinity reading NaN as 0); a string is ToString of its argument (so `indexOf(undefined)` searches "undefined", as in JS); a callback must be a function, else V8's `TypeError: number 5 is not a function`, and is called through its dynamic entry with (element, index, array) as dynamic values; `sort`'s comparator likewise (V8's message), its result ToNumber with NaN as 0. Strings: at, charAt, charCodeAt, concat, endsWith, includes, indexOf, padEnd, padStart, repeat, slice, split, startsWith, substring, toLowerCase, toUpperCase, trim and its variants, toString, valueOf (what the runtime implements; M3.5 adds the rest). Numbers and booleans: toString (radix 10 only until M3.5) and valueOf. Arrays of any element type: at, concat, every, fill, filter, find, findIndex, findLast, findLastIndex, flat, flatMap, forEach, includes (SameValueZero), indexOf and lastIndexOf (===), join, map, pop, push, reduce, reduceRight, reverse, shift, slice, some, sort, splice, toString, unshift; elements are read boxed, and values written (push, unshift, fill, splice) are converted to the array's declared element type (`pts_storable`, D-072: `Cannot set property element of Array: expected T, got U`); slice, splice and filter keep the array's type, while map, concat, flat and flatMap, whose elements are new, make `any[]`. Functions: call and apply (`this` ignored: only methods take it) and bind, which makes a runtime closure (named "bound f", no code or signature, so typed code gets it through an adapter, D-075). `Array.isArray` of a dynamic value or a union is decided at run time (`pts_value_is_array`: arrays and tuples); for a union it was decided statically before, wrongly when it held an array. The message of a primitive written to a place of another kind is now `Cannot set property p of C: expected T, got U`, as for object types.
- **Reason:** The session rule for tasks too big for one session. JSON's results are dynamic strings, numbers, arrays and hash-map objects, and code that handles them calls their methods directly (`data.items.map(…)`, `name.toUpperCase()`); a runtime table per kind reuses the typed implementations and needs no code per call site. Making new arrays `any[]` where JS fills them with arbitrary values keeps them truthful, and converting values written to typed arrays keeps the arrays' invariant (tie-breaker 1).
- **Alternatives rejected:** Lowering each method call through `any` to a switch on the receiver's kind in generated code (code size at every call site, and the same table anyway). Typed results for map (the callback's results have no declared type). Passing `this` to `call`'s function (closures don't take it).

### D-077 · Maps, sets and `Object.keys` through `any` (M3.3c3b)
- **Date:** 2026-10-12
- **Decision:** In a program whose descriptors carry declared types (D-072), map and set descriptors carry their keys' declared type (`pts_type.key_check`) and maps their values' (`pts_type.check`, as hash-map objects already did). Through `any`, maps have get, has, delete, clear, set and forEach (`callback(value, key, map)`), sets add, has, delete, clear and forEach (`callback(element, element, set)`), and hash-map objects hasOwnProperty, in `dynamic_methods.c`'s tables. A lookup's key converts to the key kind if it fits it (a key that doesn't can't be in the map: get gives undefined, has and delete false); a stored key or value is converted to its declared type (`pts_storable`: `Cannot set property key of Map: expected string, got number`). keys, values and entries, which return iterators in JS, throw TypeError until M4.1. `Object.keys`, `values`, `entries` and `hasOwn` of a dynamic value are runtime functions (`ValueKeys`, `ValueValues`, `ValueEntries`, `ValueHasOwn`; `pts_value_keys` and the rest) whose result the lowering converts to the type tsc gives the call (so entries' `[key, value]` arrays are copied into tuples): the own enumerable keys in JS's order are a hash-map object's in its key order, an object's fields in its descriptor's order (accessor properties of literals included, `#private` fields, absent optional properties and an error's own name, message and cause left out, as JS doesn't enumerate them), an array's, tuple's or string's indices, and none for numbers, booleans, maps, sets and functions; values and entries read each key through `pts_dynamic_get` (so getters run); null and undefined throw V8's `Cannot convert undefined or null to object`.
- **Reason:** Completes the methods M3.3c planned for dynamic values with the same rules as arrays (D-076): reads need no checks, writes convert to declared types (tie-breaker 1). Reusing `pts_dynamic_get` for values keeps Object.values consistent with property reads through `any`.
- **Alternatives rejected:** Returning arrays from keys(), values() and entries() before iterators exist (`console.log(m.keys())` and identity would differ from Node; M4.1 makes them iterators). A key check stored in the check of the map type (records already keep their values' check in the descriptor).

### D-078 · M3.3d split; generic function values are erased copies or context's instances (M3.3d1)
- **Date:** 2026-10-12
- **Decision:** M3.3d becomes M3.3d1 (generic function values: generic function declarations used as values, generic arrow functions and function expressions, generic function types, instantiation expressions `f<T>`) and M3.3d2 (generic methods of object literals and interfaces, generic class methods through interfaces and as values); no scope is dropped. **Erasure:** a generic function used as a value has an *erased copy*, one function whose type parameters take dynamic values: while it is lowered (`substitution.erased`), every checker type that mentions one of its type parameters is `any` (`mentionsErased` compares the type instantiated with the parameters as `any` and as themselves, which tsc interns), so a `T` parameter, a `T[]` and a `(x: T) => U` are all `ir.Value`, and everything done to them goes through the dynamic machinery of M3.3a–c (reads, writes, operators, calls, builtin methods, checked conversions). Values the code makes take the type with the erased parameters replaced by `any` instead (`instantiateMade`: array and object literals, `new`, rest parameters' arrays: `[x]` is an `any[]`, `{ value: x }` a `{ value: any }`, `new Box(x)` a `Box<any>`), and are boxed where the erased type goes. A generic function type is the function type of its erased signature (`<T>(x: T, n: number) => T[]` is `(value, number) => value`), so every value of it, a closure of `(x: any) => any` included, has one representation. **Which copy:** a generic function declaration named where tsc's context is a function type with one call signature that isn't generic is the monomorphized instance (D-049) for the type arguments tsc infers from that signature, as it does when it relates the two (`PtsInstantiateSignatureInContextOf`): `[1, 2].map(identity)` passes `identity_number`. Anywhere else (`const id = identity`, a generic context) it is the erased copy (`<name>_dynamic`, shown by `console.log` as the function). A generic arrow function or function expression, or one a generic contextual signature makes generic (`const f: <T>(x: T) => T = (x) => x`), is always erased. An instantiation expression `f<number>` is f's instance, or for any other value its conversion to the instantiated type. A call of a generic function from erased code whose type arguments mention erased parameters calls the callee's erased copy, so that arrays and objects pass by reference rather than being converted. **Boundaries:** a call of a value of a generic function type boxes its arguments and converts the dynamic result to the type tsc gives the call with a check (`fromErased`: `TypeError: Expected T, got U`, D-070/D-071), as does an adapter from an erased function type to an instantiated one (`[1, 2].map(g)` for a generic arrow g). **Iterating dynamic values** (which erased code needs for `for (const x of xs)`): `for…of` over a dynamic value reads an array or tuple live by index, and a string's code points, a set's elements or a map's [key, value] entries from a new array (`pts_value_iterable`); spreading one (into an array literal, a rest parameter or a call through `any`) and destructuring one with an array pattern take a new `any[]` of its items (`pts_value_to_array`, `ir.ValueArray`); anything else throws V8's `TypeError: x is not iterable`. Converting a dynamic tuple to another tuple type copies it element by element, as an array is. Erased code that makes an instance of a generic class makes the instance for `any` (`Box<any>`), which doesn't convert to another instance (`Box<number>`): a known issue.
- **Reason:** The session rule for tasks too big for one session. One erased copy is the only representation one value can have for every type argument (D-051), and making types that mention type parameters `any` reuses all of M3.3's checked dynamic machinery, so erased code is as safe as any other code that handles dynamic values (tie-breaker 1) while typed code keeps unboxed instances. Taking the instance where the context fixes the type arguments keeps the common case, a generic helper passed as a callback, monomorphized and fast. Erasing whole types rather than only the type parameters (`T[]` as `any`, not `any[]`) keeps arrays and objects passed to erased code shared with the caller, as JS shares them, instead of copying them into `any[]`s.
- **Alternatives rejected:** Substituting `any` for the type parameters only (`T[]` as `any[]`): a `number[]` argument would have to be copied into an `any[]`, so the callee's writes would be lost. Dictionary passing (type descriptors as hidden arguments, specialising at run time): a second representation of every generic type, for no gain over checked dynamic values. Monomorphizing generic arrow functions bound to `const`s: closures capture their scope, and calls through other names (parameters, properties) would still need erased copies; it can come later as an optimisation. Copying `Box<any>` instances into `Box<number>` at boundaries (breaks identity silently).

### D-079 · Generic methods: erased signatures, erased copies in method tables, adapted interface calls (M3.3d2)
- **Date:** 2026-10-12
- **Decision:** **Signatures:** a generic method of an interface or object type has its erased signature (D-078) in the interface's method list and in a shape's method field (`interfaceMethod` lowers it with the method's type parameters erased), and an object literal's generic method (or one a generic contextual signature makes generic) is an erased closure in its field. A call through an interface or a shape's method field whose result is dynamic converts it to the type tsc gives the call with a check (`fromErased`), as calls of generic function values do. **Classes:** a class's generic method keeps being called directly through its instances (D-051); its erased copy (`erasedInstance`, taking `this`) joins the class's method table as a plain method (`addErasedMethod`) only when the program can find it by name at run time: an interface or object type with a generic method of that name exists, or a property of that name is read or called through `any` (a computed key through `any` makes every generic method join). Every other generic method stays out of the tables, so no body is lowered erased unless the program needs it. A class's method that overrides a generic method is now PTS1001, as D-051 meant (it was silently ignored: calls typed with the base class reached the base's instance). **Values:** a generic method read as a value (`o.m`, `C.m`) is, like a generic function (D-078), the instance its context implies or the erased copy, bound to the object as other methods are (D-044); a static one is unbound. **Adapted interface calls:** an object that came through `any` may hold a method of another signature than an interface's: an erased copy's `Box<any>` where `Container<number>` is expected (its `get()` returns any). Converting a dynamic value to an object type with methods now accepts a method of the same name with a dynamic entry (`descriptor_implies`), and in a program whose descriptors carry declared types every interface call site finds its method with `pts_method_find_adapted`, which returns the method when its signature is the site's and otherwise a generated adapter of the site's signature (`pts_method_adapter_N`, one per interface method name and signature) that boxes the arguments, calls the method's dynamic entry (`pts_method_call_dynamic`) and converts the result with a check; only exact methods are cached at the site. **Also:** an arrow function without a return type in a context whose function type returns an interface returns that interface, so `(b) => (b ? new Square() : new Circle())` passes as a `(b: boolean) => Shape` (it was PTS1001: the union of the two classes didn't convert from the conditional's interface value).
- **Reason:** Completes D-051's plan with D-078's representation: interfaces and object literals need one entry per method name, which only an erased copy can fill for a generic method, while classes keep their monomorphized instances for typed calls. Adding erased copies to tables only on demand keeps programs that never dispatch generic methods dynamically exactly as before. Adapting at interface call sites rather than rejecting the conversion makes the commonest generic-method pattern, a functor or option type whose `map` makes an instance in erased code, work through its interface, with the same run-time checks as every other boundary from `any` (tie-breaker 1).
- **Alternatives rejected:** Erased copies of every generic method in every table (bodies that erased code can't lower yet would turn compiling programs into errors). Checking signatures at every interface call (the site cache would have to remember the adapter, and typed programs gain nothing: their objects always fit). Wrapping mismatched objects in proxies at the conversion (breaks identity). Copying `Box<any>` into `Box<number>` (still the known issue for class-typed places, D-078).

### D-080 · M3.4 split; how JSON.parse and JSON.stringify work (M3.4a)
- **Date:** 2026-10-12
- **Decision:** M3.4 becomes M3.4a (`JSON.parse` and `JSON.stringify`) and M3.4b (the JSON and `Map`-heavy word-frequency benchmarks); no scope is dropped. **Parse** (`pts_json_parse`, `json.c`): a recursive-descent parser over the string's UTF-8 bytes (with the stack guard, so absurd nesting throws RangeError) that makes dynamic values: objects are hash-map objects of `any` (`pts_type_any_record`, the runtime's one descriptor of `Record<string, any>`, which cgen now uses for the program's own `Record<string, any>` too, so converting a parsed object to it keeps the object), arrays `any[]`, numbers by `strtod` (correctly rounded, as JS), strings with escapes and surrogate pairs decoded (a lone surrogate escape stays one, WTF-8, D-014); a repeated key keeps its first place and its last value; keys are listed in JS's order (array indices first) as every hash-map object's are. Malformed text throws SyntaxError with V8's messages, byte for byte: the specific ones (`Expected ',' or ']' after array element in JSON at position 3 (line 1 column 4)`) where V8 gives them, `Unexpected end of JSON input`, `Unexpected token 'x', "…" is not valid JSON` with V8's context rule (the whole text up to 21 code units, else ten code units on either side with `...`), `"undefined" is not valid JSON` for V8's four special texts; positions and columns count UTF-16 code units. A reviver is PTS1001. A dynamic argument is converted with JS's ToString. **Stringify** (`pts_json_stringify`): the ES algorithm over any value, boxed: `toJSON` (a method of the program's classes and object literals, or a hash-map object's function), a replacer function (called through its dynamic entry, without `this`) or property list (strings and numbers, each once), an indent of up to ten spaces or the first ten characters of a string; numbers by JS's ToString (NaN and the infinities as null), boxed 64-bit integers exactly, strings quoted as JS quotes them (lone surrogates as `\udxxx`), arrays and tuples as arrays (undefined and functions as null), every other object by its own enumerable keys in JS's order and values as reads through `any` see them (`pts_value_keys`, `pts_dynamic_get`: fields in declaration order, literals' getters run, `#private` fields, absent optional properties and an error's name, message and cause left out; maps and sets are `{}`), undefined and functions left out; a cycle throws V8's multi-line TypeError (`--> starting at object with constructor 'Object'`, `|     property 'b' -> …`, the middle elided past three links, `--- property 'self' closes the circle`). The lowering boxes the arguments; the result stays dynamic where the context takes any value or undefined (console.log's arguments print `undefined` as Node does), and elsewhere is converted to a string with a check (`TypeError: Expected string, got undefined` where JS would put undefined in a string). A program that calls JSON.stringify gets dynamic entries and full method tables, as one that calls through `any` does (D-074). Also: console.log shows a hash-map object's own `__proto__` key as `['__proto__']`, as Node does.
- **Reason:** The session rule for tasks too big for one session; the benchmarks need the functions first. Making parse's results the same dynamic values the rest of `any` already handles gives property reads, methods, iteration and checked conversion to typed data (D-071's copies) for free, and stringify reads values exactly as `any` does, so both follow one model of the program's objects. V8's messages are part of the output programs print in `catch` blocks, hence byte-for-byte.
- **Alternatives rejected:** Parsing into typed objects from the contextual type (`const p: Point = JSON.parse(s)`): a second, type-directed parser for each target type, for a speed-up the benchmark can show later is needed (the dynamic route converts with a copy). A generated serializer per type (fast, but needs the same descriptors at run time anyway for `any`; can come later for hot paths). Returning `string | undefined` typed results (tsc says string; the check catches the rare undefined).

### D-081 · The JSON and word-frequency benchmarks; JSON's fast paths (M3.4b)
- **Date:** 2026-10-12
- **Decision:** `pts/bench/json` stringifies 50,000 typed records (an interface with a nested object and an array), parses the text back into dynamic values, reads every record through `any`, and stringifies the parsed data plain and indented, three rounds; it prints lengths and checksums, so Go's `encoding/json` twin (structs, then `[]any` of `map[string]any`, whose keys it sorts: only the parsed data's lengths are compared) prints the same. `pts/bench/word_freq` counts two million words of a generated text (MINSTD random numbers, which stay below 2^53 in every language, squared for a skewed choice from 20,000 words) in a `Map<string, number>`, sorts the entries by count and word with a comparator, and prints the top ten and a checksum; Go uses a `map[string]int` and `sort.Slice`. Node and Bun run both `.pts` files as they are. Profiling the JSON benchmark (callgrind) led to three fast paths in `json.c` with unchanged output: stringify reads an object's fields and a hash-map object's entries in place (in Object.keys' order and with its rules) instead of listing keys and reading each through `any`; parse keeps one string per repeated object key (a 256-entry cache by hash of the key's bytes, per parse); quoting copies a string that needs no escapes in one go.
- **Reason:** The brief's single-threaded benchmark list names both. Printing results every implementation agrees on keeps run.sh's output check meaningful even where Go's library orders keys differently. The fast paths took JSON from 1.58 s to about 1.1 s; the rest of the time is spread over number formatting (Ryu), allocation and marking, and hashing, which later milestones (M8) can address.
- **Alternatives rejected:** Comparing the parsed data's re-stringified text across implementations (Go sorts map keys). A typed parse into the interface for the benchmark (the point is the dynamic path that `JSON.parse(s)` takes in real programs). Benchmarking without the fast paths (the profile showed key arrays and per-field lookups that cost a third of the time for nothing).

### D-082 · M3.5 split; the String methods of M3.5a and `localeCompare`'s collation
- **Date:** 2026-10-12
- **Decision:** M3.5 becomes M3.5a (strings), M3.5b (numbers: methods, statics, globals, conversions, `String`/`Number`/`Boolean` as values), M3.5c (`Math` in full and the remaining array methods), M3.5d (`Object` functions and `for…in`) and M3.5e (basic `Date`); no scope is dropped, and `normalize` moves to M6.1, since normalization needs Unicode's decomposition and composition tables (a piece of work of its own) and its common use, stripping accents, needs regular expressions anyway. **Methods:** `at`, `charAt`, `codePointAt`, `lastIndexOf`, `substr`, `isWellFormed`, `toWellFormed`, and `toLocaleUpperCase`/`toLocaleLowerCase` (the root mappings, which every locale but Turkish, Azeri and Lithuanian shares) are runtime functions in the builtins table, with D-016's index conventions (`at` and `codePointAt` give a dynamic value, undefined out of range; a left-out `lastIndexOf` position is NaN, read as the end). A builtin method given more arguments than the runtime takes is now PTS1001 instead of silently dropping them (`toLocaleUpperCase("tr")`). `concat` lowers to concatenations (a spread `string[]` joined). `replace` and `replaceAll` take a string pattern (RegExp is M6.1) and either a replacement string, which the runtime substitutes with GetSubstitution's `$$`, `$&`, `` $` `` and `$'` (other `$` sequences stay, as a string pattern has no captures), or a callback, for which a generated helper per callback type finds the matches (an empty pattern advancing a unit at a time) and calls it with as many of (match, position, string) as it takes. `String.fromCharCode` and `String.fromCodePoint` pass their arguments (spreads included) as one `number[]` (`ir.NumberArray`, now the lowering's one number array type); fromCodePoint throws V8's `RangeError: Invalid code point n`. Through `any` the same methods are in `dynamic_methods.c`'s string table; a replacement that is a function is called through its dynamic entry. **localeCompare** orders strings as Node's default collator does (ICU's root collation at tertiary strength) from per-code-point weights generated out of Node's ICU (`pts/runtime/gen/collation_tables.mjs` → `collation_tables.h`): sorting every code point of the tables' blocks (Latin through CJK symbols, Yi and extensions, Hangul jamo, presentation and fullwidth forms, emoji) with the collator and grouping neighbours at base, accent and variant sensitivity gives each a primary rank and a secondary and tertiary rank within its group, 0 where it is ignorable at that level; strings compare by their primary weights, then secondary, then tertiary, skipping zeros (`collation.c`). Hangul syllables decompose into their jamo; code points outside the blocks take ICU's implicit weights (core Han, then other Han, then the rest, each in code point order). An English locale argument (or undefined) is accepted; other locales and options are PTS1001 (TypeError through `any`). On 300,000 random strings of Latin letters with accents, digits, punctuation, Greek, Cyrillic, Han, Hangul, emoji, combining marks and controls, the order equals Node's; the generated corpus checks it (`locale_compare_*` parts).
- **Reason:** The session rule for tasks too big for one session. Sorting names with `localeCompare` is common in plain TypeScript, and Node's order (case-insensitive first, accents second, lowercase before uppercase on ties) differs from code-unit order in nearly every list, so an approximation by `<` would break the differential tests; taking the weights from Node makes Node the oracle as D-016 did for case mapping. A table per code point is small (80 KB, linked only into programs that call localeCompare) where vendoring ICU would be tens of megabytes.
- **Alternatives rejected:** Vendoring ICU (huge, and a second copy of what Node already has). Code-unit order (wrong for mixed case and accents). Global secondary and tertiary ranks (a combining mark's secondary weight would sort below a base letter's, where ICU puts it above). Expansions in the tables (ICU compares ß as "ss" and æ as "ae"; the per-code-point model compares them as letters of their own, a documented difference that the corpus leaves out). Silently ignoring locales and options (wrong for Swedish, Turkish or `numeric: true` without a word).

### D-083 · Numbers: formatting, parsing, predicates and conversions (M3.5b)
- **Date:** 2026-10-12
- **Decision:** **Formatting** (`number_methods.c`): `toFixed`, `toExponential` and `toPrecision` round the number's exact decimal value half up (ECMAScript's "pick the larger n"), taking the exact digits from glibc's `printf("%.*f")` with a precision that covers every fractional digit the double has (53 minus its binary exponent), so 1.005.toFixed(2) is "1.00" and 2.5.toFixed(0) is "3" as in V8; their range checks and V8's messages come in the spec's order (toFixed checks the digits before NaN and Infinity, the others after). `toExponential()` without an argument uses Ryu's shortest digits. `toString(radix)` is V8's `DoubleToRadixCString` ported line by line (fraction digits until they pin the double down, rounding to even, carry back into the integer part); a 64-bit integer's is exact (`pts_i64_to_string_radix`, `pts_u64_to_string_radix`). `toLocaleString()` is Node's default English `NumberFormat`: the shortest digits (as ICU rounds them, so 1.0005 gives "1.001") rounded half up to 3 decimals, grouped by commas, `∞`, `-0`; an English locale is accepted, other locales and options are PTS1001. **Parsing:** `parseInt` follows the spec (whitespace, sign, ToInt32 radix, `0x`) with V8's value: radix 10 through `strtod` (correctly rounded), power-of-two radices rounded to nearest-even as V8 does, others accumulated in 32-bit parts as V8 does; `parseFloat` takes the longest StrDecimalLiteral prefix (and Infinity) through `strtod`. `Number.parseInt` and `Number.parseFloat` are the same. **Predicates:** `Number.isInteger`, `isSafeInteger`, `isFinite` and `isNaN` test a number directly and any other value as a dynamic value (false unless it is a number, boxed 64-bit integers included); the global `isNaN` and `isFinite` convert with ToNumber first. Number's constants are constants. **Conversions:** `Number(x)` and unary `+`, `-` and `~` on any value are ToNumber of it (non-numbers through their dynamic value, so strings parse and objects convert as their strings); only a void operand is left out (PTS1001). `Boolean(x)` is ToBoolean. `String`, `Number` and `Boolean` used as values are static closures of synthesized functions of one dynamic parameter (`xs.map(Number)`, `xs.filter(Boolean)`), printed `[Function: Number]`. Through `any`, numbers have their own method table (`toFixed`, `toPrecision`, `toExponential`, `toString(radix)`, `toLocaleString`, `valueOf`) and booleans theirs (`toString`, `valueOf`), so a boolean's `toFixed` is V8's "is not a function".
- **Reason:** Formatting numbers for output (`toFixed(2)`) is one of the most common things plain TypeScript does, and every digit is compared with Node, so the rounding must be ECMAScript's exact one; glibc already computes exact expansions, and the precision bound keeps it cheap for ordinary numbers. Porting V8's radix and parseInt algorithms makes the approximate cases (which the spec leaves to the implementation) agree with Node too. The generated corpus checks all of them on 800 random numbers per run.
- **Alternatives rejected:** `printf("%.*f", f)` alone (rounds ties to even: 2.5.toFixed(0) would be "2"). Big-decimal arithmetic of our own (more code than letting printf print the exact expansion). Approximating toString(radix) with repeated multiplication (differs from V8 in the last digits). `toLocaleString` through a vendored ICU (huge for one format). Making `String`, `Number` and `Boolean` values only where a callback type is known (the closure is simple and works everywhere).

### D-084 · M3.5c split; Math as V8 computes it
- **Date:** 2026-10-12
- **Decision:** M3.5c becomes M3.5c1 (`Math` in full) and M3.5c2 (the remaining array methods); no scope is dropped. **Math's transcendental functions are V8's fdlibm:** `pts/runtime/src/ieee754.c` is V8 13.6.233.17's `src/base/ieee754.cc` (the version Node 24 ships) converted to C (bit casts through memcpy, `pts_ieee754_` names, static helpers, the legacy pow left out), with Sun's fdlibm notice and V8's BSD license kept in its header; `sin`, `cos`, `tan`, their inverses and hyperbolic forms, `exp`, `expm1`, `log`, `log1p`, `log10`, `log2`, `cbrt` and `atan2` call it. `pow` is `**` (glibc's, which equals V8's, D-011). `hypot` is V8's algorithm (Infinity before NaN, Kahan summation of the squares scaled by the largest). `fround`, `imul` and `clz32` are inline. `random` is xorshift128+, as V8's, with a state per thread seeded from `getentropy`. Arguments convert with ToNumber (so `any` works); `Math.max`, `Math.min` and `Math.hypot` with spread arguments take them as one number array (`pts_math_max_of`, …). Math's functions used as values are static closures of synthesized functions (a rest parameter for the variadic ones), named as V8 names them (`[Function: sqrt]`). The Math object itself as a value stays PTS1001.
- **Reason:** Differential tests print every digit, and glibc's libm, more often correctly rounded than fdlibm, differs from Node in the last bit for 1 % (sin) to 50 % (cbrt) of random inputs; the converted fdlibm equals Node on all 440,000 inputs measured, and the generated corpus keeps checking it (`math` part). Taking the code from the V8 that Node ships is the only way to get V8's last bits.
- **Alternatives rejected:** glibc's libm (wrong last bits, so programs that print trigonometry differ from Node). Writing fdlibm from FreeBSD's msun (V8 modified it; its results are the oracle). Vendoring V8 as a submodule for one file (gigabytes). A seeded, reproducible `random` (Node's isn't).

### D-085 · The remaining array methods, `new Array(n)` and holes (M3.5c2)
- **Date:** 2026-10-12
- **Decision:** `at` is a runtime read relative to the end (a dynamic value, undefined out of range). `toSorted`, `toReversed` and `toSpliced` are `sort` (or `sort` with the comparator), `reverse` and `splice` on a copy (`ArrayCopy`); `with` copies and writes, with V8's `RangeError: Invalid index : i`. `Array.of(…)` is an array literal of the call's type. **`new Array(n)` and `Array(n)`** with one numeric argument make n holes (`NewArray.Length`, `pts_array_of_length`, V8's `RangeError: Invalid array length`); other arguments are the elements. Without type arguments the array takes its contextual array type where tsc says `any[]`. Holes are zero slots, which arrays of strings, objects and dynamic values already read as holes (D-038): they read as undefined where any value can go, throw RangeError where an element is required, and now print as Node's `<n empty items>` (`format_elements` ports formatSpecialArray); arrays of numbers, integers and booleans have no zero that isn't a value, so their slots start as 0 or false. `Array.from({ length: n }, f)` calls f with (undefined, i) for each i below n (a helper per callback type); without f it is n undefineds. `keys()`, `values()` and `entries()` of an array where they are iterated (`for…of`, spread, `Array.from`) are the indices, the array itself, and [index, element] pairs (a helper per array type); used anywhere else they stay PTS1001 until iterators arrive (M4.1). An `any[]` converts to a typed array as dynamic data does, by a checked copy (D-071), so `const counts: number[] = new Array(n).fill(0)` works. Through `any`, arrays gained `toSorted`, `toReversed`, `toSpliced` and `with`.
- **Reason:** These are the array idioms of modern TypeScript (`new Array(n).fill(0)`, `Array.from({ length: n }, (_, i) => …)`, `for (const [i, x] of xs.entries())`); materialising keys and entries as arrays where they are iterated gives JS's results without iterator objects, which M4.1 brings. Holes reuse the representation racing pushes already leave, so nothing new has to be checked where arrays are read.
- **Alternatives rejected:** Filling `new Array(n)` of any type with explicit undefineds (prints `[ undefined, … ]` where Node prints `<n empty items>`, and arrays of numbers can't hold undefined anyway). A "hole" bit for primitive arrays (every read would test it). Returning arrays from `keys()` and `entries()` everywhere (a value printed or kept would be an array where JS has an iterator).

### D-086 · Object's functions, `for…in` over any value, covering intersections (M3.5d)
- **Date:** 2026-10-12
- **Decision:** `Object.keys`, `values`, `entries` and `hasOwn` of a value that isn't a hash-map object go through its dynamic value and the runtime's own-keys list (D-077: a class instance's fields in its constructor's order, a literal's properties in its order with its getters, an array's or string's indices, no private or left-out optional properties); `keys` is a `string[]` at once (`pts_value_key_array`), `values` and `entries` are converted to the type tsc gives them by a checked copy. `for…in` over any value visits the same keys, taken when the loop starts; over a dynamic value or a union each key is tested again before its turn, as a hash-map object's are (D-059). `Object.assign(target, ...sources)` writes each source's own enumerable properties to the target through its dynamic value, so they are checked against the target's declared types (`TypeError: Cannot add property p, object is not extensible` for one it doesn't have, as for any other write, D-066); null and undefined sources are skipped; its value is the target. Into a new `{}` it is PTS1001 with a hint to use a spread. `Object.is` is SameValue (`pts_value_same_value`). `Object.freeze` returns its argument as `Readonly<T>`; freezing isn't enforced at run time (writes through the frozen type are tsc errors already), and `isFrozen` stays PTS1001 rather than answering wrongly. `Object.fromEntries` of an array of [key, value] tuples or a map makes a hash-map object (a helper per pair type), keys converted to strings. An intersection type whose properties one of its members already has (`Settings & { width: number }`, which `Object.assign` returns; `T & {}`) is that member's IR type. A property read on an index signature the ES library declares (`Object.fromEntries`' result) is an entry, not an Object.prototype member.
- **Reason:** These are the Object idioms of everyday TypeScript (iterating an object's entries, merging settings into a target, building a lookup from pairs); the dynamic machinery of M3.3 already knows every object's own keys and checks every write, so reusing it keeps one definition of an object's properties and their order.
- **Alternatives rejected:** Generating per-type key lists in the lowering (a second source of the property order, which console.log and JSON already take from descriptors). A frozen flag checked on every write (a cost on every field store for a rare feature). Answering `isFrozen` with a constant (silently wrong). Making `Object.assign({}, …)` a spread literal of the intersection type (the intersection isn't an object type the IR has; the spread is the TypeScript idiom anyway).

### D-087 · Basic Date (M3.5e)
- **Date:** 2026-10-12
- **Decision:** `Date` is a builtin class the runtime defines (`pts_date`: a time value, NaN when invalid; descriptor kind `PTS_KIND_DATE`). Its constructor's forms (now, a time value, a string, another date or any value, local components with two-digit years), `Date.now`, `Date.UTC`, `Date.parse` and its methods are runtime functions (`Func.Extern`, which cgen now names wherever a program calls one) that the lowering calls directly: getters and setters through one function each with a field number (setters take the count of arguments given, so left-out ones keep the date's components), formats through one with a format number. The arithmetic is ECMAScript's (21.4.1: MakeDay, MakeTime, TimeClip, the year and month from a time). Local time takes its offsets from the C library's time zone rules (TZ, /etc/localtime), as V8 takes them from ICU's; a local time in a DST gap or overlap takes the offset before the transition, as V8 does. `toString` and `toTimeString` need the zone's long name, which V8 gets from ICU: a table maps the common abbreviations (EST, EDT, HKT, CET, …, telling China's CST from America's by offset) to ICU's names, and others get ICU's fallback `GMT+hh:mm`. `Date.parse` reads ECMAScript's ISO format (date-only forms UTC, date-times without an offset local, V8's leniency about the day of the month) and the other forms dates print and people commonly write (`Jan 15, 2024`, `15 January 2024 10:30 PM`, `2024/01/15`, `1/15/2024`, the toString and toUTCString forms); anything else is NaN. `console.log` prints a date's ISO string (or `Invalid Date`), JSON uses `toJSON`, ToString gives `toString`, ToNumber and the relational operators use the time value, and `+` the string, as ToPrimitive's hints say. Through `any`, dates have a method table of their getters, setters and formats. The tests run every program, under pts and Node, with `TZ=America/New_York`, so local times print alike on every machine and cross DST. Left out (PTS1001): the `toLocale…` formats (locale-dependent, ICU's), `Date()` called as a function, classes extending Date, `getYear`.
- **Reason:** Dates appear in most real programs (timestamps, durations, ISO strings in JSON). The C library already knows the time zone rules, and ECMAScript's own arithmetic gives the calendar for the whole ±275,760-year range without depending on the C library's range; the corpus test agrees with Node on 37 lines across constructors, DST transitions, setters, invalid dates and formats.
- **Alternatives rejected:** Vendoring ICU for zone names and locale formats (tens of megabytes). `mktime`/`gmtime` for the calendar (limited range, and C's rules for out-of-range components differ from MakeDay's). UTC as the only local time (wrong wherever TZ isn't UTC). Making the corpus depend on the machine's time zone (CI runs in UTC, so DST would never be tested).
