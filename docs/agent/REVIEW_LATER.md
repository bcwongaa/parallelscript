# For the owner to review after DONE

Decisions made autonomously that are big enough to deserve a look. Nothing here blocks work.

- **D-005**: `pts` ignores `tsconfig.json`; every program is checked with fixed options (strict, ESNext, no DOM lib, every file a module). Revisit if projects need `include` lists or path mappings.
- **D-008**: the master plan lacked a task for imports between `.pts` files; M1.4 was split into M1.4a (control flow) and a new M1.4b (modules).
- **D-015**: reading a string index out of range gives `undefined` where the context can hold it (printing, concatenation, comparison with a string) and throws `RangeError` where a `string` is required (`const c: string = s[9]`), because a `string` can't hold `undefined`. A documented difference from Node (SPEC §8); arrays should follow the same rule in M2.4.
- **D-023**: the brief lists nbody under M1, but its standard form needs arrays or classes (M2) and `Math.sqrt`; it moved to M2.7 instead of a throwaway scalar version. M1's benchmarks are fib (on `number`, against Node, Bun and Go) and fib on `int` (against Go).
- **D-020**: "declaration merging" (brief §2.4) is rejected except for function overloads and interfaces merging only with interfaces, which change nothing at run time. The top-level code's C function is now `pts_main` (was `pts_fn_main`, D-007).
- **D-035, D-036**: D-L10's "per-(concrete type, interface) tables built at compile time" became each descriptor's table of fields and of the methods and accessors interfaces may call, plus a one-word cache at every place that uses an interface (descriptor and offset or index). Values are one word (D-002), so a pair's table would have to be found from the object at each use anyway. Members must match the interface's IR types exactly (an `int` field doesn't provide a `number` property).
- **D-038**: arrays have no holes: writing past the end, growing `length`, and `pop()!` on an empty array throw `RangeError` (documented in SPEC §8). Racing pushes can leave an unwritten slot, read as a hole. Arrays of integer types (`u8[]`) wait for M2.6, which teaches the semantic pass to follow type nodes for generics anyway.
- **D-037**: the array methods that take callbacks (M2.4c) moved after closures (M2.5).
- D-051: generic function values and generic methods of object literals and interfaces moved from M2.6b3 to M3.3 (they need one boxed copy serving every type argument). Static members of generic classes and `instanceof` of a generic class are PTS1001 (D-050).
- **D-048**: the integer types became distinct number types inside the forked checker (a new `internal/checker/pts.go` plus one-line calls in the checker and type printer), and tsc now types arithmetic by ParallelScript's rules (`ints.map(x => x * 2)` is an `int[]`). This replaced the plan's sketch of following type nodes in the semantic pass. Consequence: tsc relates every numeric type to every other, so overloads match as for `number` (`reduce(f, 0 as int)` on a `u8[]` picks the `T` overload; write `reduce<int>(f, 0)`).
- **D-068**: exceptions use a thread-local chain of `jmp_buf` handlers (`_setjmp`/`_longjmp`), so calls cost nothing and entering a `try` costs a `_setjmp`; locals a try block assigns are `volatile` in C. The runtime's TypeError, RangeError and ReferenceError are now catchable Error objects (running out of memory stays fatal). An error's `name` is an own field (JS: inherited), invisible except to `Object.keys` and JSON.
- **D-069**: every generated function that may recurse starts with a stack check (two instructions on x86-64), which costs fib about 5%; unbounded recursion throws `RangeError` as in Node. Stack frames come from libbacktrace (a new vendored submodule, pinned to a commit since it has no tags) reading the program's DWARF; programs link `-static-libgcc`.
- **D-071**: converting dynamic data (an `any[]`, a hash-map object of `any`, M3.4's parsed JSON) to a typed array or object type makes a checked copy, where JS keeps the one object; typed objects that fit keep their identity. Copies into an object type keep only the properties it declares.
- **D-072**: an object goes through `any` and keeps its identity only when its fields' declared types imply the target type's (a `pet: Animal` field holding a Dog no longer passes as `{ pet: Dog }`; the object is copied). Writes through `any` into object- and union-typed places are checked against declared types, which descriptors now carry in programs that use `any`; such programs also get a descriptor per array-of-objects type.
- **D-074**: calls through `any` check each argument against the callee's parameter types (TypeError where JS would carry on with a wrong value); programs that call through `any` get a dynamic entry per function value and list every class method in method tables. M3.3c is split in three (calls; function types from `any`; builtin methods through `any`).
- **D-075**: a function of another type converted from `any` is wrapped in an adapter that checks its arguments and result when called (so it isn't `===` to the original); a method read through `any` is bound to its object, like typed method reads (D-044), and each read makes a new function. Any program that uses `any` beyond primitives gets declared types, dynamic entries and signatures together.
- **D-076**: builtin methods called through `any` dispatch by name at run time; `map`, `concat`, `flat` and `flatMap` on dynamic arrays make `any[]` arrays, and values written into typed arrays through them are checked. `Array.isArray` of a union is now decided at run time (it was decided statically, wrongly for a union holding an array). M3.3c3 is split (maps and sets through `any` next).
- **D-077**: maps and sets through `any` check stored keys and values against their declared types; their keys(), values() and entries() throw until iterators arrive (M4.1). `Object.keys` of a dynamic object lists its fields in declaration order, leaving out an error's own name, message and cause as JS does.
- **D-089**: the corpus (300 programs) found that realistic TypeScript often reads past an array's end or a missing hash-map key into a variable typed without `undefined` and checks it later (`const [a, b] = s.split(":")` then `b === undefined`; `const fn = TABLE[name]; if (fn === undefined) …`). D-015, D-038 and D-059 throw `RangeError` there by design; 13 corpus programs (4%) are skipped for it. `a[i] ?? d`, `a[i] === "s"` and values narrowed by an initializer already read undefined. Changing the rule for locals would need such variables to hold `T | undefined` while tsc says `T`. Also: type-level features (`keyof` access, `as` downcasts, recursive JSON types, enum objects) are lowered through the checked dynamic machinery, which is slower than typed code.
- **D-090**: locals initialized from an element read (or array destructuring) that the program tests for undefined hold `T | undefined` though tsc says `T`, and are checked where used as a `T`; other element reads into typed places still throw `RangeError` (D-015/D-038/D-059). The heuristic ("tested for undefined") is syntactic: a test in one function makes the local loose everywhere, and a local passed to a program function whose parameter takes undefined counts as tested.
- **D-105**: `Object.freeze` marks objects in a runtime side table (weak, via bdwgc disappearing links) so `Object.isFrozen` answers as in JS, but writes to frozen objects still succeed silently (JS modules throw TypeError). Enforcing it would need a check on every field write or a frozen twin of each descriptor.
- **D-106**: module-scope generic consts are now monomorphized where called by name also when they return objects whose type mentions their type parameters (`List<T>`, `Parser<T>`, `Map<K, V>`), not only generic class instances (D-102); consts returning arrays or plain type parameters keep their checked erased copies.
- **D-L13 and typed arrays** (found by the M6.1d docs review): the locked rule says racing threads never see torn values, but `typed_array.c` reads and writes elements as plain loads and stores of their element size and its header allows torn numbers under races (never outside the view). SPEC §4.1 now says so. Whether D-L13's wording should change is the owner's call. *Resolved by D-143 (M6.0a4): elements and bulk copies are relaxed atomics now.*
- **docs/BRIEF.md's `.par` example** `orders.par.map((o) => o.amount).sum()` doesn't type-check: `.par.map` returns a plain array, so it is `….par.map(…).par.sum()` (SPEC §5.5 and the guide use the working form). The brief is the owner's; left as written.
- **A tracked `.pyc`:** `tools/agent/__pycache__/driver.cpython-314.pyc` is in git (commit aeafc3aaa) although `.gitignore` excludes `__pycache__/`; sessions don't touch `tools/agent/`, so `git rm --cached` is left to the owner.
- **D-137 and the guardrail:** with `serve({ reusePort: true })` the `fetch` handler runs on every loop at once, so `let count = 0; … fetch() { count++ }` races (memory-safe, but counts get lost) with no compile error, where the same assignment in a `.par` callback is PTS3001. D-L17 says no new parallelism checks without the owner, so the guide and spec tell programs to use `AtomicInt` instead. Extending PTS3001 to `fetch` when `reusePort` is `true` is the owner's call.
- **D-143, the shared-memory contract** (`docs/ARCHITECTURE.md` §4.13): generated code reads and writes object fields, cells and number arrays with plain one-word C loads and stores, which ISO C calls data races; the contract relies on clang's x86-64 code generation (aligned word accesses are single atomic instructions, no repeated loads of heap words) rather than relaxed atomics, which would cost optimizations in every program. Typed arrays, the runtime's shared structures, generators and promises are atomic or thread-owned. Racing resumes of one sync generator throw `TypeError: Generator is already running` instead of waiting (waiting could deadlock).
- **D-169, the VS Code extension's identity:** the extension is packaged as `pts/editors/vscode/dist/parallelscript.vsix` with the publisher id `parallelscript`, version 0.7.0, and installed from the file; it isn't on the Marketplace or Open VSX. Publishing needs the owner's publisher account (and a token), and the id should be the owner's; changing it is one field in `package.json`.
- **D-172, races on shared collections:** a newcomer's first parallel program pushed into a captured array and counted into a captured `Map` from a `parallel for`; the results were silently wrong (duplicate keys, lost and doubled elements), as SPEC §4.1 allows. The guardrail (D-L17) only rejects assigning outer variables. A second check for `push`/`set`/`add`/`delete` on a captured collection in a parallel body would catch this common mistake; D-L17 says no new parallelism checks without the owner.
- **D-172, allocation-heavy `.par` code on all cores:** with the default thread count (every core), code that does little but allocate can run several times slower than sequential code (300,000 `split`s: 100 ms plain, 496 ms in `.par.map` on 8 threads). The guide says so and suggests `PTS_THREADS=4`; whether the default should change before M8's collector work is the owner's call.
- **D-182, copies of arrays that can't hold undefined:** JS's `toSorted`, `toReversed`, `toSpliced` and `with` read each index, so a hole becomes undefined in the copy; for a `string[]` or a `P[]` (an array of one non-union element type, which has no undefined), ParallelScript keeps the hole there (it prints `<1 empty item>` where Node prints `undefined`, reads as undefined where any value goes and throws RangeError where an element is required). Arrays of any union (`(string | null)[]` too) and `any[]` hold dynamic values and get undefined, as in JS. Matching Node exactly would need a second representation of undefined in such arrays (a "zero slot is undefined" twin of each array descriptor, as match copies have for strings, D-133). Holes in these arrays come only from `new Array<T>(n)` left partly unfilled and from racing pushes.
- **D-183, holes where the element type can't hold undefined (supersedes part of D-182):** a hole that JS reads as undefined (iteration, spreads, `Array.from`, `find`, the copying methods) is undefined in ParallelScript only where the array's element type holds undefined. H06a had also given undefined to arrays of unions without it, such as `(string | null)[]`, and typed code then took that undefined for a string after `x !== null` and crashed (SIGSEGV, C99). Now such arrays are treated like a `string[]`: copies and spreads keep the hole, which prints as `<1 empty item>` where Node prints `undefined`, and a typed read of it throws RangeError (C106). The alternative is the twin descriptor D-182 rejected, extended to unions: a "zero slot reads as undefined" twin per array descriptor, with typed reads of a union element checking for it. Also, `new Set(array)` of a `string[]` or object array still leaves holes out (D-130), where JS adds undefined.
- **D-221, a `for…of` variable at a hole and lying type predicates:** a `for…of` over a `string[]` or an object array now gives `undefined` at a hole, as JS does, and its use as the element type throws `TypeError: Expected string, got undefined` (the loop's variable is a loose local, D-090); before, the loop threw `RangeError` at the hole. H11b's review found a pre-existing memory-safety gap it didn't fix (C321, assigned to H20): a type predicate that lies (`v is string` for a number) about an ordinary local of a primitive or tuple union lets the program read the value as that member unchecked, which crashes (SIGSEGV); D-067 checks only narrowings to classes. Closing it without slowing sound narrowings (`typeof`, discriminants) needs the narrowing's source; the owner may prefer a check on every narrowed read instead.
- **D-223, HTTPS's library and trust store:** `fetch` speaks TLS through mbedTLS 3.6.7, the 3.6 LTS line, which mbedTLS supports until March 2027; 4.1 (the newer LTS, until March 2029) needs a generation step to vendor (its git tags lack the generated sources), so the move to it is left for later and should happen before 3.6's end of life. The trust store is the system's CA bundle, not the Mozilla bundle Node ships, so a program trusts what the machine trusts (and `NODE_EXTRA_CA_CERTS` adds to it, as in Node); `SSL_CERT_FILE` and `SSL_CERT_DIR` replace the system's as OpenSSL and Go read them. Verification can't be turned off, and Node 24's `--use-system-ca` advice isn't printed. Names follow Node's `checkServerIdentity`, not mbedTLS's own check. mbedTLS 3.6 can't check name constraints (it ignores a non-critical extension and rejects a certificate with a critical one), so a name-constrained CA isn't trusted at all: sites behind such a CA fail where Node works; no root of the system's bundle has them. A TLS 1.3 KeyUpdate or a TLS 1.2 renegotiation from the server fails the request (mbedTLS 3.6), and fetch has no connect or handshake timeout.
