## Policy and lifecycle

`serve` accepts `handshakeTimeout` (**10000 ms**) and `headersTimeout` (**60000 ms**). Each accepts finite integers **0..2147483647**; 0 disables it, omission/undefined selects its default, invalid numeric values throw RangeError naming the option before binding. These are explicit ParallelScript options, not Bun/Node option/default parity.

Handshake timing begins at adoption on the connection's assigned event loop. First headers begin there for HTTP, after successful handshake for HTTPS. Later headers begin with the next request's first bytes, only after preceding response output drains; idle keepalive is not timed. Progress never refreshes an active budget. Complete headers stop it before body buffering, 100 Continue or handler dispatch. Neither clock cuts an active handler or queued response. Expiry closes without a 408 or TLS alert write that an unread client could defer.

One lazily allocated libuv timer belongs to the connection's loop. Stop/disconnect/failure detaches its data, stops and independently closes/frees it before the TCP callback frees the connection. A monotonic absolute timestamp is also checked before reads/parse/handshake completion, so late callback ordering cannot accept already-expired completion. A distinct pending-header phase prevents body reads from rearming headers; the final-write callback revisits even a queue below the existing backpressure threshold.
