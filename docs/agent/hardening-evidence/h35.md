### The failed run: a test-isolation fault, not a TLS fault
In that run, every request to the lab's `localhost` server from `post` to `credentials, https to http` failed with `TypeError: fetch failed | UNABLE_TO_VERIFY_LEAF_SIGNATURE | unable to verify the first certificate`. Requests to other servers with the same certificate, before and after, verified, and so did `localhost` itself for `get`. That error means mbedTLS built a chain of the leaf alone and found no trusted root of its issuer's name and key identifier (`verify_failure`'s `lone_leaf`): the certificate came from another root.

Cause: on GitHub's runners `/etc/hosts` gives `localhost` as `::1` and `127.0.0.1`, and fetch tries the addresses in order (`fetch.c`, as Node does). The lab's `localhost` servers listen on `127.0.0.1:P` only. Each lab (every TLS test starts one, in parallel) also has a server on `[::1]:0`, the only IPv6 listeners in the suite. When the kernel gave one lab's `[::1]` server the port number another lab's `localhost` server had on IPv4, that lab's requests to `localhost:P` reached the other lab's server. Its certificate comes from a root with the same name, "PTS Test Root CA", and another key. Locally `localhost` is `127.0.0.1` alone (`getent ahosts localhost`), so it never happened here.

RED (`red.log`; the probe `zz_ci_collision_probe_test.go` serves a certificate from another root of the same name on `[::1]` at the lab's `localhost` port). `in-ci-hosts.sh` runs a command under an `/etc/hosts` like the runners' (`::1 localhost` first), in a private user and mount namespace (`unshare --user --map-root-user --mount`, then a bind mount; no root):
- local `/etc/hosts`: `"200\n"`;
- the runners' `/etc/hosts`: `"TypeError: fetch failed | UNABLE_TO_VERIFY_LEAF_SIGNATURE | unable to verify the first certificate\n"`, the failed run's line exactly;
- the new regression test `TestTLSLabIPv6ServerHoldsItsIPv4Port` (the lab's `[::1]` server must hold its port on `127.0.0.1` too) before the fix: `FAIL: 127.0.0.1:34373 is free while the lab's [::1] server listens at that port`.

Fix (`pts/tests/https_test.go`, tests only): `listen` on `[::1]:0` holds the port it gets on `127.0.0.1` as well (`listenIPv6Loopback`, which tries other ports while that one is taken), so no other listener, the tests' Go servers on `127.0.0.1` or a `pts:http` program on `0.0.0.0`, can have that port number, and a request to `localhost` at a server's port can reach only that server.

## H35a: targets, the runtime's x86-only code, the cross build under qemu, the arm64 CI job (D-225)
H35 is split into H35a and H35b (D-225): qemu-user on x86 doesn't reorder memory as arm does, so arm's memory ordering (the reproducer's M1 and M2, C356 and C357) is H35b's, with its own design and the arm64 CI job's evidence.

### Implementation
`pts/toolchain/target.go` (`Target`, `Targets`, `ParseTarget`, `TargetNames`, `targetFlags`, `crossFailure`), `toolchain.go` (`Toolchain.Target`, `PTS_TARGET`, the flags in every compile, check and link), `driver.go` (`BuildFor`), `cli.go` (`--target`, `parseFileAndOptions`, help), `sync.c` (`spin_pause`), `pts.h` (aarch64 `pts_stack_check`), `process.c` and `process.pts` (`pts_process_arch`), the two workflows, the docs.

Stack guard, aarch64 (`stackcheck/` in the parent's probes; clang 18 `-O2`): for a leaf, the `sp` read gives 7 instructions before the body (`adrp`, `ldr`, `mrs`, `ldr`, `mov sp`, `cmp`, `b.lo`) and puts the frame on the throwing path; `__builtin_frame_address(0)` gives 9 (the same plus `stp`, `mov x29`, `ldp`). In a real build the TLS access is relaxed to local-exec (`movz`, `movk`, `mrs`, `ldr`); in `fib`, clang sets up the frame before the guard anyway because the recursive path needs it.
