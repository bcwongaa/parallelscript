## Causes and fix

All in D-177.

- **C02.** A getter typed `void` or `never` had the IR result `void`, for which the C emitter has no run-time check (the panic in `checks.go`) and no field kind, and which isn't an interface property's `undefined`. `resultType` now gives a getter `undefined`.
- **C27.** `returnStatement` lowered a bare `return;` to C `return;` whatever the result type. It now returns undefined converted to the result unless the result is `void` or the function is a generator.
- **C18, C29.** `for…of` over a dynamic value was an index loop over `pts_value_iterable`, which drained generators and object iterators into arrays and snapshotted maps and sets; array patterns took values eagerly (`pts_iterator_take`, or `pts_value_to_array`). Now `pts_iteration_open` gives an iterator to step (generators, runtime iterators, maps and sets live, objects with `@@iterator`) or an array, tuple or typed array to read live by index (a string's code points as a new array); `iteratorLoop` steps it once per iteration and closes it on early exits, and `destructureIterable` binds element by element and closes it at the pattern's end or when binding throws (a `withFinally` only when an element can throw).
- **C31.** Loose locals (D-172) covered a declaration's names over arrays only; `readsElement` now covers every source but a tuple.
- **C03 (typed half).** Kept as a diagnostic: `reportedGetterResult` replaces the internal-names message for a literal with a `done`/`value` accessor that fails to convert to an iterator result, and names the `next(): any` alternative.

**Iterations.** The first session's fix run (`fix1`) failed only `TestErrors/iterator_result_getters`, a new test whose own `// error:` line gave line 22 for the error at line 23 (the test was corrected, the compiler's output was right); `fix2`–`fix4` were green (1,323 / 1,326 / 1,334 passes as tests were added). Review round 1 found B1 (`declaredLocals` asserted that every statement of a `let` initializer is a `LocalDecl`; now `declaredNames` collects the pattern's names) and B2 (the diagnostic fired where tsc merely types a literal in context; now it rewords only a conversion that already failed), plus S1–S3, all fixed and pinned before round 2. Round 2 found no blockers; its R2-S2 led to the `readsElement` change above and R2-S1 to C35 (pre-existing, H03b). ## Boundaries kept and known gaps

- Spread, `Array.from`, `new Set`/`new Map` and rest elements still take everything, as in JS.
- Typed `Map`/`Set` values, tuples, arrays and strings keep their direct paths; their declarations' pattern names are now loose (undefined past the end).
- Typed names that parameter patterns, `for…of` bindings, nested patterns and patterns inside a rest element bind past the end throw (RangeError for arrays, a checked TypeError for iterables): H11.
- Destructuring assignment over iterables (`[a, b] = it`) stays PTS1001.
- H03b: C28 (methods of generator objects and runtime iterators through `any`), C30 (`it.next()` on a typed iterator builds its result at the call), C32 (`yield*` doesn't pass inner results through), C33 (an elision reads `value`), C35 (`as IteratorResult<T>` of another layout reads the field offset: a wrong value or SIGSEGV; pre-existing).
- H04: C34 (`get [Symbol.iterator]()` in an object literal panics `accessorFields`; pre-existing).
- A generator's or async function's parameter patterns still run at the first `next()` or later (D-109's known gap).
