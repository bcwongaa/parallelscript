## How the probes are run

Every probe under [probes/h01b/](probes/h01b/) starts with a machine-readable header: row, `red` or `control`, oracle (`node-self`, or `node:<name>.oracle.mts`, a sequential Node equivalent for programs that use `.par`/`pts:parallel`), thread counts, runs per thread count, expected Node behaviour, baseline PTS behaviour and, for a red probe, a `failure:` regex stating how it fails today. [run_probes.py](probes/h01b/run_probes.py) builds each probe with the given CLI, runs it at every thread count `runs` times (60 s timeout, 4 GiB address-space cap), runs the Node oracle, and compares **stdout and exit code** (stderr retained, not compared). A probe *passes* when PTS builds it and every run matches Node. The oracle must exit 0 with some stdout; otherwise the probe is an `oracle-error`. A timeout is its own outcome and never expected. A red probe behaves as claimed only when it fails (a Go panic, a diagnostic or a mismatching run) **and** its `failure:` regex matches the failed build's stderr, or the stdout and stderr of every run that differs from Node, **but not** the oracle's stdout (a regex that correct output also matches proves nothing). Panic regexes name the panic line and the first `pts/` frame; wrong-output regexes name a wrong line, or a run of lines (C18's eager order, a repeated unflattened line), that Node's output doesn't contain, which the runner enforces. A control behaves as claimed when it passes. The script exits 0 only when every probe behaves as its kind says. So once a fix task lands, a red probe that starts passing, or that fails some other way, is reported, as is a control that breaks. Each result records the probe's sha256.

Runner self-check, with throwaway probes in scratch: a red probe whose oracle file is missing, a control where Node and PTS both throw with empty stdout, a red probe whose `failure:` regex doesn't match its actual wrong output, and a red probe that runs past the timeout were all reported `BAD` (`oracle-error`, `oracle-error`, `run-mismatch` not as claimed, `run-timeout`). So was a red probe whose regex also matches Node's correct line while its real mismatch is unrelated (the reviewer's recheck case). The same program with the right regex was `ok`, and the runner exited 1. The review prompted these checks (below): the first version of the runner accepted the first two, and the second accepted the regex-matches-Node case, where two C05 regexes had that flaw.

The parent's final run, with the parent's own CLI from the main checkout:

```sh

python3 docs/agent/hardening-evidence/probes/h01b/run_probes.py --pts "$PWD/pts-bin/pts" \
  --node "$HOME/.local/node/bin/node" --scratch "$scratch/final" --out "$scratch/final.json" \
  docs/agent/hardening-evidence/probes/h01b/*.pts docs/agent/hardening-evidence/probes/h01b/parent/*.pts
# exit 0: "73 probes, 0 not behaving as their kind says"
```

Record: [h01b-probes.json](h01b-probes.json) (every command, exit code, stdout, stderr, per-thread outcome group and probe sha256). All 13 C01 panics are `interface conversion: ir.Type is *ir.Primitive, not *ir.MapType` at `pts/lower/records.go:280`, and all 7 C02 panics are `cgen: no check for void` at `pts/cgen/checks.go:305`. The `failure:` regexes now enforce this, and the reviewer independently compared the wrong-output reds with their headers (below). The `failure:` lines were derived from the parent's previous full run and reviewed by hand; that run (72 probes, before the typed array-pattern probe and the regexes) also exited 0.
