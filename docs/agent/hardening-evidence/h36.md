## The arm64 job's failures (C362–C365, D-227)
Every arm64 run failed the same tests (`ci-logs/` in [h36-parent-probes.tar.gz](h36-parent-probes.tar.gz)):
- `TestGeneratedNumberCorpusMatchesNode/{methods_1,methods_2,math}` (9, 6 and 6 lines) and `TestRunMatchesNode/{number_library,math_library}`: parseInt in radixes that aren't powers of two and Math's transcendental functions print other last digits than Node on arm64. The first run (`bdc769e35`, before H35b) also failed `TestStress/race_fields` at 4 and 8 threads, which no later run did: that is C356's race, which H35b fixed.
- `TestPublishAddsNoInstructionOnX86`: `exit status 1` from clang compiling for x86-64 (C363).
- The step after the suite, the stress programs ten times each, never ran, so H35b's litmus hasn't yet run on arm hardware.

**Cause (C362).** x86-64 Node prints exactly what PTS prints on arm64 (`parseInt("1877849bg6cba000000000000000000000000",23)`, `Math.tan(-4503.8727210219895)`, `Math.sinh(-0.20922595734114824)`, `Math.sin(-0.4115036939249933)`), and Node's official linux-arm64 binary (v24.21.0, sha256-checked, run under qemu-aarch64 through binfmt_misc) prints the CI's values: Node's own output differs by processor. Node's arm64 binary is built by GCC 12.2 (`strings`: `GCC: (GNU) 12.2.1 20221121 (Red Hat 12.2.1-7)`), whose default `-ffp-contract=fast` fuses products into adds in V8's C++; PTS's ports of that code compile with `-ffp-contract=off`.

**A local oracle.** With `/tmp/pts-h36/arm64-node-bin/node` (that Node under qemu) first on PATH and `PTS_TARGET=aarch64-linux`, the differential tests run the aarch64 build against arm64 Node on this machine: on the base they fail exactly as CI did (`red/arm64-node-red.txt`: 9, 6 and 6 lines, number_library and math_library).

**The parent's first try** (`#pragma clang fp contract(fast)` over ieee754.c and parseInt's loop on aarch64) left 4 corpus lines (atan twice, atanh, asinh: `red/arm64-node-try1.txt`); the reproducer then showed it is worse than it looks (below).

### Node's numbers on macOS
Node's darwin-arm64 binary (v24.21.0, sha256-checked) exports `v8::base::ieee754::*`: counting `fmadd`-family instructions in each, they equal those of PTS's port compiled for aarch64 with `-ffp-contract=on` in 18 of 20 functions (log 14 against 13, tan 34 against 32, where clang 18 rewrote exact products such as `2.0*x`), and differ from `fast` (GCC-like) in 9 (`darwin-fma/` in the parent's archive). So Node's macOS build fuses within one expression, as Apple clang's default does, and the suite and the recorded expressions confirm it on the runner (rounds 2, 4, 5).

### The stack guard's cost
Mach-O reaches `pts_stack_limit` (a `_Thread_local`) through a call to its thunk in every guarded function (`otool -tvV` of fib: `adrp`, `ldr`, `blr x9`). Round 5 built fib's C again with the guard removed and ran both, interleaved: fib(34) 62, 65, 68, 62, 65 ms with the guard, 68, 69, 69, 60, 60 ms without: no measurable cost, so no thread-specific slot read from `TPIDRRO_EL0` (Go's way) was added. Node took 76–80 ms there.

### Open files (C370)
